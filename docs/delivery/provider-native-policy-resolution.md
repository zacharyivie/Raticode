## Explicit grant matrix and implementation gate

The matrix assumes an exact selected MCP set, such as only `alias__swarm_action`, while other ambient MCP tools remain forbidden. `true` authorizes a category but never overrides an upstream prohibition. Support means that the selected MCP operation remains usable AND every disabled native category stays disabled even when upstream would skip its callback. These are design conclusions from the traces below, not passing runtime tests.

| Provider | shell | web | Candidate contract and present decision |
| --- | --- | --- | --- |
| Gemini | false | false | Private effective admin policy with exact selected MCP allows and fallback deny. Conditionally plausible in an unmanaged environment; not demonstrated production support. Reject if central TOML suppresses the policy, prior prohibitions cannot be preserved, or effective loading/session continuity is unknown. |
| Gemini | false | true | Same policy, plus explicit native web-tool allows above fallback deny. Shell stays denied. Requires complete web-tool identity coverage and prior-policy intersection; neither installed dispatch nor session continuity is proven. Reject until those checks pass. |
| Gemini | true | false | Same policy, plus explicit native shell allow above fallback deny, retaining native web denial. Requires prior-policy intersection and installed dispatch proof. Do not infer web denial from an MCP-only callback handler. Reject until proven. |
| Gemini | true | true | Same policy with explicit shell and web allows. No Raticode denial needed for these two categories, but exact selected MCP and existing upstream prohibitions still matter. This is not permission-free operation; reject until policy loading, intersection and exact MCP execution are proven. |
| Grok | false | false | Root deny flags do not reach ACP; callback-only denial misses safe-shell and remembered MCP execution. Native profile filtering is a conditional mechanism with unresolved model precedence and exact MCP dispatch isolation. Unsupported on present evidence. |
| Grok | false | true | Same missing shell boundary. Web permission does not repair shell or selected-MCP enforcement. Unsupported on present evidence. |
| Grok | true | false | Shell is authorized, but launch web-disable is not a demonstrated denial of every native fetch/search path. Exact MCP restriction also remains unresolved. Unsupported on present evidence. |
| Grok | true | true | Native shell/web restrictions are unnecessary, so those gaps alone do not block this row. Exact MCP selection still cannot be enforced against ambient preapproval by the callback, and profile filtering has not closed that gap. Unsupported for this exact-MCP contract on present evidence. |

No row is currently a verified production-supported combination. This does not mean that all rows require the same repair or that the upstream providers are intrinsically incapable. For a configuration with no MCP selection, absence of selected tools must still exclude ambient MCP; merely omitting injected definitions does not prove that. Relaxing exact MCP or forcing both grants true would change the task's permission contract and is not recommended.

Concrete backend decision: keep permission configuration separate from provider transport wiring. For each row, fail before `session/prompt` when its native enforcement prerequisites cannot be established, with an error naming the provider and unmet permission guarantee. Do not report AC2 complete from these errors. Do not silently blanket-deny selected MCP or silently elevate shell/web. The next implementation milestone can own a version-specific enforcement probe and adapter behavior; it must not treat a synthetic argv assertion as proof of native enforcement.

Gemini's minimum unblocker is effective-policy intersection and continuity for the conditional unmanaged recipe. Grok's minimum unblocker is a session-local rule/filter ingress that survives model selection and constrains actual MCP dispatch, plus native web coverage where web is false. A source-backed working ingress or a non-model installed compatibility result is the missing evidence, not another general survey.

## Gemini trace

All Gemini links below pin tag v0.60.0. The accepted injection addendum records release commit prefix `733edcb`, released September 15. A full commit SHA was not independently resolved in this pass; the tag is the source version used here.

1. [CLI configuration](https://raw.githubusercontent.com/google-gemini/gemini-cli/v0.60.0/packages/cli/src/config/config.ts), lines 745-799, sets `interactive` true for ACP. It passes approval mode, policy paths and MCP allowlist into policy configuration. Consequently, headless default-deny does not describe ACP behavior. `tools.exclude` comes from settings plus the special `ask_user` exclusion; a source comment mentioning an exclude flag is not evidence that such an argv option is supported.
2. [Policy configuration](https://raw.githubusercontent.com/google-gemini/gemini-cli/v0.60.0/packages/core/src/policy/config.ts), lines 61-79, 264-305 and 525-600, gives admin tier 5, user tier 4, trusted-server allows 4.2 and allowed-server allows 4.1. Headless MCP auto-allow is conditional on noninteractive mode. Supplemental admin paths are discarded if the system directory contains any `.toml`. `--policy` replaces normal user-policy paths; it is not a safe additive override. Parse warnings do not prove installation. An exact MCP allow must be paired with denial of other operations, including other tools on that server.
3. [TOML loader](https://raw.githubusercontent.com/google-gemini/gemini-cli/v0.60.0/packages/core/src/policy/toml-loader.ts), lines 32-66 and 276-305, restricts priorities to integers 0-999 and computes tier plus priority/1000. Older tier descriptions in comments differ from current constants; use the constants above. Inflating a user priority cannot cross the admin boundary.
4. [Policy engine](https://raw.githubusercontent.com/google-gemini/gemini-cli/v0.60.0/packages/core/src/policy/policy-engine.ts), lines 136-179, 231-275, 376-395 and 423-458, matches MCP server identity separately, sorts descending priority and allows some known-safe shell commands when the preliminary decision is ask. An explicit matched deny survives shell parse failures. Default mode alone therefore does not mean no shell. Equal-priority conflicts should be rejected by Raticode rather than relying on incidental ordering.
5. [Base tool invocation](https://raw.githubusercontent.com/google-gemini/gemini-cli/v0.60.0/packages/core/src/tools/tools.ts), lines 170-203, turns allow into execution without confirmation and throws on deny. [ACP session](https://raw.githubusercontent.com/google-gemini/gemini-cli/v0.60.0/packages/cli/src/acp/acpSession.ts), lines 655-716, calls `shouldConfirmExecute` before requesting permission. Its callback lacks canonical tool/server identity. Deny ambiguous callbacks; never authorize a required tool by title, kind or call-ID prefix.

Conditional candidate, only after proving that supplemental policy loads and that it does not override existing prohibitions:

```text
gemini --acp --approval-mode default --admin-policy /PRIVATE/policy.toml --allowed-mcp-server-names raticode-session
```

The private policy should give exact approved MCP pairs higher priority than a fallback deny. This schematic fragment illustrates ordering, not the complete policy for all Rem grants:

```toml
[[rule]]
mcpName = "raticode-session"
toolName = "swarm_action"
decision = "allow"
priority = 950

[[rule]]
toolName = "*"
decision = "deny"
priority = 900
```

Inference: in an environment where this is the effective highest tier, the fallback blocks native shell/web and unselected MCP operations while the exact pair can pass. It also denies other native functionality, so additional grants require separate explicit rules. This is not a recommendation to elevate MCP over a user's existing denial. A restrictive overlay must retain effective prior prohibitions.

Unsupported cases include central TOML with conflicting allows, conflicting or unreadable effective policies, unknown CLI builds, and exact MCP grants whose identity/readiness cannot be verified. A central allow can win while Raticode's supplemental deny is ignored. Even a currently compatible central policy requires proof of its effective behavior; scanning a directory once is vulnerable to changes before session configuration reload. [ACP session manager](https://raw.githubusercontent.com/google-gemini/gemini-cli/v0.60.0/packages/cli/src/acp/acpSessionManager.ts) reloads settings for session creation. No effective-policy acknowledgement or atomic restrictive-policy intersection was established over its ACP contract.

Minimum missing evidence for production support: a compatible installed build with a non-model policy probe that demonstrates the exact effective rules and failure reporting, plus a way to maintain the restriction through new/load sessions and policy changes. If that cannot be established without replacing managed settings, keep the combination unsupported. Do not change HOME, copy credentials or write provider settings to evade the conflict.

### Remaining profile and hook alternatives

These are additional observed source facts at the same Grok commit, accessed 2026-09-16:

- [Agent definition](https://raw.githubusercontent.com/xai-org/grok-build/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-agent/src/config.rs) accepts camel-case `tools`, `disallowedTools` and `injectDefaultTools`. An empty tool list inherits defaults. Internal `session_tools_allowlist` and `session_tools_denylist` have `serde(skip)` and cannot be supplied through profile JSON. `hosted_tool_allowed` checks hosted tool identities separately. Unknown JSON fields can be ignored, so successful parsing is not enforcement evidence.
- [Agent builder](https://raw.githubusercontent.com/xai-org/grok-build/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-agent/src/builder.rs) filters native tools, but ignores `mcp__` entries when resolving native allowlists and retains search/use MCP helpers. An entirely unresolved allowlist retains the toolset with a warning. Its MCP-access test proves helper retention, not restriction to one remote tool. Hosted `web_search` and `x_search` are filtered separately. The tests show denying the former alone leaves the latter. This provides a native filtering mechanism, not proof of an exact remote dispatch filter.
- [Profile resolution](https://raw.githubusercontent.com/xai-org/grok-build/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-shell/src/agent/mvp_agent/agent_ops.rs), `resolve_agent_definition`, can choose a strict model harness before ACP `_meta.agentProfile` unless an explicit agent name selection changes that branch. It later considers ACP and CLI profile paths. Consequently, a per-session profile cannot be claimed to apply regardless of model. No environment override is recommended to bypass this precedence.
- [Hook extension](https://raw.githubusercontent.com/xai-org/grok-build/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-shell/src/extensions/hooks.rs) accepts `_meta["x.ai/hooks"]` callbacks including `PreToolUse`. However, [hook execution and tests](https://raw.githubusercontent.com/xai-org/grok-build/37949780c144e37df692e3d669051a21fec24f20/crates/codegen/xai-grok-shell/src/session/acp_session/hooks.rs) explicitly continue on callback transport errors, timeout and malformed responses. A deny-capable hook that fails open is unsuitable as the sole Raticode permission boundary.

Inference: a pinned, compatible profile could help remove native tools before approval, but current evidence does not justify replacing the missing policy ingress with a general profile recipe. Remaining proof must cover dispatch through retained MCP helpers, strict model precedence, new/load/rebuild and hosted tools. The exact native tool IDs must come from the compatible build; do not assume display labels or provider-specific rule names are profile IDs. A profile that disables every MCP helper would violate the required selected-tool behavior.

Minimum missing evidence is one end-to-end, version-matched ingress-to-dispatch trace for a temporary restrictive rule set or tool filter, with exact selected MCP operations still executable and native disabled operations rejected despite ambient grants. Require a non-model installed-build compatibility check as well. A proof that no such API exists across the entire project is not claimed.

## Implementation fit, maturity and limits

Keep rule encoding, preflight errors, callback validation and process lifetime in Raticode's existing subscription modules. The checkpoint already owns temporary MCP metadata and immutable callback grants. Extend those boundaries only after the missing native contract is proven. No dependency, SDK, external orchestration, copied agent implementation or credential-store access is recommended. Shell/web denial here means native tool categories, not a full OS sandbox or a promise that an expressly granted MCP server cannot perform those operations internally.

Reuse M1d/M1e release, source-sync, maintenance and operational-readiness findings. This pass adds observed upstream permission regression tests, not executed results or a new adoption claim. Gemini has a recent versioned release; Grok's source/binary mapping still needs verification. Popularity is not evidence of this permission contract.

The preceding M1f pass reported neither `gemini` nor `grok` on PATH; this repair did not repeat binary discovery. No package install, binary invocation, auth access, model call or persistent provider write occurred. Several guessed Rust module paths returned 404 before directory `mod.rs` paths worked. Web `find` occasionally reported no match for text visible in `open`; cited positive findings use displayed source, while those negative searches cannot prove absence. No upstream build ran, and profile/reload/web-variant coverage remains incomplete. These gaps limit support claims rather than becoming assumed passes.

No product baseline suite ran for this documentation-only assignment. Updated board evidence reports the old host checkpoint suite completed with 2,101 passes, two skips and one launcher failure; the isolated launcher test passed after an ignored environment repair. The earlier socket-stall report is historical, not a current established blocker. These are attributed host results, not checks run here. ACP-S1 has separately recorded independent closure; new provider and final combined checks remain outstanding.
