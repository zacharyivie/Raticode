Raticode implementation record · 27 September 2026 · Prepared by Rem

An organization you can take back through time.

The Organizations tab now connects persistent Rem employees, owned work, and revisioned company settings. Every configuration save records a complete snapshot. Restoring an earlier state adds a revision and pauses execution.

Source checkout: /home/doonk/Projects/Raticode/Raticode. This is an implementation in the checkout, not an installed desktop release.

Experimental in 0.3.8

Organizations is disabled by default. To opt in, quit Raticode completely and launch it with RATICODE_EXPERIMENTAL_ORGANIZATIONS=1 in its environment. Removing that variable and restarting disables organization management, new employee runs and routine webhooks. Existing data remains available for a later opt-in; recovery still attempts to stop previously authorized external jobs.

Rem receives organization management tools only when this feature is enabled. All organizations start paused after a restart. Review interrupted effects before resuming work. Remote stop reconciliation runs in the background so an unavailable gateway does not block application startup.

Use this release to evaluate supervised tasks and review their evidence. Live provider, gateway and paired-desktop behavior still needs validation with release packages before relying on unattended execution.

Configuration belongs to the user and Rem

Rem receives a turn-scoped organization capability. Its changes identify the conversation in the audit actor. The authenticated desktop API records the actor as the user; request bodies cannot choose their own audit identity. Employee capabilities bind to one organization and a runtime generation. The application rejects employee configuration changes, imports, restores and company start/stop requests. Pausing or changing settings revokes old operational capabilities.

This is an application permission boundary. Employee runtime files use a separate directory, and the managed tools enforce their scope. Unrestricted shell access under the desktop user's operating-system identity is not isolated from that user's files and processes. These controls do not make a hostile full-access employee incapable of bypassing application storage. A hard guarantee would require an OS or container boundary across provider execution and delegated work.

Organizations own Raticode projects

The Organizations tab lists every configured organization, regardless of the current project, including when no project is open. Open an organization's Projects tab to assign project folders. One organization can own many projects; a project can belong to one organization. Git worktrees share their repository's ownership, including worktrees created after assignment.

The first assigned project is the default employee workspace. Select another project and choose Use as default to change it. Individual project properties include removing ownership, which leaves files intact. Ownership changes are revisioned and pause employees. Restore checks current ownership and cannot take a project from another organization.

Task groupings previously called organization projects are now Initiatives. Find them through Org chart alongside Teams and owned Projects. Each initiative retains its owner, task assignments and optional workspace in an owned project or worktree. The Agent Companies package format and API retain projects and task.project for initiative compatibility; projectRoots contains Raticode project ownership. Local ownership is not exported in portable packages.

Existing organizations migrate on startup with their history intact. Migration assigns previous workspace folders to their organizations. If multiple organizations referenced the same repository, the earliest organization keeps ownership; the others remain available and paused with a review notice. Their conflicting initiative workspace bindings are cleared and the previous values remain in configuration history.

Recovering a healthy configuration

Open Organizations → Configuration history. Revisions are grouped by calendar date in the viewing user's local timezone; persisted timestamps use UTC.

Expand changed fields and inspect the actor and reason. Employee changes have stable ID paths, so a role or provider edit is distinguishable from replacing the roster.

Select Preview restore. The preview compares the chosen state with the revision that was current when the preview opened. A concurrent edit causes a conflict instead of being silently overwritten.

Enter a reason and restore. The organization pauses, active turns receive cancellation, and the old settings become a new revision. Existing tasks, comments, working memory, usage and prior revisions remain.

Restoring configuration does not undo code changes, Git operations, remote actions, completed workflows or spending. Interrupted work is marked for review before retry. Historical configuration is stored in organizations.sqlite3 beneath the server's data directory. Back up that database using SQLite's backup mechanism, or stop the server before copying its database files.

Paperclip format support and limits

The reference is Paperclip's Agent Companies v1 draft. The importer accepts a self-contained company folder through the API or a ZIP through the UI. The package uses COMPANY.md, nested TEAM.md, AGENTS.md, PROJECT.md, TASK.md and SKILL.md.

Local includes, sibling instruction documents, reporting references, conventional skill names, starter tasks, recurring declarations, attribution and supporting skill assets are handled. Known Paperclip local adapters and model settings are mapped. Raticode exports portable execution settings in .raticode.yaml. Local workspace and Second Brain bindings, custom resource connections and persona memory are not exported as portable runtime settings.

The implementation is not exhaustive Paperclip compatibility. Remote includes must be vendored locally first. Standalone TEAM.md and AGENTS.md roots are wrapped in a paused organization and retain their local includes and assets. Known local adapter settings are mapped. Other vendor-specific runtime fields remain review material; executable remote destinations use the documented Raticode job protocol and explicit local grants. Unknown Paperclip settings require review; the original sidecar is retained with imported package data but is not emitted as an executable Paperclip configuration on export. Raticode does not implement Paperclip's REST service.

All imported organizations start paused. Local folder bindings cannot be granted by imported project metadata. ZIP traversal, symlinks, duplicates and oversized payloads are rejected. The GitHub importer fetches a public archive pinned to a 40-character commit, rejects redirects, limits compressed and expanded content, and records hashes of imported assets. Nested remote includes remain unsupported.

Audit fixes and operating controls

Start work preserves individual employee holds. Operations provides a separate Resume all employees command. Names, titles, team labels and instructions can change without interrupting active work. Instructions and models apply on the next turn. Permission changes revoke affected claims; owned workspace changes and restores pause the organization. The editors show affected running tasks before saving.

Tasks preserve an explicit execution workspace separately from initiative IDs. Cancellation signals the provider, clears the claim, revokes its tool authority and cancels managed descendants. Late output cannot reopen cancelled work. Reopen is explicit. Preparation and thread-start failures record a blocked attempt and release capacity.

Tasks have dependency links with cycle checks, an independent reviewer, versioned plan approval, completion acceptance, goal links, file artifacts and run records. Completing a dependency wakes existing work in the same transaction. Comments can explicitly unblock owned work. Creation, comments and wake requests accept scoped retry keys. Structured reviews can accept, reject or request revision.

Operations

  • The work queue supports text, assignee and initiative filters, a Needs you filter and 50-task pages. Each task shows why it is waiting. Configuration history has bounded pages; Activity retains its sequence cursor. Unchanged organization reads return a small version receipt.
  • Routines use cron with a timezone, intervals or authenticated API triggers. Each trigger has an occurrence identity. Overlap can skip or queue behind existing work; missed runs can skip or coalesce. Retrying a skipped trigger cannot create work later.
  • Structured goals have stable IDs, owners, levels, parent links and status. Progress includes descendant goals. Outcome reports show acceptance, rework, human review waiting time, elapsed runtime, known costs and missing cost coverage. Accepted-outcome costs include managed descendants. Routing suggestions require at least three accepted results per compared employee in the same goal and initiative. A user can select a cohort of up to ten pending tasks; reassignment clears plan approval and requires result review.
  • Rehearsal uses a copy of organization state and a supplied clock. It estimates queue order using stated or historical durations, workspace serialization, dependencies, routine occurrences and monthly turn reservations. It calls no provider. Review decisions, future dollar costs and external effects are not predicted.
  • Source-linked memory stores a file hash, author, verification time and optional expiry. Before a turn, changed or expired evidence becomes stale, leaves the verified-memory prompt and queues one backlog recheck.
  • Workflow contracts compile an attached workflow.rattish, validate inputs and run preflight. The preview reports source and IR hashes, declared resources and completion checks. The preview itself does not execute work. Authorize workflow execution queues the reviewed source and contract; compilation hashes, input validation, node grants, provider-turn reservations and completion checks are enforced at launch.
  • Employees have explicit workspace allowlists. MCP environment values may reference secret://id when the employee has that secret grant. Credentials remain in the OS keyring service Raticode organization secrets. Reference rotation or revocation stops affected work. Saved provider output and tool arguments redact resolved credentials and temporary capabilities.

Storage and scope

SQLite now stores task bodies, append-only comments, attempts, occurrences, retry receipts and usage separately. Existing runtime JSON migrates transactionally. Comment activity stores the new comment, not all previous comments. A synthetic 100-comment run, with 1,024 characters per comment, produced 119,194 event-payload characters versus the audit's 5,584,150. This is a storage measurement, not a latency benchmark.

Idle dispatch skips unchanged write transactions. Sidebar summaries use task counts without loading conversations. Cached Git identity uses filesystem markers to detect initialization and worktree changes, and ownership checks warm the cache before writer transactions. Dispatch rotates organizations and ages task priorities. Operations displays both configured concurrency and the eight-turn service ceiling.

Swarm and fleet launches are available as managed tasks. Swarms reserve their configured maximum provider turns and run one member at a time inside one organization concurrency slot. Paired-desktop jobs reserve one provider turn and retain the target-local grants. Destination changes pause the organization and revoke active claims. Native provider children and unrestricted shell processes are not an organization sandbox. Dollar limits still rely on reported usage and can overshoot while direct work is in flight.

Export template creates a starter company definition. It is not an operational backup. Use SQLite backup for complete recovery. Operational backup downloads a consistent SQLite snapshot containing all organizations, revisions, comments, attempts and receipts. It excludes OS keyring credential values. Restore it with the application closed, retaining the original file for rollback. Signed external webhooks and HTTPS job gateways are described below. Arbitrary Paperclip sidecars remain preserved metadata, not trusted execution configuration.

Managed execution and recovery

In Operations, add an execution destination with an ID, a runtime and an employee allowlist. Swarm destinations name an existing swarm in the task workspace; its permissions and resources must match the assigned employee. Paired-desktop destinations name the device, granted thread and target project. Remote destinations name an HTTPS base URL and an employee-granted secret reference.

A task selects execution: {"targetId": "destination-id"}. Employee-created tasks retain their parent task and run. The dispatcher reserves the destination's entire turn allowance against company, employee, initiative and task limits before launch. Completed receipts return unused reservations. Uncertain work retains the reservation. Local swarm and workflow providers stop before another invocation when observed cost reaches the available dollar budget, or when cost coverage is missing under a dollar limit. Already running work can exceed observed dollar limits.

Cancellation retains the external handle. Unknown or unconfirmed stop results hold further dispatch. Use Check stopped executions to retry confirmation. An interrupted local workflow or permanently unavailable target requires inspection; Confirm stopped after inspection records the user's evidence. A restart never replays a launch. The paired-desktop extension is optional and leaves the canonical mobile v2 schema unchanged. Older desktops reject managed-job fields before dispatch.

Workflow contracts

Save a workflow path, inputs, turn reservation, allowed resource IDs and completion checks. Validate to see the required node:<id> grants and any nested workspace:<absolute-path> grants. Review the workflow before granting its nodes, since a node grant authorizes its compiled commands, provider settings and bindings. Nested workflow compilation fingerprints are checked and execution stays within organization and employee workspace grants. Provider calls and executable nodes run serially within the managed task slot.

workflow_launch requires the task revision and the preview's irSha256. The authorization binds source and IR hashes plus the entire contract. Editing the task plan clears authorization. The runner collects node results and workflow outputs. Completion checks use {"kind":"output","name":"result","equals":true} or {"kind":"file","path":"reports/result.html","sha256":"optional expected hash"}. Failed checks block the task; successful execution goes to independent review.

HTTPS gateway protocol

Configure a trusted gateway that implements raticode/jobs/v1. Raticode sends an OS-keyring credential as a bearer token and rejects redirects. Requests time out after 15 seconds; replies are limited to 1 MiB.

RequestContract
PUT {base}/jobs/{requestId}Idempotent submit with protocol, requestId, text, lineage, turnLimit, maxConcurrency: 1 and optional budgetUsd. The gateway must enforce these limits and retain the request ID across retries.
GET {base}/jobs/{requestId}Return matching requestId and state. Terminal completion includes text, turnsUsed and usage with observed cost_usd and token counts. Missing cost stays unknown.
DELETE {base}/jobs/{requestId}Idempotent cancellation request. Only a later terminal receipt confirms settlement. Lost submit replies also cause cancellation; the launch is never retried under a new ID.

States are queued, running, completed, failed, rejected, cancel_requested, cancelled and outcome_unknown. The destination is an explicitly trusted service; application accounting cannot sandbox an arbitrary remote server or provider-native children.

Signed routine webhooks

Enable a webhook for a routine in Operations and select a signing-secret reference. POST a JSON object, at most 64 KiB, to /api/organization-webhooks/{organizationId}/{routineId}. Supply X-Raticode-Timestamp as Unix seconds, X-Raticode-Delivery as a stable delivery ID, and X-Raticode-Signature as sha256=HMAC-SHA256(secret, timestamp + "." + deliveryId + "." + rawBody). The receiver accepts timestamps within five minutes and at most 60 new deliveries per minute per organization. Retries use the same delivery ID and body with a fresh signature if necessary.

Each delivery queues the routine's fixed task template, respecting overlap behavior. The body is authenticated and hashed; it cannot override assignments, resource grants or approval policy. A repeated ID with different content is rejected. Requests can queue work while the company is paused, but execution still requires Start. Rotation and revocation take effect on subsequent deliveries.

Manage Organizations through Rem

Rem can use organizations.organization_action for every management operation in this tab. The tool is available in project threads and global threads, including when no project is open. Global organization management does not select a project or grant native file-editing tools.

Start with action=help. It returns the action catalog, configuration/task/routine schemas, session read-only status and allowed workspacePaths. Use list to locate the organization and read before changing it. providers returns the same provider, model and effort catalog as the employee settings picker, with an optional boolean refresh. configure takes the full configuration, expectedRevision and a reason. This covers employees, reporting lines, teams, initiatives, owned projects, goals, budgets, resources, execution destinations, Second Brain and report styling. Preserve unrelated fields when saving.

Work and operating actions include task creation and updates, comments, approval, review, cancellation, reopening, routines, routing trials, memory evidence, artifacts, workflow authorization, signed webhook configuration, secret references and credential rotation. Inspection includes activity, revision history, outcomes, rehearsal and execution receipts. Recovery includes configuration restore, execution reconciliation, inspected stop confirmation and operational backup.

import_preview and import accept exactly one source: files as a map of package paths to base64 bytes, zip as a base64 ZIP, or path to a folder or ZIP inside an open project. The organization MCP request limit matches the 24 MiB desktop limit; package limits remain 16 MiB and 1,000 files. Public GitHub imports require a pinned commit. Local project grants come from the validated open-project list independently of the swarm toggle.

Read-only and plan sessions cannot mutate organizations. Employee capabilities remain narrower than Rem's management capabilities. Workflow launch still requires user authorization. Credentials remain in the OS keyring; use protected credential entry when a value has not already been supplied to Rem. Changes remain attributed to the Rem conversation and follow the same revision and execution checks as the tab.
