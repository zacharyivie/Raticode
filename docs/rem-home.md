# Rem home

> User documentation for this feature is on the website: [Rem's home and tasks](../website/docs/rem/home.md). The website is the single source of truth for how Raticode works; this file is developer and design detail.

The rat-face tab at the top of the activity rail opens Rem's home: one continuous conversation and the list of work Rem is responsible for. There is no thread picker. Rem answers simple questions directly and starts a linked worker thread for anything else. The plan for the backend lives in the Second Brain report *Rem: conversation, responsibilities, and verified work* (7 October 2026).

The backend control service owns conversation history, tasks, schedules, worker threads, review and task controls. Until `/api/rem/*` responds, the home shows **Not connected**, disables sending, and starts no work. Development builds retain **Preview with sample data**, which loads explicit fixtures and labels the header **Preview**. Production never seeds sample data.

## Layout

- **Sidebar.** The Rem row returns to the conversation and summarizes Rem's state ("Working on 2 things", "1 thing needs you"). **+** adds a task. Tasks are grouped as Working on, Needs you, Coming up, Paused and Done (Done starts collapsed). Executing, verifying, repairing and cancelling runs show a spinner and their phase. Queued runs show a clock. Each row has a menu: Edit, Run now/again or Stop current run, Pause schedule or Resume, Dismiss (for runs that need attention) and Delete. Delete asks for confirmation inline.
- **Conversation.** A centered column with day separators and short Rem replies. When a Rem message refers to work, it carries a live work card. The card shows the task, its type, its current phase, the checks that passed, an **Open thread** link and, during review, a **Review** link. Links dispatch `gofer:rem-open-thread`, and the studio opens that thread in the Rem pane. A new conversation opens with Rem's animated sprite (it waves, blinks, and sleeps after 10 minutes; **Show Rem avatar** and **Animate Rem** in Settings control it) and four starter prompts. The thread list in the Rem pane no longer has a sprite or introduction. The composer is a single field: Enter sends, Shift+Enter adds a line.
- **Task sheet.** Opens on the right, or as an overlay when the workspace is narrower than 900px. A status card at the top shows the run's progress (Working → Checking/Fixing → Done), its work and review threads, and the controls for its state. Once a review has looked at the checks, the card lists them by outcome under the count line: **Failed** and **Unresolved** checks by name with the reviewer's reason (reasons over three lines fold behind **Show more**), then **Not checked**, with **Passed** folded below. An unresolved check is one the review answered `unknown` with a reason, such as a pass that wasn't accepted. A run being fixed shows the same list as *What the review found*. Before any review, only "N checks not run yet" shows. Task lists leave out run recipes, so each `criteria` entry of a listed run carries `description`, looked up by ID in the run's recipe, then a pending edit, then the task's current checks. Below it are the editable sections: *What should Rem do?* (prompt), *Kind of work* (Research, Maintain or Develop), *Project* (project_dir), *When* (Once, Daily, Weekly or Custom cron), and *Done when* (acceptance criteria). Criteria Rem suggested carry a **Suggested** tag. If you leave the criteria empty, Rem proposes them. Errand and Reminder tasks created by Rem show their type read-only. Interval schedules are described but not edited here.

Edits stay local until you save. Escape closes an unchanged sheet but never discards typed edits. If a change to the prompt, type, project or criteria affects a running task, the sheet says Rem will update the running thread, and the button reads **Save and update**. Server revisions replace the form only while it is untouched.

## Data the UI renders

The store (`frontend/src/lib/remHomeStore.js`) polls every 2.5s while a Rem surface is mounted. An event stream can replace polling without changing the components. `GET /api/rem/conversation`, `/tasks` and `/threads/{id}` include a content `version`. A poll that sends it back in the `X-Gofer-Known` header (older clients use `?known=<version>`) gets `{ unchanged: true, version }` while nothing changed (the conversation also keeps `context_ready`), so an idle poll downloads, parses and re-renders nothing. Keeping the version out of the address lets the browser reuse its cross-origin preflight, which the backend allows for 600 seconds (`Access-Control-Max-Age`). Task lists carry run summaries: `worker_traces`, `review_traces`, `config`, `recipe`, `worker_result`, `review_verdict` and `previous_success` stay on the server (`RUN_INTERNALS` in `rem_home_store.py`). The draft is read only by the composer, and message rows are memoized, so typing doesn't re-render the conversation. Every mutation sends a `request_id`. Edits also send `expected_revision`, and a 409 response keeps the draft and explains the conflict.

| Request | Body / response used by the UI |
| --- | --- |
| `GET /api/rem/conversation` | `{ conversation: { id, turn_state: "idle" \| "replying" }, messages: [{ id, request_id?, role: "user" \| "rem", body, created_at, work? }] }`. `work` is `{ task_id, run_id, thread_id?, title?, type?, state? }`. |
| `GET /api/rem/tasks` | `{ tasks: [Task] }` (see below) |
| `POST /api/rem/messages` | `{ request_id, body }` |
| `POST /api/rem/tasks` | `{ request_id, title, type, prompt, project_dir, schedule, acceptance_criteria }` → `{ task }` |
| `PATCH /api/rem/tasks/{id}` | `{ request_id, expected_revision, apply_to: "current_and_future", ...changed fields }`. Resume sends `enabled: true`. |
| `POST /api/rem/tasks/{id}/run` · `/pause` | `{ request_id }`. Pause also sends `cancel_current: false`. |
| `POST /api/rem/runs/{id}/cancel` · `/acknowledge` | `{ request_id }`. Acknowledge clears **Needs you** for a blocked, failed or unclear run. |
| `POST /api/rem/runs/{id}/retry_review` | `{ request_id }`. Reviews the saved work again, as asking Rem to "retry the review" does. 409 unless the run's review was interrupted and the task hasn't changed since. A task's newest run has `review_retryable: true` exactly when this would be accepted and no run is active. |
| `DELETE /api/rem/tasks/{id}?request_id=…` | Tombstones the task |
| `POST /api/rem/reset` | `{ request_id, conversation_id, confirm: true }` → `{ conversation, removed_thread_ids }`. Clears Rem’s history and tasks; see below. |
| `GET /api/rem/memories` | `{ memories: [{ id, text, created_at, source_message_id?, edited_at?, added_by? }], mode }`, newest first. `mode` is `on`, `paused` or `off`. |
| `POST /api/rem/memories` | `{ text }` (1–2,000 characters) adds a memory the user typed; the same words aren't added twice. Returns the list. |
| `PATCH /api/rem/memories/{id}` · `DELETE /api/rem/memories/{id}` | `{ text }` (1–2,000 characters) corrects one memory; DELETE forgets it. Both return the updated list. Text that looks like a password, key or token is refused with 400. |
| `PUT /api/rem/memory-mode` | `{ mode: "on" \| "paused" \| "off" }`. Returns the list. |
| `POST /api/rem/messages/{id}/undo-memory` | Reverses what that reply saved, changed or forgot and marks its `memory` note `undone_at`. Repeating it changes nothing. |

Rem messages can also carry optional rich fields. The body stays the complete answer, with its report links, so a client that ignores them loses nothing:

- `details`: Markdown under the short reply (at most 6,000 characters), shown behind **Details**. It can hold tables, task lists, code and ```` ```rem-chart ```` blocks (JSON `{type: "bar" | "line", title, labels, series: [{name, values}]}`, at most 50 points and 4 series). Invalid chart JSON shows as a code block.
- `suggestions`: up to three replies the user might send. A tap fills the message box and sends nothing.
- `meta`: `{ provider, model, seconds }` for a chat reply.
- `result`, on task updates: `{ title, type, state, checks: { passed, failed, total }, artifacts: [{ name, title, path, link, kind, size }], sources: [{ url, title, kind }], thread_id }`. It is built from the run record, not from model output, so it survives a failed summary call. Sources come from the worker's own search, fetch and browser steps (`rem_home_results.py` uses the same rules as `chatSources.js`), cited links first. The card hides only body paragraphs that are exactly one of its artifact links.

Under the newest update about a finished task (`kind: "task_update"`), action chips offer **Open report** (its first saved report), **Retry review** (when `review_retryable`) and **Run again** (when the task isn't running). They come from the task record only (`resultActions` in `remRich.js`), never from Rem's text, and call the same controls as the task sheet.

A long message's text folds (`FoldableText` in `RemRichParts.jsx`). `collapseLimits` in `remRich.js` sets the preview to 30% of the window height, kept between 168 and 360 px, and folds only text taller than 1.5 times the preview. The phone uses the same numbers in dp (`RemRich.collapseLimits`). Rem's newest message starts open and every other long message starts folded; a choice stays while the window is open. Only the text folds, so quotes, files, cards and actions stay in view. The full text stays in the page: tabbing to a link in the hidden part opens the message, and folding a message you scrolled through brings its **Show more** back into view.

While Rem replies, `conversation` has `turn_label` (what it is doing: "Reading your message", "Reading earlier messages", "Starting a task", "Writing the reply") and, with Claude Code as the chat provider, `draft_reply`, the reply text as it is written (saved at most about three times a second). Both clear when the turn ends. Screen readers hear the finished message, not the draft.

Web images in Markdown load through `GET /api/media-image?url=`, which uses the link-preview fetcher (public addresses only, no cookies or referrer). Clicking one opens it large over the window, with **Open in browser** for the site; if it can't load an image, the chat shows a link that opens it in a browser tab.

Files you attach, in Rem's chat or a thread, show as tiles in the composer and on the sent message (`AttachmentTiles.jsx`, shared through `ChatComposer`'s `MessageAttachments`). A picture or video gets a thumbnail, from the picked file before sending and afterwards from the stored upload through the media preview; other files get a tile with their type (`fileKinds.js`). Clicking one opens `AttachmentPreview.jsx` (loaded on first click): pictures, video and sound in the viewer, text and code as their first 256 KB, and other files as a card with **Open in editor** and **Open in its app**. A sent thread attachment has only its stored name, so the window asks `GET /api/chat/attachments/locate?storageName=` for its path; that accepts only Raticode's upload names inside the chat attachment folders and doesn't follow links. A file that has gone says **No longer available**.

Pictures and videos among a reply's `files` show inline under the reply (`RemMedia.jsx`), read through the same `raticode-media://` preview the editor uses (`textFiles.openPreview`), and each preview is released when the message leaves the chat. A video shows its first frame and length. Clicking a picture opens it large; clicking a video opens a player that starts playing (`MediaViewer.jsx`). Escape or **Close** returns to the chat, and **Open in editor** opens the file as before. The file's name under the preview still opens it in the editor. A file that has gone, or that this window can't decode, says so in place of the preview. Other files keep their plain button. Only files `reply_files` already accepted are shown, so this adds no new way to read a file. Highlighting and charts load on first use from `RichCodeBlock.jsx`, outside the main bundle.

A finished task's update can carry `files` and `reply_to` too, the same as a reply. When the user asks Rem to send a file whose path it doesn't have yet, Rem's decision starts an errand with `send_files: true`. The run that the request starts records the request's message ID as `deliver_files_to`. A chat `follow_up` whose patch (or task) has `send_files` does the same, and so does the run of a one-time task scheduled for later from that request (`delegation_context.source_message_id`). When such a run succeeds, the update prompt also gets the user's `request` and may return `files`. When the request asked only for a link, the paths become Markdown links under the update instead and nothing is attached (see **Links and settings**). Otherwise those paths go through `reply_files` with the worker result, review verdict and saved artifacts as the records, and the original request as the request that can name sensitive paths. Refusals are appended to the update. Repeating schedules, **Run again**, desktop-created tasks, runs without the flag and blocked runs never attach files; `files` from the model is ignored for them. If the update's model call fails, the plain recap is posted without files and a warning is logged.

A task has `id`, `revision`, `state` (`enabled` or `paused`), `type`, `title`, `prompt`, `project_dir`, `schedule`, `send_files`, `acceptance_criteria: [{ id, description, authored_by: "user" | "rem_recommended" | "project_rules" }]`, `next_occurrence_at`, `active_run`, `last_run` and optionally `recent_runs` and `deleted_at`. A run has `id`, `state`, `started_at`, `finished_at`, `thread_id`, `verification_thread_id`, `phase_label` (an optional override such as "Second pass after review"), `summary_short`, `acknowledged`, and `criteria: [{ id, result: "pass" | "fail" | "unknown" }]`. A schedule is `{ kind: "once" | "daily" | "weekly" | "interval" | "cron", local_time, weekdays, every_minutes, cron, timezone }`.

Run states follow the plan: `queued`, `executing`, `verifying`, `repairing`, `cancelling`, `blocked`, `outcome_unknown`, `failed`, `cancelled` and `succeeded`. An unknown state shows "Status unavailable" and never spins.

## Backend behavior

`src/gofer/ui/rem_home.py` runs the supervisor and reconciles durable responsibilities while the Raticode backend is running. `rem_home_store.py` stores the continuous conversation, immutable task revisions, occurrences, managed thread histories, request receipts and events in `rem-home.sqlite3` under the application data directory. Task edits use optimistic revisions; retries with the same request ID cannot repeat effects, and conflicting reuse returns 409.

The conversational provider receives a bounded snapshot of project tasks, workflow runs, threads, swarms, organizations, saved memories and authorized Second Brain notes. It runs separately from project work, with shell, web and inherited integrations disabled. Its structured response can answer, propose a task, remember an explicit preference, or request a validated task control. The backend provisions the worker and linked acknowledgement; conversation text never serves as an execution command.

Rem also searches its full stored conversation for relevant older messages and reads the corresponding linked worker transcripts, including archived threads. The initial context includes recent chat, matching older exchanges, a linked-thread index, and relevant transcript pages with report artifact paths. If Rem needs more context, it can request up to two additional internal reads through a private `recall` response. Reads can search chat and worker replies, page older chat by source message ID, or page a linked thread by thread ID and source message ID. No task, control, or user-visible message is created until Rem returns its final decision. Source text is bounded and shortened excerpts are marked. Thread reads omit provider thoughts and respect current project and Second Brain access. Deleted tasks and unlinked threads cannot be recalled this way.

Tasks created from chat retain the original request ID and retrieval references, rather than copying historical private text into their prompts. The backend rereads permitted sources for worker instructions, review, and Rem's clarification replies. This keeps the user's visible task prompt concise while giving workers the earlier report, requested timing, destination, and decisions. The current user request takes precedence over prior context. Invalid internal task fields get one repair attempt using that same context instead of asking the user to repeat the request.

`develop` tasks may omit `project_dir` for explicitly standalone tools and scripts. They use `<backend data directory>/rem-work/<task ID>`, shared by that task's worker, reviewer, and later runs. Project development still uses the selected approved project; `maintain` requires a project. Standalone development receives the same independent review, file fingerprint checks, and test receipt requirements. Implementing a daily reporting tool now is distinct from scheduling its implementation to repeat daily; the task prompt carries the requested report behavior and destination.

Each run snapshots its provider and task contract. Workers execute through the existing backend chat jobs and provider session handling. Visible worker messages contain the requested question or instruction in plain language. Permissions, acceptance criteria and supervision instructions go through the provider's instruction context, not the user's chat bubble. Review threads display readable findings instead of the JSON verdict used by the backend.

Rem is the coordinator, and worker threads are separate agents. Rem answers their clarifying questions and chooses routine defaults within the user's request. It does not invent personal facts or authorization. Consequential choices such as payments, irreversible deletion, publishing, deployment, external messages or expanded access require explicit user authorization, including authorization already supplied in the request. An attention decision must include a specific question for the human; ordinary questions directed to Rem do not require human participation. Worker authors are labeled in provider context while visible message bubbles remain plain.

The private task controls include `follow_up` with a required worker message, and `retry_review`. When the user answers a blocked worker in the main Rem conversation, `follow_up` requeues the same run and work thread, adds the new instruction to its requirements, and independently reviews the result. Rem's visible reply retains the work-thread link. Manual thread messages preserve their human authorship; coordinator messages appear once as Rem's ordinary reply. A message the user types in a work thread, whether it steers a running worker or prompts one that ended, stopped or failed, is the worker's next prompt as written: Rem adds no message of its own after it (earlier builds added "Please continue with the user's latest instruction."). If the user writes while a worker is still running, the thread shows the message where it was sent and the restarted turn answers it; the provider's private copy moves it after the stopped turn's last steps so it is the latest user message, which also keeps native session resume intact. Rem's own follow-ups, review findings and the opening task prompt remain Rem's messages.

User-role thread messages carry `sender`: `rem` for Rem's prompts and `user` for the human's. Messages saved before the user's were tagged are read as the user's, since Rem's prompts have always been tagged. The provider receives both as user-role messages, labelled `Rem:` or `User:` in its private copy. The desktop thread pane labels each instruction **Rem** or **You** and gives Rem's a tinted outline instead of the solid bubble; the phone's work-thread view (`rem.thread`) does the same. When Rem reads a linked thread, the `sender` field tells it which instructions it wrote. Task edits and new work remain separate controls.

When execution finished but its review was interrupted, `retry_review` and the existing **Run again** button reuse the saved worker result and work thread. They launch a fresh independent review without repeating development. An edited task needs a new run, and an active or uncertain run prevents another review from being queued. Run context distinguishes the worker result, blocking phase, and diagnostic details so Rem can explain what was saved and what remains unverified. Older blocked runs with a recorded worker result and review thread support this recovery too.

A task keeps one visible thread across runs while its project stays the same. Worker replies and readable review findings share that transcript. Review executes in a separate read-only provider session with its own message history, so independent verification does not create a second UI thread. Legacy separate review threads stay retrievable from old links but are hidden from the general thread list. Repairs, review retries and follow-ups on blocked or stopped work reuse them, and a follow-up after a finished run starts a new run in the same work thread. Only moving a task to another project opens a new work thread. A follow-up may change the task type and checks when the user requests a new action on the same work: workflow execution uses an errand rather than inheriting research read-only restrictions, and implementation uses develop or maintain. On a one-time task the change is saved to the task. On a repeating task it applies only to that run: the saved task, its revision and its schedule stay as they were, so the next scheduled run does its usual work in the same thread. Changing what a repeating task does needs an explicit task edit (the `update` control or the task sheet). Existing user constraints still apply. Rem distinguishes an unimplemented proposal from the current installed tool when answering setup questions. A terse “continue”, “try again” or “resume” goes to the most recent linked task: it continues stopped work or retries an interrupted review, and it never cancels work or creates a task. If the model proposes a one-time task matching an unfinished task's title and project, Rem follows up on that task instead. When a review repeats an unresolved result after Rem's follow-up, the run stops instead of looping. Rem explains the saved findings and remaining problem in chat. **Needs you** is reserved for a specific missing human-only fact or consequential authorization; operational problems appear as updates.

**What Rem remembers** (Rem options menu) lists the facts and preferences Rem saved, newest first, and lets you edit or forget each one, add your own, or copy them all as a list. Rem uses the change from its next turn. The phone's Rem screen has the same list and controls (`rem.memories` and the `rem.memory.*` actions).

How memory works, for every provider and model:

- **Saving and changing.** Rem's structured reply can add `memories` and return `memory_changes` entries `{id, action: update|forget, text?}` for saved memories, so "forget that" or "I moved to tea" changes the existing memory instead of adding a second one. An unknown ID gets one repair attempt. The same words aren't saved twice.
- **What reaches the model.** Every Rem prompt lists memories as `{id, text, saved}` with the memory mode. Up to 40 memories and 12,000 characters go as they are; past that, the ones sharing words with the request go first, then the newest, and the prompt says how many were left out. Worker and reviewer threads receive up to 20 memory texts (6,000 characters) as `user_memories` in their background, so a Codex worker and a Claude Code worker see the same preferences.
- **Seeing what changed.** The reply that saved, corrected or forgot something shows a note (`memory` on the message) with **Undo**. Undo leaves alone any memory you edited after that reply; it only reverses what still reads as the reply wrote it. Editing or forgetting a memory in the panel or on the phone also updates or removes its words in those notes. A memory Rem forgets because you asked in chat keeps its words in that reply's note, so Undo can bring it back, until you undo the note or clear history.
- **Modes.** *On* uses and saves memories. *Paused* uses them but saves nothing new; asking Rem to correct or forget still works. *Off* sends no memories and changes none, without deleting them. Clear history keeps the mode.
- **Secrets.** Memories that look like passwords, API keys, tokens or private keys aren't saved, whether Rem or you wrote them, because every memory goes to the chat provider. The reply note says how many were skipped.
- **Leftover copies.** Forgetting or editing a memory overwrites the freed database pages and checkpoints the log. Rem's chat calls ask Claude Code (`--no-session-persistence`) and Codex (`exec --ephemeral`) not to save their sessions, when the installed CLI lists that option. Other providers' CLIs may keep their own logs, and sessions saved before this change stay where those CLIs put them.

**Clear history and tasks** (Rem options menu, with confirmation) gives Rem a clean slate. The renderer releases its reset flag and immediately resynchronizes provider context, so the next message needs no app restart. The backend fences out other windows, stops running workers and Rem's own reply, and waits for them to drain. It then deletes every task, revision, run, message, memory, receipt, event, managed thread and transcript, and resets the conversation ID. It also deletes the workspace snapshot, steering receipts, job journals and provider session references for Rem's threads, then vacuums the database so deleted rows don't persist on disk. The renderer removes its local copies and archived copies of those threads. Users' own threads, project files, standalone task workspaces and saved reports are kept. A repeated request ID returns the original result, so the client can safely retry an interrupted clear.

Codex chat prompts travel through standard input for `exec`, native session resumes, compaction, and the safe pre-turn fallback from app-server. App-server turns receive their prompt through the existing RPC input. Full prompts and review evidence stay out of process arguments, avoiding operating-system argument length limits. Windows shims use the same standard-input delivery without a prompt-file instruction or a shortened user request.

Rem uses the internal `execution_mode: conversation` on an `errand` task for a discussion, casual chat or status update. The worker answers in a read-only thread; Rem reads the transcript and sends its actual replies in that same thread, answering questions as well as asking them. The private completion decision checks every criterion against the conversation and available receipts. `conversation_turns` preserves the requested minimum number of worker replies, defaulting to one for a simple question and three for "a few turns". Valid requests use one to twelve replies, with two additional replies allowed for clarification and a minimum overall budget of three. Early passing criteria cannot truncate the requested exchange count. A friendly closing question does not block an otherwise completed conversation. An empty continuation decision is retried once before reporting a controller error. Discussions need no whole-project snapshot, report artifact, or separate review thread; casual chats need no project inspection. The mode and turn count are not new UI settings. Old recipes default to `work` and one reply; code changes and saved research cannot use conversational execution.

For work tasks, a fresh read-only thread checks every current acceptance criterion, source content and relevant security/regression concerns. Success requires complete pass evidence, independent inspection receipts, unchanged project content during review, and command receipts for development/maintenance. Research additionally requires an artifact saved through the scoped output service with a matching content hash. Unknown evidence cannot pass. Failed review returns to the worker for up to two repair attempts, then becomes **Needs you**. A missing research report stops immediately when the worker's trace shows the provider refused the save tool (for example, plan mode or a permission denial), and after one follow-up when the worker repeats the same unsaved result or the save fails again with the same error; retrying cannot fix these. The follow-up quotes the last `save_report` error. Saved reports are never replaced: a taken name returns an error naming the next free `-vN` path, a path outside the report folder returns the relative form to use, and an absolute path inside the folder is accepted. If a report is written but its receipt can't be recorded, the error says so and asks for a new name. `rem_artifacts`, `rem_threads`, fleet and Organizations tools share one local tool server; an unexpected failure names its own service and error type (never a swarm), while the full detail goes only to the backend log. When a criterion can only be proven by a future event, such as the task's next scheduled run, the reviewer returns `wait_until` and `wait_for`. The run then waits in `queued` with "Waiting for … before checking again" and reruns only the review 30 minutes after that time. A run can wait up to three times, each within eight days, and a failed criterion still goes to repair. Cards show "N checks not run yet" or split passed, failed and unchecked counts, so a review that never ran doesn't read as failures. Codex reviewers start in a private scratch folder under `rem-work/review-scratch` that holds temp files and tool caches (`TMPDIR`, `MYPY_CACHE_DIR`, `PYTHONPYCACHEPREFIX`, pytest's cache disabled). Only that folder and temp are writable; the project and Raticode's data stay read-only.

When review identifies a worker clarification that prevents completion, Rem answers it using the same coordination policy and passes that reply to the worker. A specific unauthorized consequential choice is escalated to the human. Routine answers still require another worker turn and fresh independent review before completion; Rem's clarification cannot accept the work. Terminal runs clear their temporary phase label so cards display Done or Needs you rather than Reading the reply.

Finished task threads stay in the thread list. A finish the user hasn't seen is unread until they open the thread; one that finishes while its thread is open lands in Read. Rem never archives a task thread: the desktop owns pinned, archived, unread and read state, and Rem's later sync of the thread keeps it. New messages in an archived thread (another run, a repair or a follow-up) unarchive it, as does a turn sent or finished from the phone. Earlier builds archived worker and review threads when a run succeeded and stamped them `archivedAt`; startup and the renderer's next sync return those threads to the list once, and a later archive by the user sticks. The renderer synchronizes completed runs as well as active runs so final replies and unread state reach the normal thread list even when work finishes between polls. Finished transcripts are synchronized once per completion version.

Edits and instructions increment the run epoch, invalidate old evidence and stop the current turn before restarting with the latest contract. Provider processes must drain before replacement work starts. Changing projects creates a new worker thread. Messages from managed thread panes use the same lifecycle; ordinary chat endpoints cannot bypass it. Pause only stops future occurrences; Stop cancels the current occurrence; Delete tombstones the definition and requests cancellation without erasing audit history. Cancellation never reports success. Unconfirmed stops become **outcome_unknown** and block automatic retry.

Schedules support once, local-time daily/weekly, elapsed intervals and five-field cron. Missed occurrences coalesce into one run; a task cannot overlap itself, and managed runs sharing a project are serialized. A database lease prevents two controllers from admitting the same work. Restart preserves queued work and replays pending conversation decisions from the stored user message, with idempotent task controls. A request submitted before the first scheduler tick belongs to the current controller and is not considered interrupted. Saved worker results go directly to a fresh review in the existing review thread. When a result was not saved, a read-only reviewer first inspects the saved worker transcript, receipts and current files; mutating work continues only if that inspection establishes it can safely resume. Uncertain external actions are not repeated. Older runs blocked solely by the obsolete project-change check recover their saved results automatically once.

The renderer sends `POST /api/rem/context` with the existing provider/resource selection and current desktop folder grants. Grants refresh in the background, including when the Rem tab is closed or the window is hidden. Revoked project access or Second Brain cloud permission stops affected execution. Research reports save under `reports/rem` in the selected Second Brain, or the task's project when Second Brain is disabled. Paths and saved report hashes are checked by the backend.

### Opening and creating projects

When a request needs a local folder that isn't open, Rem's decision lists it in `open_projects: [{ path, create?, git_init? }]` and uses the same path as the task's `project_dir`. Rem does this without asking. The backend (`src/gofer/ui/rem_projects.py`) handles each folder before any task in the decision starts:

- **Safe paths only.** The path must be absolute. Rem refuses the filesystem root, the home folder or any folder containing it, credential and browser stores (the same list as file sending), `/proc`, `/sys`, `/dev`, `/run`, `/boot`, `/etc`, and Raticode's data folder. The check runs on the path as written and after following symlinks.
- **Nothing is overwritten.** `create: true` makes a missing folder and its parents. An existing folder opens as it is. `git_init` only runs in a folder this request created or found empty.
- **Clear errors.** A missing folder without `create`, a file in the way, or an OS permission error stops the whole decision. Nothing starts, and Rem's reply gives the reason. Concurrent requests for the same new folder create it once.

An opened folder joins Rem's projects with a backend grant that doesn't expire. It stays in the stored context until the window lists it. `GET /api/rem/conversation` reports such folders in `opened_projects`; the window adds them to its recent projects (without switching to them) and trusts them through its usual folder grant. The next context update includes them, and the backend stops reporting them. After a restart the backend re-registers the grants of folders the window hasn't listed yet. Rem's reply ends with a line from the backend saying what it opened or created. Organizations work that claims a folder as a project root runs as a task in that folder, because an organization only accepts folders open in the session. A worker that finds it needs another folder names it in its result instead of asking the user to open it.

`GET /api/rem/search?q=&before=&limit=` searches the whole saved chat without a model (`rem_chat_search.py`; see `docs/mobile-desktop-parity.md`, "Searching Rem's chat"). `GET /api/rem/threads/{id}` mirrors managed thread metadata, messages and active turn into the existing thread repository. `POST /api/rem/threads/{id}/messages` submits an occurrence-specific instruction. `GET /api/rem/runs/{id}` and `GET /api/rem/events?after=…` provide run details and durable event replay.

All seven Raticode providers support Rem conversations and delegated tasks: Codex, Claude Code, Cursor, Copilot, OpenCode, Antigravity and Grok. Tasks can carry optional `provider`, `model` and `effort` fields. Rem records an explicitly requested selection there, such as `provider: "cursor", model: "auto"` for "Cursor Auto". Worker turns, follow-ups, reviews and thread metadata use that selection. Unspecified fields inherit Settings > Rem at run creation. A different provider starts with its own CLI default model and no inherited effort; an explicit model also clears inherited effort unless the task specifies effort. Existing provider validation reports unavailable or invalid selections rather than substituting another model. Task selections survive scheduling, edits and retries without changing Rem's own conversational provider. **Settings > Rem > Rem chat provider** can give Rem's chat replies and proactive task updates their own provider, model and effort (`chat_provider`, `chat_model`, `chat_effort` in the context). Left empty, the chat uses the task defaults. Answers to worker questions and conversation reviews keep the run's selection.

Conversation messages are append-only. A task acknowledgement stays in its original place; results, problems, retries and follow-ups arrive as new messages, in sequence order. Each request shows a task card once: a follow-up that starts a new run puts the card on Rem's reply (or on "I’ll follow up and check the result." from a thread), not also on a separate "Started …" notice. Earlier builds wrote both; the conversation leaves out such a stored "Started …" notice when a reply for the same run was written within seconds of it. Task cards can reflect current run status without changing their message text. The task sheet's **Conversation** disclosure lists every linked update across runs, with links to the original chat message and its corresponding thread. Message navigation leaves unsaved task edits intact by requiring save or discard first. Stored legacy replies are visible again. New final recaps answer the original question in two or three short sentences, with concrete next steps and report links; complete findings remain in the thread.

Memory's report format and theme apply to all new informational documents, including notes, audits, plans, summaries and handoffs, wherever a provider saves them. Explicit user format requests take precedence, and source files retain their required formats. Managed research workers receive these preferences in both their provider prompt and the granted artifact tool's description. Read-only reviewers receive the same guidance without gaining report write tools.

Rem posts task updates proactively. Completion, blockers, failures, cancellation and uncertain restart outcomes append a durable `kind: "task_update"` message with the task and thread link, independently of user turns. Newly inserted messages emit a `conversation.message` event for replay; duplicate deliveries do not create another message or event. Visible Rem surfaces pick updates up on their regular poll. Updates created with the tab closed are retained and loaded when it opens. These in-app messages require no user permission. While Raticode is in the background, the desktop app also shows an operating-system notification when a run it saw working finishes, can't finish or needs you; clicking it opens the task. Update summaries never promise actions Rem can't take, such as changing a thread's permission mode: Rem's prompt lists the actions available, and first-person promises are removed from the update. If the conversation model answers without the requested JSON, Rem asks once more and then explains the problem in plain words instead of showing a parser error. Summary generation failures fall back to a durable update with saved findings and artifact links. Before asking an essential question, Rem rechecks the original request, memories, current workspace records and recalled chat/linked threads; routine choices and answers inferable from those records go back to the worker. External messages still follow the task's authorization rules. Provider exceptions retain their actual error in the worker thread and task update.

Review fingerprints have no project-size or file-count cutoff. They record every included file's path, type, permissions, size and full content, read in chunks of at most 64 KiB. Timestamps and inode identity do not invalidate unchanged content. The configured Second Brain's index database, its journals, configuration bookkeeping and the configured conversation archive folder are excluded; reports and source files remain checked. Symlinks are recorded without following them, and generated dependency directories are excluded. The scan runs in the background task worker and does not load project files into memory all at once. Larger projects may take longer to check. The reviewer still needs independent evidence for each acceptance criterion, including same-size edits with preserved modification times. A source change during review triggers up to two fresh checks in the same review thread, using the saved worker result without repeating implementation. Continued changes stop the checks, and Rem explains the limitation with the saved findings in chat instead of asking the user to retry an internal check.

Conversation decisions use isolated temporary directories with no project or integration grants. Grok uses its official headless tool allowlist and permission denials, including MCP denial; delegated Grok threads retain the existing ACP transport. Antigravity conversations select a private agent with an empty tool list. Its delegated threads use the existing native headless transport. Neither path relocates authentication or modifies global CLI configuration.

Task threads get the same tools as a new desktop thread: the Settings > Thread tools defaults (commands, web, subagents, browser, skills and MCP servers), the browser chosen in Settings > Browser, and the swarm access setting. Library skills and MCP servers resolve the same way, and the provider-specific configuration (Codex `-c` overrides with quoted MCP names, Claude Code's strict MCP config) is built by the same code. Rem adds its own `rem_artifacts` tool and read-only fleet status. Task threads don't get `rem_threads` or `fleet_send`, since a task never delegates itself again. Research and review keep commands and the enabled skills, which they only read; MCP servers, subagents and the browser stay off, and only research can use the web.

When two writer tasks share a project, the second normally runs in a temporary worktree under `rem-worktrees`. If an enabled skill sets the project's own worktree process (its name or description mentions worktrees, like `worktree-dev-flow`), Rem skips its worktree and starts the task in the project folder. The worker is told to follow that skill, leave the checkout alone and, since a task can't move its own thread, work in the skill's worktree by absolute path. Landing is the one exception to leaving the checkout alone: a develop or maintain task isn't finished until its branch is on local `dev`, and the task authorizes the fast-forward, including in the project's own checkout when `dev` is checked out there and it has no uncommitted changes. Two mobile tasks in November 2026 skipped the fast-forward for exactly that reason, and one was still accepted.

`rem_home_landing.py` enforces this. When such a run starts, Rem records the repository's local branch tips (`branch_tips`). Before acceptance, a branch counts as the run's own when it was created or moved during the run and one of the run's own git commands that writes (`worktree add`, `commit`, `rebase`, `merge` and so on) names the branch or its worktree folder, or an earlier turn of the run was already charged with it (`landing_branches`). Shared branches (`dev`, `main`, `stage`, `test`) and the branch checked out in the project's own folder never count. If one of the run's branches has commits that `dev` lacks, or tracked files with uncommitted changes, the gate returns a repair naming the branch and the land step; after the repair budget the run is blocked instead of succeeding. Projects without a local `dev` branch, read-only runs, runs in Rem's own temporary worktree and tasks whose prompt says not to merge into `dev` are skipped.

Managed research/review passes an explicit read-only scope to Raticode's organization and swarm services, regardless of provider. Cursor, Copilot and OpenCode also receive the existing adapter's read-only permissions. Grok and Antigravity delegated threads use CLI-managed native permissions, like their other Raticode features: their native policies remain authoritative rather than promising a Raticode filesystem sandbox. Review still requires independent inspection and unchanged project content. Copilot managed threads request JSON tool events; native successful completions, outputs and explicit exit codes are retained for verification. Errors, denials, incomplete turns and nonzero command exits cannot satisfy successful-check receipts.

An omitted or null task schedule means one immediate run. Explicit schedules are validated normally, so malformed recurring schedules cannot silently turn into immediate work. Invalid model decisions return a readable error instead of an internal validation traceback.

Operational limits: schedules require the Raticode backend to be running; reminders are durable in-app notices. Desktop notifications for finished work appear only while the app is running; phone notifications are not implemented. Live provider credentials remain in their existing CLI configuration. Tests use deterministic providers rather than paid live calls.

**Memory safeguards (Linux with systemd).** Every provider turn runs in a scope of `raticode.slice`, which slows down above 75% of RAM, may use at most 40% of swap, and has the kernel stop its biggest process at 85% of RAM, so parallel work can't starve the desktop. Each queued test, build or browser run (`Raticode slot run`) gets a scope of its own, `raticode-cmd-*`. Raticode measures its memory plus swap and stops it with SIGTERM, then SIGKILL, once it passes 35% of RAM. The agent reads why in the command's output, and the desktop shows no false "low on memory" warning. A kernel limit at 45% of RAM is a backstop only, and the desktop does warn if that one fires. New commands and new Rem workers wait while swap is 80% full, because swap is often compressed RAM. While memory is critical (under 10% of RAM free, or swap 90% full), the backend stops leftovers of finished turns every 15 seconds, biggest first: scopes whose processes now belong only to the service manager, such as Gradle and Kotlin daemons, adb or a browser an agent left running. It logs `RATICODE_RECLAIMED` for each one. A provider stopped by a signal reports why, for example SIGKILL when memory ran out, instead of a piece of its raw output.

## Links and settings

Asking Rem to *link* a file ("link me the video") gets a clickable link in the reply, never an attachment. Rem's prompt says so, and `wants_link` in `rem_home.py` enforces it without the model: when the request mentions a link and doesn't ask to send, attach, share, upload, transfer, download, email or deliver the file ("send me a link" still counts as a link), any `files` in the decision become Markdown links (`reply_links`). The same check covers a request Rem hands to a worker because it doesn't have the path yet: the run is marked to answer the request (`deliver_files_to`) as for a send, whether it starts now, is a chat `follow_up` or is a one-time task scheduled for later, and when the update's `files` arrive, `_deliver` reads the original request with `wants_link` and appends links instead of attaching. The update prompt says the file is linked rather than attached. What counts as a link request is decided by the wording of the user's message, not by the model. A link copies nothing, so the size limit and the sensitive-file rule don't apply, but the file must exist and, outside open folders, its path must be in Rem's records, as for sent files. Asking to send a file keeps using `files` and `reply_files`.

Full file paths in Rem's text are links too. `file_mentions.py` finds them for `GET /api/rem/conversation` without a model: from each place a path can start (`/` or `~/` after a space, bracket, quote or emphasis), the longest stretch of the line that names an existing regular file wins, so paths with spaces end in the right place. Folders, missing files, web addresses and relative paths aren't linked. Rem's messages, including their details, carry `file_mentions: [{text, path}]`; the user's own messages don't. `remarkFileMentions` in `frontend/src/lib/fileMentions.js` links that exact text in the desktop chat, and inline code that is exactly one of the paths; code blocks and existing links are left alone. Results are cached for 30 seconds per message text. The phone's `rem.home` result doesn't include the field.

Board ticket keys in Rem's text become ticket pills (user-facing behavior: [Talk to Rem](../website/docs/rem/home.md#talk-to-rem) on the website). `rem_kanban.TICKET_KEY` matches a whole word: a capital, capitals or digits, a dash and a number, not after a letter, digit, `_`, `-`, `/`, `.`, `#` or `@`, and not before a letter, digit, `_`, `-` or `.digit`. `RemKanban.resolve(keys)` looks the keys up without a model: Rem's `REM-n` by number in `kanban_tickets` (declined proposals left out), other prefixes against organizations' ticket keys, re-read at most every 5 seconds. Rem's own tickets win if an organization uses the `REM` prefix too. `GET /api/rem/conversation` carries `tickets: {key: {ticket_id, key, title, status, scope, organization_id, proposed}}` for keys in message bodies, Details and task cards, and `GET /api/rem/tasks` does the same for the tickets on tasks' runs, so a rename or deletion changes the version clients poll. `remarkTicketMentions` in `frontend/src/lib/ticketMentions.js` turns only those keys into `TicketPill` buttons, skipping code, inline code and links; anything else stays text. A pill calls `openKanbanTicket`, which opens the board and selects the ticket (`findRequestedTicket` explains one that isn't there). The phone gets the same index in `rem.home` and `rem.task` (`TicketMentions.kt`, `TicketPills.kt`).

A run keeps the tickets it touched in `run.tickets` (`[{ticket_id, key, title, scope, organization_id?, role}]`, role `created`, `worked` or `updated`, at most 40, merged by `merge_refs` with the strongest role kept). `RemHomeStore.work` copies them, and a `self_work` kind, onto every task card, so a card still names a ticket after the task is gone; clients prefer the live run's list. Self-work sets them when it claims a ticket (`worked`), when research adds proposals (`created`) or closes duplicates, and when a ranking judges tickets (`updated`). Tickets Rem creates or changes from chat are linked to the run the same reply starts or follows, and the reply names them by key (`TicketRequest.done_text`).

Self-work's runs are in the chat too. Each start writes `queued-<run>` with the task card and `self_work: {kind, batch}`; cards one `SelfWork.tick` pass started share the batch and clients show them as one message (`chatRows` on the desktop, `remRows` on the phone). Ticket runs get the usual outbox update. Ranking and research runs skip the outbox and post `finished-<run>-<epoch>` from `SelfWork.reconcile` once their results are read, so the update can name the tickets they proposed, left out or closed; the ID keeps a re-run from posting twice. Phone alerts for this work still come from the self-work report: `_rem_notices` doesn't give a task-update alert reason to a card marked `self_work`.

Report links in Rem use the same local-file handler as thread links. The clicked path is granted through the existing desktop bridge; files open in the editor, and directories open as projects with the Files tab selected. Recent-project menus give approximately ten rows room when the window height permits and retain the full scrollable history. Rem options → **Provider, model and effort** opens Settings → Rem directly. Those existing defaults apply to the next Rem message and new tasks and threads; saved task and thread selections remain unchanged.


Rem synchronizes managed threads while any app workspace is open. Transcript reads and writes for each thread are serialized, and opening a cached thread replays its transcript and running state to the pane. Managed snapshots replace stale versions of messages with the same ID. Terminal snapshots clear the worker spinner and include its final reply.

Writable Codex workers with web access selected can use the network from their workspace sandbox, including when executing authorized workflows. The CLI and app-server transports both carry this setting. Research and review retain their read-only permissions. Workflow commands that exit unsuccessfully preserve useful diagnostics from stdout as well as stderr; JSON failure summaries are reduced to the first concrete cause. Run failures appear in Problems with their node ID, and clicking one opens Run Timeline. Older generic failure receipts recover their explanation from saved command output without rewriting the receipt.
