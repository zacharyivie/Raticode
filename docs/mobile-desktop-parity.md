## Optional Tailscale address for phones, October 31, 2026

A phone may reach its desktop over the user's own Tailscale network away from home. The desktop opt-in is **Away from home with Tailscale** under Paired devices, which is off by default. When it is on and Tailscale is running, the desktop also listens on its Tailscale node address, using the same port and authentication as the LAN listener.

Wire contract, additive and opt-in:

- Request: `sync.request.payload.include_tailnet_endpoint: true`, sent together with `include_connection: true`.
- Response: `sync.snapshot.payload.connection.tailnet_endpoint` is `{host, port}` or `null`. It is present only when the request asked for it. `null` means the desktop's option is off, and the phone should then stop using any reported Tailscale address. While the option is on but the desktop isn't listening (just after it starts, while Tailscale restarts or signs in), the field is left out so the phone keeps the address it has. A brief Tailscale hiccup on the desktop no longer closes the listener or its sessions; only turning the option off or a different Tailscale address moves it, and the new address is bound before the old one closes.
- `host` is always an IP literal inside `100.64.0.0/10` or `fd7a:115c:a1e0::/48`. IPv4 is preferred. `port` is the LAN listener's port. The phone must validate both, and it must keep this address separate from `lan_endpoint` and from a manually entered LAN address.
- `lan_endpoint` and invitations are unchanged. Pairing still needs the LAN. Invitations never carry a Tailscale address.
- The flag grants no authority. The connection uses the same pinned, mutually authenticated TLS 1.3 session, and the desktop's per-phone permissions still apply.

Fixtures: `protocol/v2/fixtures/sync.request.tailnet.json` and `sync.snapshot.tailnet.json`. The phone repository's `protocol/v2` copy and `SHA256SUMS` must match this repository's files byte for byte.

Compatibility: older phones never send the flag, so they get the same snapshot as before. An older desktop rejects the unknown request field. The phone should therefore send it only while its own Tailscale mode is on, and the desktop should be updated first.
## Files and images in Rem's chat on the phone, October 30, 2026

Android 0.7.1 can attach files in Rem's chat, receive files Rem sends, and show web images in replies. All three need **Use Raticode from this phone**, and the phone uses each one only after the desktop advertises it, so an older desktop keeps working.

- **File channel.** `rem.home` results carry `files_thread`, a UUID the desktop derives for each phone. It is not a shared thread. `DeviceApplication` accepts the normal `file.*` events on it only from that phone and only while desktop control is on. The usual 10 MiB per file, 50 MiB quota and SHA-256 checks apply.
- **Phone attachments.** `rem.message` accepts `params.attachment_ids`, up to eight files that finished uploading on the channel. The desktop copies each one into Rem's chat attachments (`chat-attachments/rem-home`), which is where the window's own uploads go, then frees the channel copy. User messages in `rem.home` list `attachments: [{file_id, name, size}]`.
- **Files from Rem.** Rem's chat decision has an optional `files` list of absolute paths. `reply_files` in `rem_home.py` keeps only regular files up to 10 MB. Files in one of Rem's projects or the Second Brain folder need no mention in the conversation. Since November 1, 2026 any other file the account running Raticode can read is sent too, if its exact path appears in what Rem was given for that reply (the request, chat history and recalled task threads), or its folder and its bare file name both do, as in a worker's "Screenshots are in `/dir/`:" list (`listed_in_folder`). A name that appears only inside another folder's path doesn't count, so Rem never sends a path it guessed. When none of a reply's files can be sent and the reply does nothing else, Rem's message is just the refusals, so it never says "Here they are" above them; a task update whose files were all refused leads with the worker's own summary instead. Some files also need the user's current message to name the exact path: credential stores (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.kube`, `~/.docker`, password stores, keyrings and browser profiles); the coding agents' sign-ins (`~/.claude`, `~/.claude.json`, `~/.config/claude`, `~/.codex`, `~/.cursor`, `~/.copilot`, `~/.config/github-copilot`, opencode, `~/.grok`, `~/.gemini`, `~/.antigravity`); Raticode's window profile and `~/.local/share/gofer`; files whose names suggest secrets (`auth.json`, anything with credential, secret, token, oauth, password or api key in the name, `.env*`, `id_*` keys, and `.pem`, `.key`, `.p12`, `.pfx`, `.jks`, `.keystore`, `.kdbx`, `.ppk`); Raticode's data folder, or the folder above it when that holds `.gofer-trusted-bin` (chat attachments excepted); and `/proc`, `/sys`, `/dev` and `/run`. These rules apply inside open projects and the Second Brain too, so opening a broad folder such as the home folder doesn't release `~/.ssh` or a project's `.env`. A folder the user opened inside one of these places, such as a skill folder or a Second Brain kept in Raticode's data folder, is not protected as a whole; secret-looking names inside it still are. The path must appear as a whole path in the user's message: asking for `~/.ssh/id_ed25519.pub` doesn't name `~/.ssh/id_ed25519`. The `~/` form counts. It drops symlinks and tells the user about every file it refused, and why. The reply stores `files` and `reply_to`, and the desktop window lists the files under the reply and opens them in the editor. When the phone that sent the request reads `rem.home`, the desktop takes a scoped snapshot of each file and sends a `file.offer` on that phone's channel, once per file. A file outside the open folders is read from its own folder, still without following symlinks; tapped links in Rem's chat (below) reach the same files; links in task threads and shared threads keep the open-folder rule. The reply then lists `files: [{file_id, name, size}]`. Paths never leave the desktop. Replies to requests sent from the desktop or another phone are not offered. A finished task's update (`kind: "task_update"`) is offered the same way when it carries `files` and `reply_to`: Rem sets `reply_to` to the chat request that asked for the file, so the phone that sent "Send me a video" receives it once the task finishes. Phones need no change; they already show `files` under any Rem message.
- **Images.** `overview` and `rem.home` report `media: true`. The `media.image` read fetches `params.url` through the link-preview fetcher, which pins one public address and sends no cookies. It answers with at most 768 KiB of JPEG, PNG, GIF or WebP data, with the type taken from the file's own bytes. The fetch runs outside the device lock.

The schema adds `media.image` to the `desktop.read` and `desktop.result` operation lists. It matches the mobile repository's `protocol/v2`. Install this desktop build before the 0.7.1 phone build.

## Tapping file links on the phone, October 31, 2026

On the phone, tapping a web link (`http:` or `https:`) opens the phone's browser. Tapping a link to a file on the desktop sends one `files.link` desktop action, and the desktop answers it without asking Rem or any other model. The phone sends the request only after the desktop advertises `file_links: true` in `overview` and `rem.home`. Otherwise it shows a message asking the user to update Raticode on the computer. Like every desktop action, it needs **Use Raticode from this phone**.

- **Request.** `desktop.action` with `op: "files.link"` and these params:
  - `source`: `"rem"` for Rem's chat (`rem.home`), `"rem_thread"` for a Rem task thread (`rem.thread`), or `"thread"` for a shared desktop thread (`thread.history.snapshot`).
  - `message_id`: the ID of the message the link is in, as the phone received it. For a shared thread this is the history fragment's `id`; its `source_id` works too.
  - `thread_id`: required for `rem_thread` and `thread`. Leave it out for `rem`.
  - `href`: the link exactly as the phone's CommonMark parser returns it (`Link.destination`), at most 2048 characters. Examples: `/home/me/notes/plan.html`, `/home/me/My%20Project/a.py`, `src/app.py:12`, `file:///home/me/plan.html`.
- **Checks on the desktop.** The link must appear in that message's text or, for Rem's chat, its Details section (the phone shows both as Markdown), and the message must be from Rem or the assistant. A link the user typed into their own message is refused. The desktop removes `<…>`, a `?query` or `#fragment`, and a trailing `:line` or `:line:column`, and it decodes `%20`-style escapes. `file:` URLs become paths. A relative link resolves against the shared thread's project folder, or the Rem task's project folder for `rem_thread`; in Rem's chat it must be a full path. The file must then pass the same scoped snapshot used for every phone transfer: a regular file of at most 10 MiB, no symlinks or `..`, inside an open desktop project or the Second Brain folder (for `rem_thread`), or inside the shared thread's project folders (for `thread`). Since November 2, 2026 a link in Rem's chat (`rem`) reaches the same files as Rem's reply files: one outside the open folders is read from its own folder, still without following symlinks. A tapped link never sends a file Rem would only send when the user names its path (credential stores, secret-looking names, Raticode's own data), even inside those folders; the refusal tells the user to ask Rem for it by its full path. The phone never gains access to anything a Rem reply couldn't already send it.
- **Delivery.** The desktop sends a `file.offer` and then answers `desktop.result` with `{file_id, name, size, thread_id}`. `thread_id` is the channel to request the file on: the phone's `files_thread` for `rem` and `rem_thread`, or the shared thread itself for `thread`. The tap is the user's request, so the phone may send `file.request` right away. Tapping the same link again replaces the earlier offer, so repeated taps don't fill the 50 MiB quota.
- **Refusals.** `desktop.result` with `ok: false` and a sentence in `detail`: `not_found` when the message, the link in it or the file is gone; `unauthorized` when the file is outside the allowed folders, may hold credentials, is a symlink or isn't a regular file; `invalid` for missing or malformed params or a file over 10 MiB.

The schema adds `files.link` to the `desktop.action` and `desktop.result` operation lists. The mobile repository's `protocol/v2` copy and `SHA256SUMS` must match byte for byte. An older desktop rejects the unknown operation, which is why the phone waits for `file_links: true`. Install this desktop build before the phone build that sends `files.link`.

## Workflows on the phone, October 31, 2026

The phone can list workflows, show one workflow's graph, status and run history, and send **Run**, **Stop** and **Resume**. It can't edit a workflow or supply run inputs. This follows the phone's proposal in its `docs/mobile-desktop-v2.md`, with one addition: `workflows.run` must send the `revision` the phone was shown. Like every desktop operation, these need **Use Raticode from this phone**. `overview` reports `workflows: true`, and the phone sends these ops only after seeing it, because an older desktop rejects them. The code is in `src/gofer/devices/workflows.py`.

- **Scope.** The phone sees only Rattish workflows registered in a desktop project its catalog names (an open, shared project), the same scope as swarms. Their `project_root` must match the project's folder exactly, so workflows in a worktree of an open project appear only when that worktree is open itself. Legacy TOML workflows aren't shown. Any other workflow ID is refused with `not_found`.
- **`workflows.list`**, params `{}`. Answers `{workflows, earlier}`: at most 100 entries, newest activity first. Each entry has `workflow_id`, `name`, `description` (node and route counts), `project_name`, `status`, `updated_at` (UTC ISO time of the last source change) and `latest_run` (a run summary or `null`). Only the newest run's artifact is read per workflow.
- **`workflows.read`**, params `{workflow_id, run_id?}`. Answers the list fields plus:
  - `revision`: the saved source's fingerprint, to send back with `workflows.run`.
  - `nodes: [{node_id, label, kind}]` (at most 200) and `edges: [{from, to, label}]` (at most 400). Edges are the compiled routes, labeled `""`, `when` or `otherwise`, plus `needs` edges where a node waits on another without a route from it. A workflow that no longer compiles shows the graph its shown run executed.
  - `runs`: the newest 20 run summaries, and `earlier_runs`.
  - `run`: the detail of `run_id`, or of the newest run, or `null`. It adds `error` and `nodes: [{node_id, status, started_at, finished_at, detail}]` for every graph node.
  - `preview: {blocking, destructive, warnings}`: the lists the desktop's run preview shows before Run. The phone shows `destructive` and `warnings` in its confirmation before sending `workflows.run`.
  - `controls: {run, stop, resume}`, each `{allowed, reason}`. Run is refused for a workflow with errors, blocking preflight problems, no nodes, or a required input without a default. Stop is allowed while a run is going. Resume describes the shown `run` (the one the phone's Resume button names): it is allowed when the desktop can resume that run, with `rerun_nodes` listing the steps a resume runs again; otherwise `reason` is the desktop's sentence, such as "This run finished successfully, so there is nothing to resume." With no run it says "There is no run to resume."
- **Run summary.** `{run_id, status, started_at, finished_at, trigger, summary, duration_seconds}`. Run and workflow `status` is `idle` (never run), `running`, `waiting` (blocked on an approval), `succeeded`, `failed`, `stopped`, `interrupted` (the runner went away before the run finished) or `invalid` (workflow only). Node `status` adds `pending` (the run is still going), `skipped` (it finished without reaching the node) and `waiting`; `failed` with detail "Failed, allowed to continue" is a failure the workflow allows. `detail` and `error` are short lines with the project and data folders replaced by names. No source, inputs, outputs or provider settings are sent.
- **`workflows.run`**, params `{workflow_id, expected_revision}`. The desktop compiles the saved source, checks that its fingerprint equals `expected_revision` (otherwise `conflict`, "This workflow changed on your computer. Review it again before running."), refuses a required input without a default (`invalid`), then calls the same background start as the desktop's Run button, which checks the revision again, applies the 32-active-run limit and runs preflight. Approval gates still stop the run for a decision through `approval.request`/`approval.resolve`. The request ID is remembered, so a resent request starts nothing and answers with the run it started.
- **`workflows.stop`**, params `{workflow_id, run_id}`, calls the desktop's per-run stop. **`workflows.resume`**, params `{workflow_id, run_id}`, calls the desktop's resume in the background, as the desktop's Resume button does. It resumes the run as a new run with the rules in `rattish/spec/README.md` ("Resuming a run") and answers that new run's `run_id` with "Resumed on your computer as a new run." A refused resume answers `invalid` with the desktop's sentence. The request ID is remembered like Run's. Run summaries and the run detail add `resumed_from`, the earlier run's ID or `""`, and a reused node's `detail` is "Reused from the earlier run".
- **Answers.** Actions answer `{workflow_id, run_id, status, message}`: `running` or `failed` with the reason after a start, `stopping` after a stop request, or the run's current status with the desktop's message when there was nothing to stop. Refusals use `unauthorized`, `unavailable`, `invalid`, `conflict` and `not_found` with a sentence in `detail`.
- **Waiting.** Phone requests are answered on the device loop. A run start waits at most 5 seconds for the runner's start acknowledgement, which comes before any node runs. A slower start answers `queued` with "Your computer is still starting this run. It will appear in the run list." and keeps going.

The schema adds `workflows.list` and `workflows.read` to the `desktop.read` list, `workflows.run`, `workflows.stop` and `workflows.resume` to the `desktop.action` list, and all five to `desktop.result`, with fixtures `desktop.read.workflows-read.json`, `desktop.action.workflows-run.json` and `desktop.action.workflows-stop.json`. The mobile repository's `protocol/v2` copy and `SHA256SUMS` must match byte for byte. Install this desktop build before the phone build that sends these operations.

## Finished one-time tasks, November 1, 2026

A one-time Rem task (`schedule.kind` is `once`) leaves the phone's task list once its run is finished, and the desktop removes it completely 30 days later. Links to the task and its work thread stay in Rem's conversation. Recurring tasks (`daily`, `weekly`, `interval`, `cron`) are always listed and never removed this way. The code is in `src/gofer/ui/rem_home_store.py` (`retention`, `cleanup`) and `src/gofer/devices/desktop_control.py`. Both `overview` and `rem.home` report `task_retention: true`; with an older desktop the phone sees every task and none of the fields below.

- **Finished.** A one-time task is finished when nothing is scheduled (`next_occurrence_at` is empty), it has no active run, and its newest run `succeeded`, was `cancelled`, or is a `blocked`, `failed` or `outcome_unknown` run the user dismissed. A run that still needs the user keeps the task listed. Running it again, or a follow-up from the conversation, lists it again until that run finishes.
- **`rem.home` `tasks`.** Only listed tasks, at most 100, sorted by `ran_at`, newest first. Ties put the newer task first.
- **Task fields.** Every task in `rem.home` and `rem.task` adds `ran_at` (UTC: the latest of its active and newest runs' start and finish times, or the task's creation time if it never ran), `listed` (`false` for a finished one-time task), `finished_at` (the newest run's finish, or `""`) and `cleanup_at` (when the desktop removes the task, or `""` when it never will).
- **`rem.task`.** Still answers for a finished one-time task until it is removed, then answers `not_found`.
- **`rem.thread`.** A finished task's work thread stays readable until the task is removed, then answers `not_found`.
- **Conversation links.** `rem.home` messages keep their `work` object (`task_id`, `run_id`, `thread_id`, `title`, `type`, `state`) for good. `work` adds `task_available` and `thread_available`, which say whether `rem.task` and `rem.thread` can still open them. A phone should open a work card's task with `rem.task` by `task_id` rather than looking it up in `rem.home` `tasks`, because a finished one-time task isn't there.
- **Removal.** 30 days after the newest run finished, the desktop deletes the task, its saved revisions, its runs, their work threads and transcripts, and the threads' saved provider sessions, job logs and control records. It checks about once an hour. It never removes a task that is recurring, scheduled, running, waiting for delivery of its result, or has a run that still needs the user. A deleted one-time task follows the same 30-day rule. Rem's conversation messages, project files, worktree branches, reports and Second Brain notes stay.

No protocol schema changes: these are fields inside the `desktop.result` body, which older phones ignore.

## Rich results in Rem's chat, November 1, 2026

Rem's chat shows the same rich parts on both apps: result cards for finished tasks, Plan · Work · Check · Report progress, an expandable Details section, up to three suggested replies, Copy and Ask about this, what Rem is doing while it replies, and the reply as it is written. The phone's rules (`RemRich.kt`, `CodeHighlight.kt`, `RemChartSpec.kt`) mirror `remRich.js`, `highlight.js` and `remChart.js`.

- **`rem.home` messages** add optional `details` (at most 6,000 characters), `suggestions` (at most 3), `meta` and `result`. A result artifact is sent as `{name, title, kind, size, href}` only when its path appears in the message body, so `href` is exactly what `files.link` accepts and the phone never learns another path. The card's Open goes through `files.link` like tapping the link.
- **Runs** add `phase_label`, `waiting_reason` and `checks: {passed, failed, total}`.
- **While Rem replies**, `rem.home` has `turn_label` and `draft_reply`; both are empty otherwise.
- **Previews.** The `media.preview` read returns `{url, kind, title, description, site_name, image}` from the same link-preview fetcher and cache as the desktop's cards. A thumbnail larger than about 280 KB is left out. `overview` and `rem.home` report `rich_results: true`, and the phone sends `media.preview` only after seeing it.

The schema adds `media.preview` to the `desktop.read` and `desktop.result` operation lists, with the fixture `desktop.read.media-preview.json`; the manifest matches the mobile repository's `protocol/v2`. Install this desktop build before the matching phone build.

**Action chips and reply deltas (later the same day).** `rem.home` messages carry `kind: "task_update"` for task updates, and runs carry `review_retryable`. The phone shows Open report, Retry review and Run again under the newest finished-task update with the same rules as the desktop (`RemRich.resultActions`). Run again sends `rem.task.run`; Retry review sends the new `rem.run.retry_review {run_id}`, which calls the same `retry_review` as the desktop and refuses runs without an interrupted review. While Rem replies, the phone reads `rem.draft {since}` about every 0.7 s and gets `{replying, turn_label, start, text, length, reset}`, only the text added since `since` (all of it, with `reset`, when the draft started over). These are reads rather than pushed events on purpose: each desktop-to-phone event is a durable row in the desktop's per-phone outbox (at most 10,000) and a received-ID record in the phone's encrypted journal, so pushing every fragment would fill both with throwaway text. `overview` and `rem.home` report `review_retry: true` and `draft_deltas: true`; the phone sends neither op without them. The schema adds `rem.draft` to the `desktop.read` and `desktop.result` lists and `rem.run.retry_review` to `desktop.action` and `desktop.result`, with fixtures `desktop.read.rem-draft.json` and `desktop.action.rem-retry-review.json`.

## Work threads on the phone, November 1, 2026

`rem.thread` used to send the newest 120 transcript records as separate messages, each body cut at 4,000 characters. Worker transcripts are about 98% `thought` records (thinking, tool start, update and result), so the phone showed rows of "Bash" and "Tool result" and lost the instruction and the final report. The code is `_thread_entries` and `_thought_steps` in `src/gofer/devices/desktop_control.py`.

- **Messages.** User, final and error messages keep `{id, role, body, kind}`. Bodies now go up to 16,000 characters. `memory` and `continuation-context` records are left out and don't split a run of thoughts, as in the desktop's `buildChatItems`.
- **Thought groups.** Each run of consecutive `thought` records becomes one entry: `{id, role: "assistant", kind: "thoughts", body, count, steps}`. `id` is the first record's ID. `body` reads "Worked through N steps." for older phones. `count` is the number of steps in the run, and `steps` holds the newest 60.
- **Steps.** Records sharing a trace ID merge into one step, as `buildThoughtTrace` does, and "tokens used" summaries are dropped. Each step is `{kind: "tool" | "summary", title, detail, body, command, status}`. `command` is sent, at most 200 characters, only when the step has no description. Tool inputs and outputs stay on the desktop.
- **Window.** The newest 120 entries are sent, within the 600,000-byte budget, and `earlier` counts the entries left out. On this machine's largest Rem threads, 1,279 to 2,548 records fold into 18 to 67 entries, so nothing is left out.

No protocol schema change: these are fields inside the `desktop.result` body. An older phone shows each group as one message.

## Pictures and videos from Rem, November 1, 2026

Pictures and videos Rem sends now show inline in Rem's chat on both apps, and open large when tapped or clicked. Nothing changed on the wire: they are the same reply `files` as before, checked by `reply_files` and, on the phone, offered by `file.offer` only to the phone whose request the reply answers.

- **Desktop.** Picture and video files under a reply preview through the window's `raticode-media://` protocol (`textFiles.openPreview`), the one the editor's media tabs use. A click opens a full-window viewer or a player with controls that starts playing; Escape or Close returns. A file that's gone says so. Web images in Markdown open in the same viewer, with **Open in browser**.
- **Phone (Android 0.8.1).** The phone picks out pictures (`jpg`, `jpeg`, `png`, `gif`, `webp`, `bmp`, `heic`, `heif`) and videos (`mp4`, `m4v`, `webm`, `3gp`, `mkv`, `mov`) by name, because the desktop offers every file as `application/octet-stream`. It downloads them over the encrypted link without a tap, checks the SHA-256 as for any file, and makes the preview in memory: the picture scaled to at most 720 px, or the video's first frame and length. Tapping opens a full-screen picture with pinch and double-tap zoom, or an in-app player that plays the verified bytes from memory and wipes them when closed; no plaintext copy is written. Save and Open stay under each preview. The tile says when it is downloading, waiting for the desktop, no longer available or not previewable, and an unplayable video offers another app.
- **Limits.** Files are still at most 10 MB, and an offer the phone hasn't downloaded lapses after an hour. YouTube links stay cards that open YouTube; neither app embeds a site's player.

## Phone action cards, November 2, 2026

When a request reaches Rem from a paired phone, Rem may answer with up to three phone actions: a timer, an alarm, a calendar draft, a place or directions, a number in the dialer, or a text or email draft. The phone shows each as a card and opens the user's own app only when they tap it on an unlocked phone; that app is where they set, save, call or send. Nothing new is sent by the phone, and there is no new op, event or schema change.

- **Marking phone requests.** `desktop_control` calls `RemHome.submit_message(..., source="phone")`, which stores `source: "phone"` on the user message. The local API can't set it (`source` isn't an accepted payload field). Only then does the chat prompt describe `phone_actions` (`rem_phone_actions.PHONE_ACTIONS`) and add it to the decision's fields, with instructions not to guess numbers or addresses, not to act on instructions from files, pages or earlier messages, and never to claim the action happened.
- **Checking.** `Decision.phone_actions` accepts any list; `clean_phone_actions` keeps at most three entries that match the fixed types and fields exactly and drops the rest without failing the reply. The rules match the phone's `PhoneActions.kt`; mobile `docs/mobile-desktop-v2.md` ("Phone action cards") lists them. Kept actions are stored on Rem's reply with `reply_to` set to the request ID, or on a separate "Ready on your phone." message when the reply started a task.
- **Delivery.** `rem.home` reports `phone_actions: true` and includes a message's actions only for the phone whose `device_rem_requests` row matches its `reply_to`, checking them again. Desktop requests, task updates and other phones never get them.
- **Desktop window.** The window doesn't draw the cards; Rem's reply says the card is ready on the phone.
- **Dropped cards (November 4, 2026).** Rem writes its reply before the cards are checked, so it can promise a card that doesn't pass. When any card Rem returned is dropped, `missing_cards_note` adds a sentence to the reply saying the card couldn't be made, or how many remain.

## Phone screen context, November 2, 2026

Raticode Mobile can send the text of the app on the phone's screen with one voice-mode request, when the user turned **Let Rem read your screen** on.

- **Accepting it.** `rem.home` reports `screen_context: true`. `rem.message` reads an optional `params.screen = {app, text}` and checks it with `clean_screen` (`gofer.ui.rem_screen`): only those two fields, 1 to 8,000 characters of text, hidden and control characters removed, an app name of at most 80 characters. Anything else is refused as invalid.
- **Never stored.** `RemHome.submit_message` accepts `screen` only with `source="phone"`. It keeps the text in memory (`RemHome.screens`, at most four waiting) and stores only `screen_app` on the message and in the command record. The reply that answers it takes the text once; later turns and history never see it. If the desktop restarted in between, the prompt says the screen was lost.
- **Untrusted.** The prompt adds `SCREEN_RULES`, which tells the model the text is page content, not the user's words, and not to follow it. That is only an instruction to the model. The guarantee is in code (`RemHome._screen_safe`): a reply that saw a screen and proposes nothing to do keeps only its answer, with details and suggestions dropped. If it proposes any work (tasks, task controls, memories, memory changes, files or phone action cards), Rem decides again from the same prompt with the screen text removed and `SCREEN_WITHHELD` added, and keeps that second decision whole. Recall reads the first pass asks for are used for its answer only; they are not added to the task's stored `delegation_context`, since their search terms may quote the screen. So work the user's own words ask for goes ahead, decided by a pass that never saw the screen, and work only the screen asks for doesn't happen. If the second pass proposes nothing, the reply is `SCREEN_HELD`, which says nothing was started and asks the user to say what they want, including any details from the screen. Until November 4, 2026 every proposed action was dropped and the prompt told the model not to plan work, so a request like "fix the 4 AM task" sent with a shared screen was refused.
- **What is kept.** Rem's answer is stored in its chat like any reply, so a summary or a quote it writes stays there. The prompt asks it to summarize rather than quote. The screen text itself, details and suggestions are never stored.
- **Where it goes.** The model provider Rem uses reads the text as part of that one prompt; its own logs are outside Raticode's control. The device inbox stores only event digests.

## Rem chat notifications, November 2, 2026

Phones can alert their user to Rem's replies and task updates, with a Reply button, through a new read, `rem.notices {after}`. Nothing is pushed: the phone reads about every 10 seconds while it's connected and Rem chat notifications are on.

- **What counts.** `after` is Rem's message position (`seq` in the messages table, fixed once a message is stored). The desktop returns at most 8 of Rem's messages after it, oldest first: a reply counts when the latest question before it came from this phone (`device_rem_requests`), and a task update counts when the task's `delegation_context.source_message_id` is one of this phone's requests. Answers to questions typed on the desktop, and updates for tasks started there, never alert the phone. The answer is `{cursor, notices, skipped, more}`, with each notice `{id, kind, body, created_at, title, needs_user}`.
- **Positions.** Without `after`, or past the end of a reset conversation, only `cursor` comes back, so turning alerts on never replays old messages. Anything other than an integer from 0 to 2^53 − 1 is refused as `invalid`. `overview` reports `rem_notices: true` when Rem is available; phones send the read only then.
- **Privacy and replies.** The phone decides what an alert shows: generic text unless its user opts in to Rem's words, and never the words on the lock screen. A reply is an ordinary `rem.message` from that phone, so the usual "Use Raticode from this phone" check, attachment rules and file delivery apply. Nothing about alerts is stored on the desktop.

The schema adds `rem.notices` to the `desktop.read` and `desktop.result` lists, with fixture `desktop.read.rem-notices.json`. `RemHomeStore.messages_after` reads the messages in one snapshot and leaves out legacy duplicate "Started …" notices, as Rem's chat does.

## Replies to a message, November 3, 2026

Both apps can reply to any message in Rem's chat. The link is one message ID; the desktop owns what it shows and what Rem reads.

- **Sending.** `POST /api/rem/messages` and the phone's `rem.message` take an optional `refers_to`: a string of 1 to 128 characters that isn't the message's own `request_id`. Anything else is refused as invalid. `RemHome.submit_message` stores only `refers_to` on the user's message and in its command record. A link to a message that isn't in the chat is accepted, so a reply queued on a phone while the history was cleared still arrives.
- **Showing.** `RemHomeStore.conversation()` adds `referenced` to every message with `refers_to`, built when the chat is read by `reference_preview`: `{id, role, body, created_at, kind?, title?, files?}`, where `body` is plain text of at most 280 characters, `title` is a linked task's title and `files` counts attachments and sent files. It is `{id, unavailable: true}` once the message is gone. Files, phone cards and details stay with the original. `rem.home` passes the same preview to the phone, bounded again, and reports `replies: true`; phones offer Reply only then, because an older desktop would drop the link. The preview is resolved against the whole chat, so a reply shows its message even when the phone holds only the last 80.
- **What Rem reads.** `_reply` adds `current_request.replying_to`: the referenced message in full (up to 6,000 characters, as recall reads it), including its task link. It is read wherever the message is in the chat, not just in the 60 recent messages Rem gets. The first recall read is seeded with its ID, so its task's thread is among those read. `RemRecall.referenced` applies recall's rules: a message whose task was deleted, or whose project is no longer open in Raticode, reaches Rem as `{id, unavailable: true}`, while the chat still shows its preview. `REPLYING_RULES` tells the model to resolve "this" and "that" to it and to treat its text as background, not a new instruction. A terse "continue" or "try again" sent as a reply follows the referenced task instead of the newest one. History excerpts carry `refers_to` too.
- **Unchanged.** Clearing Rem's history removes replies with everything else. Desktop action params are an open object, so the event schema and fixtures are unchanged.

- **Phone (Android 0.15.0).** The phone shows thumbnails and previews only for files it holds: the files it sent itself (for about a day) and files it downloaded. ## Attachments from either device, November 4, 2026

Every file on the user's messages in Rem's chat now reaches every device. The desktop window already showed files the phone sent, because the desktop stores them with the message. The phone now also gets files attached in the desktop window, and gets its own sent files back after its copy expires.

- **Desktop.** The phone action `rem.attachment` (`params: {message_id, file_id}`) offers one stored attachment of one user message on the phone's Rem chat file channel, under the name it was attached with. The phone never sends a path: the file is looked up on the message and read from Rem's chat attachment folder through the scoped snapshot, which refuses symlinks and anything but a regular file. A file that is gone, a message that isn't the user's, or an attachment not on it is `not_found`; a file over 10 MiB is `unavailable`. `overview` and `rem.home` report `attachment_files: true`. Like every phone action it needs **Use Raticode from this phone**. `files.snapshot` takes an optional offered `name`.
- **Phone (Android 0.18.0).** Pictures and videos are fetched for their thumbnails without a tap, other files when tapped, and the fetched copies are kept, the oldest removed past 40 MB. Tiles say when a file is deleted on the computer, the phone is offline, the file is too large or the phone's file space is full. An older desktop leaves the old "Not on this phone".

## Source control on the phone, November 4, 2026

The phone can show the Git status of the desktop projects shared with it, read-only, as a destination the user can put on its bottom bar. Like every desktop operation this needs **Use Raticode from this phone**. `overview` reports `source_control: true`, and the phone sends these reads only after seeing it, because an older desktop rejects them. The code is in `src/gofer/devices/source_control.py`.

- **Scope.** The phone names a project by its catalog ID and never sends a path. Only open projects the window shared with this phone appear (`DesktopControl.projects`), the same scope as workflows and swarms. Their folders are read under the device lock, Git runs outside it, and the answer is rebuilt under the lock again, dropping any project closed or moved meanwhile. Any other ID is refused with `not_found`.
- **`source_control.list`**, params `{}`. Answers `{projects, more}`: up to 24 projects, read four at a time. Each is a summary: `project_id`, `name`, `state` (`ok`, `not_repository`, `missing`, `unavailable`), `detail` (a sentence when not `ok`), `branch`, `detached`, `head`, `upstream`, `ahead`, `behind`, `changes: {total, staged, unstaged, untracked, conflicts}`, `operation` (`merge`, `rebase`, `cherry-pick`, `revert` or `""`), `fetched_at`, `last_commit: {hash, subject, author, at}` and `subfolder`.
- **`source_control.read`**, params `{project_id}`. Answers the summary plus `files: [{path, status, staged, unstaged}]` (up to 200, conflicts first, paths relative to the project), `more_files`, `commits` (the newest 15), `stashes`, `worktrees: [{name, branch, detached, current, locked, missing, changes}]` (up to 12) and `more_worktrees`.
- **Read-only.** Only `rev-parse`, `status`, `log`, `stash list` and `worktree list` run, with `core.fsmonitor=false`, `GIT_OPTIONAL_LOCKS=0`, no terminal prompts, a 10-second timeout and inherited `GIT_*` variables removed, so a read never changes a repository, its index or its refs. Nothing fetches, so `behind` is as of the last fetch, and `fetched_at` says when that was. Untracked files are counted individually, as the desktop panel does.
- **What is not sent.** Full folder paths, remote URLs and author e-mail addresses. Worktree `name` is the folder relative to the project, or its last part.

The schema adds both ops to the `desktop.read` and `desktop.result` lists, and the fixture `desktop.read.source-control-read.json`. The mobile repository's `protocol/v2` copy and `SHA256SUMS` must match byte for byte. Install this desktop build before a phone build that sends these reads.

### History, branch graph and diffs, November 4, 2026

The phone's Source control now mirrors the side pane's Changes, History and Branches views, read-only. `overview` adds `source_control_history: true`, and three reads in `source_control.py` serve it:

- **`source_control.history`**, params `{project_id, refs?, limit?}`: the panel's own `git log --topo-order --numstat --diff-merges=first-parent` over the chosen refs (null for all branches, remotes, tags and HEAD; otherwise `HEAD`, `local`, `remote`, `tag` or ref IDs from the answer, else `invalid`), 100 to 400 commits. Answers `{refs, head, commits, has_more}`; commits carry parents and ref labels so the phone draws the same graph.
- **`source_control.commit`**, params `{project_id, hash}`: one commit and its files against the first parent, with line counts. An unknown or malformed hash is `not_found`.
- **`source_control.diff`**, params `{project_id, source, path, hash?}`: a unified diff (200,000 characters at most) of a file the current status lists (`unstaged` or `staged`) or that commit changed (`commit`). Any other path is `not_found`; pathspecs are literal. Files `rem_home.sensitive_path` flags, such as `.env`, are refused with `unauthorized`.
- `source_control.read` adds local `branches` with tracking and a `remotes` count.

All of them run Git read commands only, under the same environment as the status reads, and are scoped to the phone's open projects. Writes in the desktop panel (stage, discard, commit, push, pull, publish, branch and worktree changes, merge, rebase, reset, stash, cleanup) are not offered to the phone.
