# Mobile architecture

## Production app and thread identity

`MainActivity` hosts the live-only `RaticodeApp`. `LiveScreen` separates Conversations, Chat and Desktop controls. Message history uses a lazy list and the composer remains below it with keyboard insets. The app supports Android 10+ live TLS; older devices receive an explicit OS requirement. The historical demo, simulated replies, model and notification code live in test source sets and are not shipped. Existing demo data is left untouched during upgrade and is never interpreted as live history.

`LiveClient` owns session, journal and file operations on one worker. Composables observe state and submit commands. Stable desktop thread IDs own titles, provider/model context, resource IDs, drafts and history. Thread grants come from authenticated desktop snapshots. The desktop chooses execution context and owns Rem dispatch; mobile never becomes a worker.

Desktop can grant conversation creation within an authorized project. `thread.create` carries a template thread ID and its existing project/resource/provider/model selections. Desktop checks the exact local template and copies its permissions and canonical project identity, assigns a new thread ID and durably returns `thread.snapshot`. Requests are idempotent across reconnects and desktop restarts. The creation dialog follows incoming grants while open, validates its selected template against the latest list, and gives connection or authorization guidance when none is available. Derived conversations cannot create more grants. Revoking or replacing a parent grant cancels work and revokes its children; duplicate creation requests cannot recreate a revoked thread.

## Connections and lifecycle

Pinned platform TLS 1.3 authenticates the saved desktop over a direct TCP connection on Wi-Fi or, when the user opts in, through their own Tailscale network. There is no internet relay. `DeviceConnection` creates a fresh TLS engine for every attempt and verifies the first encrypted binding echo. Desktop identity confirmation, trust revisions and ready acknowledgments remain enforced. LAN framing retains partial headers and bodies across one-second polling timeouts. A monotonic 30-second deadline bounds each incomplete frame, and the 3072-byte frame limit is checked before body allocation. There is no plaintext fallback. See [the v2 contract](mobile-desktop-v2.md).

The app connects to a saved desktop when foregrounded. `WifiRoute` tracks connected, non-VPN Wi-Fi networks through `ConnectivityManager` and binds every device socket to one of them before connecting. Without Wi-Fi, and with Tailscale off, the app does not open a socket; it reports that both devices must share a Wi-Fi network. Mobile data and VPN routes are never used unless the Tailscale switch is on. Regaining Wi-Fi retries immediately; other failures back off from two to 30 seconds. Every five seconds, coalesced sync refreshes thread grants and keeps the connection active. Updated desktop addresses and dispatcher readiness arrive inside authenticated `sync.snapshot` records, requested by `include_connection`. A null reported address keeps the working address. Endpoint validation rejects hostnames, public, multicast and wildcard addresses. Reconnection resends the same immutable pending events, so it does not imply new dispatch.

The Tailscale route is opt-in and stored in the encrypted device state as `tailscale.enabled` and an optional user-chosen `tailscale.endpoint`. `DeviceRoutes` classifies every desktop address by range: private, loopback and link-local addresses use `WifiRoute`; `100.64.0.0/10` and `fd7a:115c:a1e0::/48` use `TailscaleRoute`, and nothing else is accepted. `TailscaleRoute` watches VPN networks visible to the app and binds a socket only to one whose link routes carry the exact desktop address (longest prefix, excluded routes honored). With no such network it throws fixed guidance and opens no socket, so a missing, signed-out or split-tunnel-excluded Tailscale fails closed instead of using raw mobile data. Each connect tries the Wi-Fi address first when Wi-Fi is up, then the Tailscale address; Tailscale goes first after it was the route that worked, until a new Wi-Fi network appears. Every attempt builds a fresh pinned TLS engine with the same identity, binding and confirmation rules, so the route never changes authentication. Desktop-reported Tailscale addresses (`connection.tailnet_endpoint`, or a Tailscale-range `lan_endpoint`) are kept as `peer.tailnet_endpoint` and never replace the Wi-Fi address or the user's choice. The phone requests them with `include_tailnet_endpoint` only while the switch is on. Turning the switch off removes queued requests carrying that flag in the same journal save, and every reconnect with the switch off removes any that remain before the outbox is resent. These requests are read-only and the desktop needs only unique sequence numbers, so dropping them is safe; the next sync queues a clean request with a new sequence number. Rewriting one in place is avoided because a reused event ID with a different payload is an `event_id_conflict` on desktop. Raticode does not sign in to Tailscale, hold Tailscale credentials or change Tailscale policy; the user's Tailscale app owns the tunnel. See [Tailscale setup](live-device-setup.md#away-from-home-with-tailscale-optional).

Pending enrollment exposes the same address and recovery controls as an established peer. Pending resume failures retry the original unexpired invitation bytes. Invitations without a Wi-Fi address are rejected. A user-entered private IP/port is stored as an encrypted `lan_override` route hint. It changes only the socket address, never invitation bytes, the pinned identity or desktop grants. An authenticated snapshot with a non-null address supersedes that hint. A new invitation for a different desktop clears it.

The desktop requires the explicit networking opt-in. With it enabled and no host override, it asks the OS for the outgoing private IPv4 address without transmitting a probe packet. It binds only that interface and advertises the actual listener port. Without a private address the listener stays on loopback and desktop refuses to create phone invitations. The UI API remains on loopback. Restart desktop after a changed network address or use `RATICODE_DEVICE_HOST` for a specific interface.

LAN connection failures distinguish opening the TCP socket from authenticating TLS on an open socket. A connect timeout reports firewall and Wi-Fi reachability guidance without suggesting revocation. No pending phone can appear on desktop until the encrypted enrollment binding arrives. A local handshake test does not establish that the firewall permits an incoming phone connection. Firewall rules remain host administration; the app does not change them.

Leaving the app disconnects unless the user enabled the foreground sync service. The service has a visible notification and respects Android stop/time limits. Generic response notifications require a separate opt-in. No message bodies or filenames appear in notifications or diagnostics, with one user-chosen exception: Rem chat notifications (a second opt-in, off by default) can show Rem's reply text in the shade when the user also turns on **Show Rem's words**, which also starts off. The lock screen still shows only a generic public version, and replying from a Rem notification needs an unlocked phone. See [Rem chat notifications](mobile-desktop-v2.md#rem-chat-notifications-november-2-2026). Further opt-ins cover tasks needing the user or finishing from any source and one batched self-work proposals alert per round, always generic unless **Show Rem's words** is on; the desktop decides what counts, and quiet hours on the phone only silence alerts. See [Alerts for anything that needs you](mobile-desktop-v2.md#alerts-for-anything-that-needs-you-november-9-2026). Screenshots and recents previews are allowed at the user's request. FLAG_SECURE is not applied to chat or QR capture.

## Durable state and files

`DeviceStore` uses Android Keystore identities and authenticated encryption for trust, pending enrollment, journal and blobs. Stable outgoing IDs persist before sending. The composer clears only after journal commit and preserves a newer draft. A transport write never counts as desktop acceptance. The desktop commits acceptance and results before emitting their receipts. Lost or duplicate frames cannot manufacture delivery status. All journal writes run on the device-sync thread. Applying a received event works on a copy of the journal, so `CommitGate` holds any request queued meanwhile until that copy is saved. Each request's `sequence` then comes from the saved journal and never repeats; see [request numbers](mobile-desktop-v2.md#request-numbers-after-link-previews-november-4-2026).

History holds at most 2,000 messages. The outbox is bounded to 128 events and 8 MiB; the encrypted journal to 32 MiB. Received-event hashes and removed-file tombstones are retained up to 100,000 each. Completed-history cleanup preserves pending work, drafts, cursor and replay protection. Queue and storage failures preserve drafts and show recovery guidance. Missing or corrupt keys fail closed and never silently replace trust.

`DocumentImport` bounds untrusted document-provider reads and cancellation. `FileMetadata` supplies shared filename sanitization, digest and size limits without depending on demo storage. `FileTransfers` authenticates encrypted chunks, verifies complete size and SHA-256 before export, and limits files to 10 MiB with a 50 MiB quota. Transfers require a currently granted thread. Android document pickers grant access only to chosen files. Exported copies leave the encrypted vault. Open writes a verified plaintext copy to `cache/opened/<random>/`, shares it through a non-exported `FileProvider` with a one-intent read grant, deletes copies older than 30 minutes whenever a file is opened or the app starts, and deletes every copy on reset. Nothing opens without a tap, and app packages are refused because the app does not request install permission.

## Scope and verification

Current live behavior includes pairing, reconnect, scoped new conversations, text messages, Rem replies, file transfer, generic notifications and fleet snapshots. Phone-side project, provider, model, effort, permission and resource changes, on-device speech recognition, workflow and swarm approvals, and a swarm console are implemented. Approvals and swarm controls require a per-phone desktop opt-in that is off by default. Desktop remote conversations have their own durable transcript and can be inspected through **View conversation** in Paired devices. Workspace sync bridges the desktop renderer repository and device journal while retaining native desktop thread identity.

Local tests retain the historical simulator as test fixtures and exercise real protocol validation, journals, crypto interoperability, lifecycle and UI. The disposable integration fixture uses the real desktop `DeviceChatBridge`, `ChatJobs` and `ChatSteering` with a canned provider response. A passing emulator test does not establish physical Wi-Fi routing, paid-provider execution or independent security review. See [live setup](live-device-setup.md) and [release readiness](release-readiness.md).

## Shared desktop conversations

Desktop identity confirmation enables workspace sync for a new controller phone in the same transaction as trust confirmation. The setting becomes effective only after the authenticated ready acknowledgment. Existing sync choices survive upgrades and reconnects; desktop peers retain explicit grants. A renderer synchronizer copies existing thread metadata and text messages through the authenticated local API. The backend checks project path grants and stores each phone's mirror encrypted in the device registry. A deterministic UUID maps a native renderer thread ID to the wire ID; ChatJobs and ChatSteering use the native ID. Phone-created threads are imported into the same renderer repository. Revocation tombstones prevent polling from recreating removed authority. Provider/model updates carry an expected revision and retain project/resource context.

Mobile requests a paged thread catalog and history pages of at most 40 text fragments, capped to 45 KB of encoded payload. Long messages split at 4000 characters with deterministic IDs. The latest page loads on opening a thread and during active sync; earlier pages load on demand. Desktop history mirrors allow 10000 messages per thread, 8 MiB per thread and 64 MiB per phone. Mobile retains its existing 2000-message and 32 MiB journal limits. Provider dispatch uses at most the latest 200 shared text messages. File bytes still use the separately scoped transfer protocol.

The mobile composer exposes verified attachments, on-device dictation and cancellation. Thread settings edit provider/model, effort, project/global scope and provider permission mode using expected revisions. Desktop-supplied capability catalogs bound valid models and efforts; provider permissions use the same validators and defaults as desktop. Shared conversations preserve resources and native thread identity. Antigravity and Grok are selectable and use their desktop CLI-managed policy. Individually scoped legacy grants still retain their explicit limits.

Shared execution uses the desktop provider, Rem thread tools, Second Brain configuration and swarm services. Global turns select one of the desktop's validated open projects and restart the provider in that project under the selected desktop policy. Paths and credentials are never supplied by phone context events. Explicit Rem child-thread requests are queued by the desktop with inherited settings and durable deduplication. Routine metadata, resource or scope sync does not revoke running work; explicit revocation still does.

`thread.search.request/snapshot` search the encrypted desktop mirror with the desktop's case-insensitive NFKC substring semantics. Results include a snippet and a deterministic history fragment ID. `thread.history.request.message_id` loads the matching fragment, and mobile retains history positions when merging it. Search covers saved text messages and titles across all groups, within the existing mirror quotas. The renderer supplies desktop group classification, including its inactivity and missing-project rules. Desktop ChatJobs supplies running indicators for either origin. Optional sync fields carry group, effort, permission, running state and modification time.

File offers from shared Rem turns use wire thread IDs and may read another validated open desktop project. The selected project identity and no-symlink snapshot checks still guard each read. Grouped thought and tool trace rendering is available in the native app. Remote approvals and the swarm console arrived in 0.6.0; see below. Provider approval modes still apply on desktop; mobile does not silently approve a provider prompt.


## Removing desktop pairing

Desktop unpairing removes trust, routes, grants, shared-history mirrors and file transfers without retaining a revoked entry. Removing a revoked identity permits fresh enrollment but restores no authority. Desktop retains Rem request deduplication records, cancels pending work and checks a persistent local pairing generation in each session, preventing old TLS sessions from surviving removal and re-enrollment of the same identity. These are local lifecycle changes; the wire contract is unchanged. Mobile forgetting remains an explicit local reset, and its confirmation now distinguishes desktop Unpair from Revoke.

Desktop runs only the local network listener. The ntfy relay service was removed on October 26, 2026.


## Mobile layout and desktop turn display

LiveScreen keeps transport and session behavior in LiveClient. The presentation separates conversations, chat, conversation files and desktop settings. The composer keeps a stable accessibility label while drafts contain text; its menu holds attachment and dictation actions. Headers collapse while the keyboard is visible. Long connection status messages remain available in an explicit detail dialog. System-bar icon contrast follows the Compose theme.

Desktop now projects its existing local ChatJobs event journals into the renderer-owned conversation repository with stable IDs and a phone-origin marker. The renderer receives this projection over the authenticated loopback API; phones with sync enabled receive its bounded presentation fields inside pinned TLS. Renderer reconciliation does not grant authority or launch work. Existing durable receipt boundaries remain unchanged.

## Structured chat history

History requests now opt into `include_presentation`. Desktop projects both renderer history and phone ChatJobs into the same thought groups and supplies kind, group identity, trace fields, turn timing, attachment metadata and stable source/fragment identity. Mobile validates these bounded fields before committing a page. The journal replaces the refreshed page, including obsolete summaries, while preserving pending requests and authenticated receipt states. Presentation code (`ui/ChatHistory.kt`) mirrors desktop `buildChatItems` and `buildThoughtTrace`: it joins text fragments, groups every run of consecutive thoughts regardless of `groupId`, merges tool entries by group and trace ID, and opens a group until a Rem reply follows it. It drops the desktop's "previous process was interrupted" notice and hidden context (compaction `memory` and `continuation-context` rows, which desktop also leaves out of phone history pages), draws Rem replies as bordered cards with Copy Markdown, your messages as full-width bubbles, desktop notes as centered pills and errors as alerts, without sender labels. Turn summaries are status rows using desktop's "Running for" and "Ran for" wording. Thread Markdown uses desktop's sizes and spacing through `LocalMarkdownStyle`; Rem chat keeps its own.

Mobile snapshots attachment names, MIME types and sizes when a message is queued. Desktop saves the verified offer metadata atomically with accepted work in an encrypted attachment-history table, capped at 32 MiB per peer. Renderer synchronization repairs previously imported phone messages without overwriting desktop text edits. Attachment metadata conveys no path grant or execution authority. Removing a transfer copy does not remove its message-history label. Older messages whose offers already expired may only recover a generic attachment label. Unpairing removes the metadata table rows.

Thread catalog refreshes never select the first thread. Explicit selection, notification navigation and newly created threads retain their navigation behavior. A synchronized catalog can update the thread list without leaving it.

Thought timeline rows align markers against the first text baseline supplied by the content, so tool-button padding and font scaling determine their position. Markdown list markers use the same type style and baseline as their first block.

## Thread home and organization

Android 0.5.3 displays compact desktop thread groups and dates with a bottom composer. Home scope and model choices survive opening a conversation. New threads need no user-supplied title. LiveClient commits the first-message intent together with `thread.create`; the authenticated creation snapshot atomically replaces that intent with one durable `chat.submit`. Reconnect uses the existing stable IDs. Rejection restores the draft. An attachment-first creation carries an unsent draft into its new thread. Composables never send transport records directly.

`thread.manage` requires a current thread grant and `expected_revision`. Desktop stores pin/archive changes separately from their base metadata so renderer reconciliation can preserve concurrent desktop edits. Delete records a durable pending request and blocks new submissions to that thread. The renderer imports the latest mirrored messages, saves its configured archive, deletes the local conversation and acknowledges `workspace_remove`; only then does the thread disappear from mobile sync. A failed archive or renderer operation keeps deletion pending for retry. Existing peer trust, revocation and durable receipt rules remain authoritative.

Shared creation can select an open desktop project or Global and validated provider/model/effort/permission choices. Resource IDs still come from the desktop grant. Legacy individually scoped grants still require exact context matching. Desktop assigns the native ID and derives the title from the first accepted user message with the desktop's eight-word rule, bounded by the 160-character wire title limit. On completion it sends the current revision before the final reply, preventing an immediate organization action from using a stale revision.


## Desktop running in the background

Closing the desktop window hides it to the tray; the renderer keeps running without timer throttling, so thread sync, phone deletions and archives continue. Electron reloads a crashed main renderer up to three times an hour. If the window is destroyed some other way, such as a page-initiated close, Raticode restores a hidden window so sync continues, and the tray's Open Raticode shows it. The backend reads the provider catalog itself on a worker thread, so model choices do not depend on the window. Phone requests already run in the backend's chat jobs. History for phone-started turns, including thoughts and tools, is built from those backend jobs.

Two limits used to break long background use. Desktop recorded every phone polling request in a lifetime inbox capped at 100,000, and the phone recorded every snapshot ID under the same cap; both would fill after days of sync. Polling requests and snapshots now use bounded recent windows. The phone's 2,000-message history limit stopped incoming replies once full; history is now a cache that evicts other threads' pages, never pending work. See the [background parity extension](mobile-desktop-v2.md#background-parity-extension-october-27-2026).

`scripts/background-desktop-acceptance.mjs` checks this against a real, isolated desktop instance on a virtual display: it closes the window to the tray, waits past Chromium's five-minute background threshold, adds a desktop message the phone must receive, and requires the hidden window to finish a phone deletion.


## Using Raticode from the phone

Android 0.7.0 adds a bottom bar, so the phone works as another view of the desktop app. It now reads Rem, Threads, Orgs, Swarms and More, and a plain launch opens Rem; links from notifications, sharing and voice mode keep their own destination (`LiveNavigation` in `ui/LiveScreen.kt`). **Rem** shows the desktop's Rem conversation and tasks: message Rem, add, run, pause, resume or delete tasks, stop or dismiss runs, and read or instruct a task's work thread. **Orgs** lists organizations; inside one, the phone shows the desktop's five sections (Organization, Projects, Issues, Workers and Knowledge, since November 6, 2026). It adds tickets, moves them on the board by long-press, approves, accepts or sends back work, comments, reopens and cancels, adds notes, asks a worker to look at something, holds or releases a sandboxed worker, and pauses or starts the organization. With an older desktop it keeps the earlier task list and asks to update Raticode. **Swarms** can start a run on an idle or finished swarm. **More** holds approvals, desktop settings, usage and the connection page. The bar hides while the keyboard is open. Since November 4, 2026 the user chooses up to four bar destinations and their order (**More › Bottom bar**, stored as page names in private preferences); More always follows them and lists the rest, and the app opens to the first. **Source control** is one of the choices: a read-only Git status view of the shared desktop projects, served by the desktop's `source_control.*` reads. See [bottom bar choices and source control](mobile-desktop-v2.md#bottom-bar-choices-and-source-control-november-4-2026). **Files** (since November 6, 2026) browses the same projects read-only and opens their files on the phone (`files.list`, `files.text`, `files.open`). The phone names a project by catalog ID and a file by its project-relative path; the desktop walks folders without following links, refuses secret-looking files and offers whole files through the normal 10 MiB end-to-end file transfer. HTML and SVG previews run in a web view with JavaScript, file access and network loads off. See [file explorer](mobile-desktop-v2.md#file-explorer-november-6-2026).

All of this needs **Use Raticode from this phone** in desktop Paired devices, which is off by default. LiveClient polls only the open screen, every five seconds or every two while Rem works, and holds results in memory; nothing from these screens is written to the phone's journal except the queued request itself. Requests and actions use the journal and durable receipts like other events. Composables call LiveClient methods and never build transport records. See the [desktop control extension](mobile-desktop-v2.md#desktop-control-extension-october-27-2026) for the wire format and what stays desktop-only.

Organizations remain an experimental desktop feature; when the desktop has it turned off, the Orgs screen says so. Desktop settings changes reach the desktop window through its normal settings code, so they apply while Raticode runs, including from the tray. **More > Workflows** lists workflows from the shared desktop projects. For each one it shows the graph top to bottom, with loops drawn as dashed lines on the side, or the same steps as a list. It also shows the run history, and the node statuses of any run the user selects. **Run**, **Stop** and **Resume** use the desktop's own run service and its revision check, preview, limits, approvals and resume policy. The phone cannot edit a workflow or supply inputs. See [workflows on the phone](mobile-desktop-v2.md#workflows-on-the-phone-october-31-2026). Second Brain, the code editor and terminals are not phone screens. The browser is the phone's own; see [The browser](#the-browser).

### Global board and self-work

`live/Kanban.kt` is the phone's model of the desktop's global board and Rem's self-work; `ui/KanbanScreens.kt` shows it. Tickets, the 15-minute idle rule, scheduling, thread limits, deduplication and approvals stay on the desktop, and every change is re-checked there against its revision. The phone holds only what the desktop last said, in memory, and offers only what its rules allow. See `docs/mobile-desktop-v2.md`.

### Developer log and Organizations

The Developer log reads the desktop's `app.jsonl` through `developer.log`, a cursor-following read the desktop answers from the file the window names in `GOFER_APP_LOG`. Entries are redacted on the desktop and held only in memory on the phone. This phone's own connection events (`PhoneLog` in `live/DeveloperLog.kt`) are also memory-only and carry the app's own wording, request names and exception class names, never addresses, keys, invitations or message text. Ask Rem writes the selection to a file under the app's private `cache/handoff/` (a FileProvider path never granted to another app), attaches it through the normal Rem upload and deletes it once read; leftover files go after 30 minutes. It never sends the message.

The Organizations screens show the desktop's five sections from one `organizations.read` projection and `organizations.note` for a note's body. The phone may add tickets (Backlog or To do), move them by the desktop board's rules, review, comment, reopen, cancel, add notes, ask a worker, hold or release a sandboxed worker, and start or pause the organization (refused for full-access workers). Configuration, permissions, planning, Rem's consent requests and checks stay on the desktop, which checks every action again. See [Developer log and Organizations](mobile-desktop-v2.md#developer-log-and-the-five-section-organizations-view-november-6-2026).

## Desktop thread sections

The thread list follows desktop `organizeThreads` (`frontend/src/lib/threadActivity.js`) and its `ThreadSections` labels: Pinned, Unread, Read, Running and Archived. `ThreadActivity.organize` applies the same order: archived first, then pinned, running, unread and read. Read keeps the seven most recently read threads and moves the rest to Archived. Pinned, Unread and Running sort by update time; Read and Archived by the later of read and update time. Desktop sends `group` (it already archives missing projects and older read threads), ChatJobs supplies `running`, and the optional `unread`/`read_at` sync fields carry the renderer's saved unread state. The list classifies every thread before applying the project filter, so a filter never moves a thread between sections.

Opening a chat records the desktop update time it showed in the encrypted journal's `read_marks`. That clears Unread on the phone until desktop reports a newer update. Only the chat on screen counts, while the app is in the foreground. When the desktop's overview reports `thread_read` (it needs **Use Raticode from this phone**), the phone also sends `thread.manage` `read` for that thread, so the desktop marks it read too. Older desktops never get the action, because they reject it and close the connection. A `thread.snapshot` answering the phone's own change moves an existing mark to the new update time, so archiving or pinning a read thread can't bring back its dot. Running and Archived start collapsed as on desktop, archived rows offer Delete instead of Archive, and row menus use desktop's Pin thread, Unpin thread and Delete thread labels, plus Restore thread. Rename and Clear archive remain desktop-only.

Android 0.8.1 lays out Rem's chat like desktop RemHomeWorkspace: rat-face replies at body size, lavender user bubbles, day labels, per-message stamps worded like the desktop's (time today, day and time before; full date for TalkBack; nothing for a missing or unreadable `created_at`), a faint rule between consecutive Rem replies, task cards and the desktop's Paperclip/Send composer. Navigation uses the desktop rail icons (MessageSquare, rat face, Building2, rat swarm, Ellipsis). Rem chat files use the desktop-advertised `files_thread` channel with the normal verified transfer code, and `rem.message` names uploaded files by ID only. Files Rem sends download only on tap. A tap on the file name sends `file.request` when needed and passes the verified file to the same Open path as the Open button once it is available (hash check, `cache/opened/` copy, one-intent read grant, installer refusal, "Save instead" when no app opens it); expired, failed or cancelled files have no name action, and a tap while offline waits in the outbox until the desktop reconnects. Pictures and videos are the exception (known by name), which download by themselves so they can preview inline. Their previews are made in memory from the verified bytes; the full-screen picture is decoded at no more than 2,048 pixels, and the in-app video player reads the bytes from memory through a `MediaDataSource` and zeroes them when it closes, so showing or playing them writes no plaintext copy. Markdown images are fetched by the desktop through `media.image`, decoded with a size cap and kept in memory only, so image addresses never leave pinned TLS and the phone makes no internet requests. Details are in the protocol document's October 30 Rem chat section.

**Attach sources (0.14.0).** Rem chat's paperclip (`ui/RemAttach.kt`) opens a bottom sheet instead of going straight to Android's document picker. **Photos and videos** uses the AndroidX `PickVisualMedia` contract, which is Android's photo picker where the phone has one and `ACTION_OPEN_DOCUMENT` limited to pictures and videos otherwise; the sheet then says it opens in the file browser. **Recent files**, **Downloads** and **All files** are `ACTION_OPEN_DOCUMENT` with `EXTRA_INITIAL_URI` set to nothing, the Downloads provider's `downloads` root and the external-storage `primary` root. Android's file browser restores the caller's last place when no start is given, so Recent may open elsewhere; the sheet groups these three under "In Android's file browser" and says to use its menu. No storage or media permission is requested. **Camera** uses `TakePicture` into `cache/camera/<uuid>.jpg`, shared to the camera app through the existing non-exported FileProvider with a one-intent write grant. Because the manifest declares `CAMERA` for QR scanning, Android refuses `ACTION_IMAGE_CAPTURE` until that permission is granted, so the sheet asks for it first; a refusal, a missing camera app or an empty result leaves a note in the message box (with Settings after a permanent refusal) and attaches nothing. Backing out of any picker is silent. The photo is named "Photo <date> <time>.jpg", read through `DocumentImport` like any file and deleted once read or refused; leftovers older than 30 minutes go when the next photo is made or the app starts, and reset deletes them all. Picked files are capped to the eight-file room left, with a note for any that didn't fit, refused if they come from Raticode's own provider, and read one at a time because the client imports one file at once; Send waits until they are read. Upload, verification, chips and `rem.message` are unchanged.

**Attachments from either device (0.18.0).** Every file on the user's messages in Rem's chat is available on the phone, not only the ones it sent and still holds. The desktop keeps all of them in Rem's chat attachment folder, so the phone asks for one it lacks with the desktop action `rem.attachment` (message ID and attachment ID, never a path), only from a desktop whose `overview` or `rem.home` says `attachment_files`. The desktop offers a fresh copy on the Rem chat file channel and the phone downloads it with the usual verified transfer. `live/RemAttachments.kt` keeps the journal map from attachment ID to the download holding it (`rem_attachment_files`), picks the oldest fetched copies to remove when another would take Raticode's files past 40 MB or 90 files (leaving room for uploads and Rem's files under the 50 MiB limit), drops queued fetches before each connection, and words each state. `AttachmentTile` takes the message ID only in Rem's chat: it uses the phone's own upload while that is held, then the fetched copy; pictures and videos are fetched once per session without a tap for their thumbnails, other files when tapped, opening once they arrive; the ring shows the download. A tap made just after reconnecting, before the desktop says it supports fetching, waits for that answer instead of being lost. A file deleted on the computer says so, as do an offline phone, a file over 10 MB and a full phone. Threads are unchanged.

**Attachment tiles (0.15.0).** Attachments in Rem's chat and threads show as tiles (`ui/AttachmentTiles.kt`): a thumbnail when the phone holds the bytes (its own uploads until they fail, are cancelled or expire, and finished downloads), otherwise a file-type tile from `live/FileKinds.kt`, which uses the desktop's groups. Tapping one previews it from the verified encrypted store through `FileTransfers.read` (size and SHA-256 checked): pictures full screen, video in the in-memory player, text and code as the first 256 KB of UTF-8, other types in another app through the existing short-lived opened copy. The tiles get the phone's files through a composition local built where the client is created. Until 0.18.0 a file attached in the desktop window was never on the phone, so its tile said so instead of asking the desktop for it; see above.

**Upload speed, progress and waiting messages (0.16.0).** Measured cause of slow uploads: for every 16 KiB chunk, `FileTransfers.nextUpload` decrypted the whole stored file through the Android Keystore and hashed it again, and each acknowledgment cost two full saves of the encrypted journal. Work per upload grew with the square of the file's size: on the user's phone a 7.1 MB upload ran at about 1.7 s per chunk (desktop records, November 3, 2026). Uploads also went one at a time in the order offered, and removing a chip didn't cancel its upload, so a 694 KB picture waited at 0 bytes behind a 7 MB file the user had given up on. Now the upload being sent is decrypted and checked once and kept in memory (zeroed when it ends, on reset and when the sync thread stops); `UploadQueue` sends the upload with the fewest bytes left first and keeps up to four chunks unacknowledged; and the next chunks are queued inside the same journal save as the acknowledgment that frees their room (`LiveClient.advance`). On the emulator a 582 KB picture attached during a 7 MB upload arrived in 1.6 s instead of 220 s. An upload whose stored copy no longer reads or matches, or whose offer or chunk the desktop refuses, is marked failed rather than left waiting. Removing a chip, in Rem's chat or a thread, calls `cancelFile`, which marks the upload cancelled on the phone in the same save that queues `file.cancel`. A cancelled or failed transfer ignores late statuses, and the desktop's `cancelled` status (which reports 0 bytes received) no longer fails validation against the phone's offset.

The tile's ring fills with the share of the file the desktop has confirmed in `file.status` (`UploadQueue.progress`), animated between confirmations, with "Uploading · N%", "Not connected · N%" or "Didn't upload" on the tile. Send no longer waits for uploads in Rem's chat: `sendRemMessage(hold = true)` stores the message under `rem_held` in the encrypted journal (words, `rem.message` params, file IDs, Rem's file channel and the reply target). `HeldSends.decide` runs with every journal change; once every file is available, the message is queued as an ordinary `rem.message` in the same save that removes `rem_held`, so it goes once. A file that fails, is cancelled or expires returns the message as unsent, naming the file, with Edit and without Try again. The chat shows the waiting message with its files' rings; **Edit** takes it back into the message box with its words, reply and chips, and the uploads carry on. One message waits at a time, and Send and follow-up chips are off meanwhile. Held files count as referenced, so expiry and Remove keep them. Uploads still need the phone connected: closing the app without background sync pauses them and the waiting message until it reconnects.

Upload offers now expire ten minutes short of a day (`FileTransfers.UPLOAD_SECONDS`). The desktop refuses an offer ending more than a day after its own clock (`file_offer_bounds`), so a full day failed whenever the phone's clock ran even a fraction of a second ahead.

Message links are classified by `ChatLinks` and rendered by `ChatMarkdown` (Rem chat also passes the desktop's `file_mentions`, so full paths with spaces and code that is exactly a path or address link) with the message they came from. Composables hand taps to one `ChatLinkHandler`: web addresses go to the default browser through a browser-selector intent, and file links call `LiveClient.fetchLink`, which sends the desktop action `files.link` only to a desktop that advertises `file_links`. The phone sends the link text and message ID, never a path; the desktop finds the link in a Rem- or agent-written message, resolves it and applies the same scoped, no-symlink snapshot as every other phone file. The downloaded file uses the normal verified transfer. Because the tap already asked for it, `rememberChatLinks` passes it to the existing Open path as soon as it is available while the link sheet is open: size and SHA-256 are checked again, a copy goes to `cache/opened/`, and only the chosen viewer gets a one-intent read grant. Text types without their own viewer retry as `text/plain`. App packages are still refused, and a file no app can open gets the "Save instead" dialog. Closing the sheet before the download finishes cancels the open, not the download. See the protocol document's October 31 section.

Rem's task list is ordered and filtered on the phone by `RemTaskList`: running tasks first, then the desktop's `ran_at`, newest first, without one-time tasks whose run finished and needs nothing from the user. The desktop decides with `listed` when it sends it; for an older desktop the phone applies the same rule itself. Chat work cards open `rem.task` and `rem.thread` by ID instead of looking the task up in the list, and follow the desktop's `task_available` and `thread_available`. The work-thread screen (`RemThreadView`, laid out by `RemThreadRows`) gets each run of worker thoughts from the desktop as one group and shows it folded under **Show thoughts**, like the desktop's thread pane. Since November 6, 2026 each instruction says who wrote it: **Rem** for Rem's prompt to the worker, in Rem's sage colours, and **You** for a message the user wrote in the thread, from the desktop's `sender` field. An older desktop sends no `sender`, and the phone then shows no author. Retention and the 30-day cleanup run only on the desktop; the phone deletes nothing. See the protocol document's November 1 section.

Rem's rich messages are drawn from optional `rem.home` fields (`details`, `suggestions`, `meta`, `result`, and `phase_label`, `waiting_reason` and `checks` on runs, plus `turn_label` and `draft_reply` while Rem replies). `RemRich` holds the rules shared with the desktop's `remRich.js`; `CodeHighlight` and `RemChartSpec` match its `highlight.js` and `remChart.js`. Markdown uses the commonmark GFM table, strikethrough and task-list extensions. A message's `body` stays complete, including its report links, so the result card only hides links it shows as buttons, and its Open button goes through the same `files.link` request as tapping the link. Source previews use the `media.preview` read, sent only after the desktop reports `rich_results`, because an older desktop would reject the unknown read and close the session. See the protocol document's rich results section.

## Voice assistant

Android 0.9.0 adds voice mode for Android 12 and newer, which have on-device speech recognition. Every voice component is switched off below Android 12 through the `voice_mode` boolean resource (`values-v31`).

**Entry points.** `RemVoiceInteractionService` makes Raticode selectable as the phone's digital assistant; Android's assistant role can't be requested by an app, so the user picks it in Settings. While Raticode holds the role, Android keeps the service bound and shows `RemVoiceSession` for the assist gesture, the assist key and, where the phone maps it to the assistant, a power-button hold. The session window is drawn above other apps and above the lock screen. The service turns off the screen-content and screenshot hand-off (`setDisabledShowContext`), so Rem never receives what was on screen. `VoiceActivity` shows the same panel for the Quick Settings tile (`RemVoiceTile`), the launcher shortcut (`xml-v31/shortcuts.xml`), the sync notification button and **Try voice mode**. An exported `ACTION_ASSIST` alias covers phones where Android skips voice interaction services; it only opens the panel and ignores extras. The required `RemRecognitionService` hands other apps' requests to the on-device recognizer and refuses when there is none. On the test emulator the system's default speech recognizer stayed Google's after Raticode became the assistant.

**One turn.** `VoiceController` (one per process, `VoiceRuntime`) holds the turn in memory: listening, review, unlock, sending, waiting and the reply. `OnDeviceDictation` listens only with `createOnDeviceSpeechRecognizer` and shows partial words; nothing falls back to a recognizer that may upload audio. The microphone runs only while a voice surface is on screen and stops as soon as the last one leaves; there is no microphone foreground service and no wake word. Sending reuses `LiveClient.sendRemMessage` (`desktop.action` `rem.message`), so the message is journaled with a stable request ID and the desktop decides what happens. `VoiceLogic.reply` finds Rem's answer as the first Rem message after the user's own message ID once `turn_state` is no longer `replying`; a refusal for that request (`remRefusal`) ends the turn with the desktop's reason. A message sent while Rem is still replying isn't refused by a current desktop: it holds the message, lists it in `rem.home` with `state: "waiting"` (shown as "Sends when Rem finishes replying"), and answers it next, so the same reply lookup finds it. Older desktops refused it with "Rem is still replying". While voice mode is open, `LiveClient.voiceStart` connects like the app coming to the screen and reads `rem.home` about once a second whatever page the app shows; `voiceStop` disconnects unless the app is on screen or background sync is on. Before the first sync snapshot since the app started, the phone doesn't know whether the desktop allows Rem from this phone, so a request waits up to 25 seconds for it and then reports that the desktop is unreachable. After a snapshot, an offline request goes into the encrypted queue as usual.

**Speech output.** `RemSpeaker` uses Android `TextToSpeech` with an offline voice in the phone's language (`isNetworkConnectionRequired` false and installed) and asks the engine not to synthesize on the network. Without such a voice, replies are shown but not read. `SpeechText` turns Markdown into short sentences, says there is code instead of reading it, replaces addresses with "a link", and stops at a sentence after about 600 characters with "The rest is on screen."

**Lock screen.** The gate uses `KeyguardManager.isDeviceLocked` (a PIN, pattern or password). While locked, listening and typing work but **Send** becomes **Unlock and send**: the overlay hands the turn to `VoiceActivity`, which shows over the lock screen and asks Android for the unlock prompt once its window has focus. Only Android's success callback, or returning to the panel on an unlocked phone after Send, releases the request. The device keys don't require an unlocked phone, so this gate is what keeps a locked phone from starting desktop work. Replies arriving while locked stay hidden and silent unless the user turns on **Show replies on the lock screen**. Voice settings are plain switches in shared preferences; nothing said or heard is stored.

**Screen context.** With the user's opt-in, the assistant service lets Android collect assist text (never screenshots) and `RemVoiceSession.onHandleAssist` reads the focused app's `AssistStructure`, skipping assist-blocked views, password and PIN fields, secure windows and anything behind the keyguard. The text stays in memory and goes only with a message the user chose to share it with (the share-screen button, off each time Rem opens), to a desktop that reports `screen_context`; the desktop uses it for that reply and stores only the app's name. Work the user's own words ask for is decided again without the screen, so the screen can't start, change, remember or send anything (`RemHome._screen_safe`). Voice mode's paperclip uses Rem chat's attach menu; the overlay hands the turn to `VoiceActivity` to pick, after an unlock. See the screen context section of `docs/mobile-desktop-v2.md`. **Talk back to me** (`VoicePrefs.speak`) can be switched in settings or from voice mode whether or not an offline voice exists; `VoiceLogic.voiceStatus` and `replyNote` say nothing about voices while it is off.

**Listening until Send.** Android's recognizer ends a session at each pause, so `VoiceController` starts the next session (`OnDeviceSpeech`, on-device only) at once until the user taps Send or the keyboard, waiting 150 ms only after a session that failed straight away. One recognizer is kept between sessions (`WarmRecognizer`) and released when listening stops, because a new one has Android restart the recognition service: on the emulator that left the microphone deaf for about 0.7 s at every pause, and reuse brings it to about 0.1–0.2 s. On Android 13 and newer each session also turns off the recognizer's masking of swear words (`EXTRA_MASK_OFFENSIVE_WORDS` false; Android writes "f***" by default and older versions have no such option) and asks for a segmented session (`EXTRA_SEGMENTED_SESSION`), so a recognizer that supports it keeps one session across pauses and reports each stretch through `onSegmentResults`. The silence hints are Int extras: Google's recognizer reads them as Int and ignored the Long values sent before. `DictationText` joins the sessions' words after any text kept from before. Send (`sendSpoken`) asks for the last session's final words and waits up to 2.5 seconds before using the partial words, then sends; with tidying on it first tidies what the pauses haven't, and words that couldn't be tidied open for review instead of being sent unseen. Nothing sends without a tap: there is no Done step and no auto-send countdown. The keyboard button (once something has been said) and pausing the microphone wait the same way for the session's last words before closing it, so neither cuts off the end of a sentence; if those words don't come within 2.5 seconds the words heard so far are kept. Tidy rounds run on their own and never stop or restart the recognizer: speech keeps being heard while a round is out, and only a change in the words counts as new speech, so a recognizer repeating the same partial during a pause doesn't postpone the pause round. Ordinary session ends (no match, speech timeout, a busy or released recognizer) continue; microphone, permission, language or service failures stop and keep the words in review with the reason (`Dictation.classify`), as do five failures in a row each under a second. After 45 seconds without words listening pauses, and tapping the microphone pauses or resumes it. Leaving voice mode mid-sentence turns the words into a review, kept in memory only for 10 minutes for the next time voice mode opens; Cancel clears them. The microphone's loudness drives the listening animation: `VoiceDots` draws a full-width dotted line that rises into dot bars with it (`DotMeter` keeps each column's rise, fall and held peak, and is unit-tested), on a thin night-indigo card with a gradient edge. The line is also the pause/resume button (`voiceMic`). Its frame loop is an infinite animation, so Compose tests stay idle and draw the current level directly, and it honours Android's animator scale of 0 by dropping the sway, glint and sweep. Controls are icons with spoken labels, and the state is announced through a live-region description (`voiceStatus`) instead of printed. The recognizer gets the longer silence hints (`EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS`), which some recognizers ignore; a word spoken in the short gap between sessions can still be missed where segmented sessions aren't supported.

**Setup offer.** `MainActivity` marks a launcher start (`ACTION_MAIN`, not a notification) and `LiveScreen` shows `VoiceSetupOffer` once the client is loaded and paired. `VoiceSetup.offerOnLaunch` offers only when Android reports the assistant role available and not held by Raticode, on Android 12+, and while **Offer setup when Raticode opens** is on (`VoicePrefs.offerSetup`). Android doesn't let apps request the assistant role or open its picker (`MANAGE_DEFAULT_APP` needs a system permission and the settings-search trampoline a Settings-only key), so **Set up** opens `ACTION_VOICE_INPUT_SETTINGS`, or `ACTION_MANAGE_DEFAULT_APPS_SETTINGS` first on Samsung, and rechecks `RoleManager.isRoleHeld` on resume. `VoiceSetup.steps` names each maker's menus and detects the Galaxy S20 family (SM-G98x, SM-G78x). A turn started through the exported `ACTION_ASSIST` alias always waits for a tap on Send, whatever **Send when I stop talking** says. More › Voice assistant (`VoicePage`) shows the same settings as the Desktop page.

**Phone action cards.** A reply to the phone's own request may carry up to three suggested actions (timer, alarm, calendar draft, map, dialer, text or email draft). `PhoneActions` accepts only those types and fields, rechecks every value, and maps each to one fixed implicit intent that shows the other app's screen: no `EXTRA_SKIP_UI`, `ACTION_DIAL` rather than `ACTION_CALL`, `ACTION_SENDTO` drafts with one recipient at most and no calendar attendees. Clock apps act on the intent itself (Google Clock starts the timer and saves the alarm as it opens, checked on an Android 16 emulator), so those buttons read **Start timer** and **Set alarm** and the card says so; the other cards only fill in drafts. Nothing opens without a tap on the card, the button stays disabled for two seconds after a tap so a double tap can't act twice, and a showing lock screen must be dismissed first. On the voice overlay the tap moves to `VoiceActivity`, which unlocks, starts the other app in its own task (the voice task is hidden from Recents) and closes voice mode. Calendar drafts carry the `vnd.android.cursor.dir/event` type that Google Calendar's insert filter matches; a map query falls back to a Google Maps web address when nothing handles `geo:`. The only new permission is the normal `SET_ALARM`, which the clock intents require. The app still lists no SMS, call, call-log, contacts, overlay, accessibility or notification-listener permission (the assistant role would grant some of them silently), and `PhoneActionsTest` fails if the manifest gains one. See mobile-desktop-v2.md, "Phone action cards".

**Ask Rem from Files and Source control.** The file viewer's selection menu, each diff file and hunk, and commit details hand Rem's message box a draft through `RemHandoff` (`live/AskRem.kt`, `ui/AskRemSelection.kt`). It never sends and adds no peer behavior. The draft names the project, relative path, lines or commit ID, and any picked text, and the desktop decides what Rem may do with it as for typed text. Secret-looking files, which the desktop already refuses to read, offer no Ask Rem. See [the protocol section](mobile-desktop-v2.md#ask-rem-about-a-file-or-a-change-november-9-2026).

**Phone commands.** Voice mode runs `PhoneCommands.parse` on the final words before anything is queued for the desktop (`VoiceController.send`, and `tidyThenReview` before the desktop's tidy model). A match never reaches the desktop or a model: `CommandPlan` resolves the person through `PhonePeople`, `TextTidy` tidies a text's message with fixed rules, and `PhoneEffects` acts. Calls go through `TelecomManager.placeCall` and texts through `SmsManager` (multipart when long, with a sent-status broadcast to an unexported receiver), after a 2 s (call) or 3 s (text) countdown the user can cancel; closing voice mode cancels it too. They need `CALL_PHONE` and `SEND_SMS`, asked for at first use; without them the dialer or a draft opens. Emergency numbers (`TelephonyManager.isEmergencyNumber`) are never called directly. Calls, texts and anything that opens another app need an unlocked phone; the flashlight, media keys, volume and the time, date and battery answers don't. Commands run only on the user's own words in voice mode, never on Rem's replies, the suggestion chips Rem writes under them (`sendSuggestion` always goes to Rem, `VoiceLogic.mayRunOnPhone`), shared content, notifications or screen text, and with files attached the words go to Rem. Media keys and volume need an object ("pause the music", "mute the sound"), so bare words such as "stop", "continue", "next" or "mute" go to Rem; device results offer **Ask Rem instead** for 3 seconds before voice mode steps aside. While the user talks, words that start like a command (`PhoneCommands.mightBeCommand`) are kept from the desktop's progressive tidy. The manifest test still forbids reading SMS, the call log, contacts and the rest of the SMS group; only `CALL_PHONE` and `SEND_SMS` are allowed, and `scripts/release-policy.json` lists both. Opening an app by name uses a `<queries>` entry for launcher activities, not `QUERY_ALL_PACKAGES`. Words the desktop tidied never run as a phone command when Send delivers them straight away: the words as heard weren't a command, so they go to Rem.

**People for call and text cards.** When the user names a person, the card carries only their words (`recipient`). `PhonePeople` matches them against people the user picked with Android's phone-number contact picker, which grants read access to the one chosen entry without `READ_CONTACTS`. `PeopleStore` keeps those entries encrypted under its own Keystore key in no-backup storage and holds per-card picks in memory; nothing about them is sent to the desktop or logged. One match opens that number, several ask which, none opens the picker, and every path still ends in the dialer or a draft the user completes. More › People Rem can reach manages the list.

**Not verified.** Real speech, the microphone indicator, offline voices and power-button mappings depend on the phone and were only exercised on an Android 16 emulator. Manufacturer settings menus, low-RAM assistant activities and vendor battery limits on the bound service remain untested on hardware.

## Child lock

`ChildLock` holds one saved fact, whether Raticode is locked. `ChildLockActivity` is a private, see-through activity on top of `MainActivity` in the same task. Being a separate window above the app, it covers every Compose dialog, sheet and popup, the WebView full-screen dialog and browser prompts, and takes key and accessibility focus. Its theme is translucent, so `MainActivity` only pauses: `BrowserRuntime` and `GeckoBrowser` follow `onStart`/`onStop`, so browser playback continues. Raticode's own player for chat and file video and audio pauses on `ON_PAUSE` (`ChatMediaView.kt`), so it stops if the lock covers it. That player is a dialog over the lock handle, so the handle can't be reached while it is open.

**The handle.** `ChildLockHandle` (`ui/ChildLockControl.kt`) is one edge tab drawn in three places: `MainActivity`'s root, the WebView full-screen video dialog and `ChildLockScreen`. `MainActivity` and the video dialog draw it only while unlocked; the lock screen draws it in the same spot with a closed padlock, so the control that turns the lock on is the one that turns it off, and there is no second button. Whether it is out is process-wide state in `EdgeHandle`, so every copy agrees and it survives the switch to the lock activity and a rotation; it starts tucked away after a process start. Away, only a 4 dp mark and a 24 × 80 dp target stay on the edge; a tap or a pull to the left brings it out, a vertical scroll there doesn't. A swipe right past 40% of its width, or a flick faster than 400 dp/s, puts it away, and it hides after `IDLE_MS`, stretched by `AccessibilityManager.calculateRecommendedTimeoutMillis`, unless a tap is armed, a finger holds it or Android's prompt is up. The slide is a Compose spring, which Compose scales by Android's animator duration setting, so it is instant with animations off. The 1.5-second hold is a real `delay`, not the ring animation, so turning animations off can't shorten it. The visible handle is excluded from system back gestures. Trade-off: a child can still find the edge mark and bring the handle out, and holding it brings up Android's prompt, which they can only cancel; before this change the lock was always on screen.

**Turning on.** The edge handle (tap, then tap again) and the More row call `ChildLockRuntime.engage`. The state is committed to storage first. With no screen lock (`KeyguardManager.isDeviceSecure` false), or if the write fails, the lock is refused with an explanation, since it could never be turned off or wouldn't survive a relaunch.

**Staying on.** Each `MainActivity.onResume` starts the lock again if it is missing, which covers a relaunch, recreation and notification intents. Notifications and the conversation shortcut open `NotificationOpenActivity`, a private activity with no window that finishes at once. While locked it leaves the lock in place, so a tap brings the task forward without clearing the lock, without touching an open dialog or full-screen video, and without changing the page. Only when Android has ended the lock activity does it start `MainActivity`, without the notification's destination, and that locks itself. Otherwise it forwards to `MainActivity` with `LiveNotifications.OPEN_FLAGS`, which reuses the existing screen. `dispatchTouchEvent` drops main-window touches in the moment before the lock window appears, and notification intents received while locked are dropped. `ShareActivity`, `VoiceActivity` and `RemVoiceSession` refuse to open. Alert replies and the Stop actions on the playback and sync notifications are refused, and a file download that finishes under the lock doesn't open in another app.

**Turning off.** A 1.5-second hold starts Android's prompt. On Android 11 and newer that is `BiometricPrompt` limited to `DEVICE_CREDENTIAL`, which needs the normal `USE_BIOMETRIC` permission; on Android 10, which can't limit the prompt that way, it is `createConfirmDeviceCredentialIntent`, whose screen may also offer an enrolled fingerprint or face. Android collects the credential; the app only gets a result. Only a success result that Android labels as the device credential turns the lock off; a biometric or unknown result type is refused. Every error, a cancel and an unknown code leave it on. If the screen lock was removed while locked, the hold explains that and offers Android's security settings, and the lock stays on until a new screen lock is confirmed.

**Limits.** The lock is unavailable below Android 10: `minSdk` is 26, but `RaticodeApp` shows only a notice below API 29 and `MainActivity` adds the control only from API 29. `ChildLockActivity` has no key handling, so volume keys still change the volume; Android would let a focused activity consume them, but the lock doesn't. Android gives an ordinary app no way to block Home, Recents, the notification shade or other apps. Lock task mode needs a device owner, and `startLockTask` without one is screen pinning, which the user confirms and can leave. Clearing Raticode's storage or uninstalling it removes the lock, because Android doesn't let an app prevent that. A force stop only closes the app, and the lock is back at the next launch. See `docs/live-device-setup.md` for the device checks still to run.

## App lock

`AppLock` is off until the user turns it on (More › App lock). It decides when Raticode has to ask who is holding the phone, in plain Kotlin that the unit tests run. `AppLockActivity` asks; `ScreenLockPrompt`, shared with Child lock, drives Android's prompt. Child lock stays `DEVICE_CREDENTIAL` only. App lock allows `BIOMETRIC_WEAK | DEVICE_CREDENTIAL`, since face unlock is commonly class 2 and no key depends on the result. Android 10 uses `createConfirmDeviceCredentialIntent`, as Child lock does. Android collects the credential; the app only gets a result. Only a success Android labels as biometric or device credential counts. No new permission or exported component is added.

**When it asks.** `RaticodeApplication` registers one `ActivityLifecycleCallbacks` that counts every Raticode screen except `VoiceActivity` and the windowless `NotificationOpenActivity`, so moving between screens is not leaving. When the last screen stops, it commits the time since boot and Android's boot count; a return decides from those and clears the record. A rotation doesn't count, a new process honours the delay, and anything doubtful asks: no record (a crash), another boot, an unreadable count, a clock running backward, or an unreadable delay. The delay is compared against `SystemClock.elapsedRealtime`, which Android settings can't change. Android 10's confirmation is another screen, so a return within two minutes of an open prompt isn't treated as opening the app.

**Covering the app.** `AppLockActivity` is private and goes above the screen that started it. It draws an opaque page in `Theme.Raticode.ChildLock`'s translucent window: nothing shows through, but `MainActivity` only pauses. `LiveClient` therefore keeps `onScreen` and the connection, background sync and alert replies are untouched, and the outbox keeps sending. `RemReplyReceiver` doesn't check App lock. The lock is started from `onStart`, and `MainActivity` draws an opaque `AppLockCover` from the first frame, clears its semantics and drops touches until the lock window arrives. Passing App lock never clears Child lock; with both on, App lock goes first and Child lock returns under it.

**While covered.** `LiveClient.userSees` is false, so the page under the lock isn't marked read, Rem's alerts still show, and `remChatOnScreen` reads false. `LiveScreen` calls `client.foreground()` when the lock clears, which is when the page first counts as seen. Files finishing a download under the lock don't open in another app. A notification tapped while a lock screen is showing is held in memory and opened after unlock, so the lock isn't cleared to reach `MainActivity`. A cold notification opens `MainActivity` directly and locks itself with its destination intact. `ShareActivity` is gated the same way in the sharing app's task, and Back there closes the share rather than moving the other app's task. Voice mode is deliberately not gated: it keeps its own `isDeviceLocked` rule.

**Settings.** Turning it on or off and lengthening the delay need Android's prompt, which also proves a screen lock works before the user can be locked out. A phone with no screen lock can't turn it on; if the screen lock is removed later, the lock stays on and offers Android's security settings. On Android 13 and newer `setRecentsScreenshotEnabled(false)` hides the recent-apps preview while the lock is on.

**Limits.** The lock is unavailable below Android 10, where the app is only a notice. Recent-apps previews are not hidden on Android 10 to 12L (no per-activity API short of `FLAG_SECURE`, which would also block the user's screenshots). The idle time counts from leaving the screen, not from inactivity while the app stays open; the phone's own screen timeout covers that. With **Immediately**, returning from a system picker asks. The picked file arrives beneath the lock. Clearing Raticode's storage removes the setting.

## Wake the computer

A sleeping desktop leaves the phone with nothing it can do, so the phone can offer one Wake-on-LAN packet. The desktop owns the opt-in. Its off-by-default setting adds `wake_mac` to the `overview` answer inside the pinned TLS session, and the phone keeps that in its encrypted journal next to the paired peer, because it has to be readable while the desktop is off. An `overview` without the field removes the saved address, and so does a snapshot saying desktop control is off. Forgetting the pairing removes it with the peer.

**When the button shows.** `WakeOnLan.target` needs a saved address and a private IPv4 Wi-Fi desktop address (a manual one wins, as it does for connections). `WifiRoute` then checks that one of this phone's own Wi-Fi addresses shares a subnet with it, using the phone's prefix length. Tailscale addresses never qualify. The button is on the Desktop page, and elsewhere `WakeBanner` offers it after a connection attempt has actually failed, so it doesn't flash during an ordinary reconnect.

**What a tap does.** `LiveClient.wakeComputer` sends one 102-byte packet to the subnet's broadcast address on UDP port 9, on a socket bound to that exact Wi-Fi network, then asks for the usual reconnect. It runs on its own short thread because the sync thread may be waiting on a connection attempt to the sleeping desktop. The button is disabled for 30 seconds so a double tap can't send twice. Wake-on-LAN has no reply, so the button says only "Wake signal sent" and never reports success; whether the desktop came back is shown by the ordinary connection status.

**Limits.** It doesn't work over Tailscale, because a tunnel can't carry a subnet broadcast. It needs firmware and network card support, and routers or access points that isolate Wi-Fi clients may not pass it on to a wired computer.

**Security review note.** The packet is unencrypted by design: the format is defined by network card firmware, which can't do TLS. It is the only desktop-related traffic outside end-to-end TLS, and it holds the fixed header and the hardware address and nothing else, as `WakeOnLanTest` asserts byte for byte. For the independent reviewer:

- Anyone on the same subnet can read the hardware address and send the same packet. A hardware address isn't a secret, and it is already visible on the local network whenever the computer talks. The most an attacker gains is waking a computer that has Wake-on-LAN enabled.
- Showing the button only proves the numbers match. A different network using the same subnet numbers, such as another `192.168.1.0/24`, passes the check, and a tap there broadcasts the hardware address to that network. It needs a deliberate tap on a button that the user turned on, and Android gives this app no way to identify the network without location permission, which was judged not worth adding.
- The desktop can't direct the packet anywhere. The phone works out the destination from its own Wi-Fi prefix, and the desktop's reported address only chooses which Wi-Fi network to use. A malformed, multicast or all-zero hardware address is refused and clears the saved one.
- It adds no permission (`INTERNET` and `ACCESS_NETWORK_STATE` were already granted), no exported component, no mobile-data or Tailscale route, and no new authority: the packet can only wake a computer, and everything afterwards still goes through the paired, pinned TLS session and desktop policy. The address is never logged.

## Task progress notification

`TaskProgress` is plain Kotlin and decides everything: which runs this phone started, what the notification says and whether reading the desktop is still useful. `TaskNotification` carries it out with Android's APIs and `TaskProgressReceiver` takes Hide and swipes. `LiveClient` only records requests, feeds each full `rem.home` answer in and clears the notification when sync, the pairing or the connection go away.

**What counts.** A run belongs to this phone when it follows one of this phone's own `rem.message` requests in Rem's chat (the desktop's message ID is the phone's request ID), when its task was asked for by **Run now**, **Retry review** or a new task from this phone's screens, and only for 10 minutes after the request. A run from a schedule, one Rem started for the desktop, or one that was already going does not count. Self-work posts no chat messages, so nothing links its runs to a request. Claims live in the encrypted journal, in the same write as the request or the received answer.

**Android.** One notification, ID 2005, on the Low-importance `task-progress` channel. It always has the four steps in its text, a chronometer for elapsed time and a generic public version. Android 16 adds `ProgressStyle` and a promotion request with the current step as the status-bar chip's text, which Android 16.1 and newer honour as a Live Update. Older versions show only the step line, because a progress bar replaces the text when the notification is collapsed, and use their own notification group so Android doesn't fold it under the sync notification. Android 13 and older can't swipe away an ongoing notification, so Hide works on every version. A dismissed run is saved in the journal and never reposted; a new run shows again. A process that dies leaves a notification nobody can update, so the client clears it on start, and a connection lost for two minutes clears it until a later read confirms the run.

**Battery.** The phone reads `rem.home` every 15 seconds only while background sync is on, Android allows the notification, and there is a claimed run not dismissed or a request under 10 minutes old. Otherwise it adds no traffic. The `known` digest makes most answers a few bytes. Android counts the elapsed time itself, so the notification changes only when a step does. A real-phone battery check is still outstanding.

## Share to Rem

Android 10 and newer list Raticode as **Rem** in the share sheet for text, pictures, videos and PDFs (`ACTION_SEND` and `ACTION_SEND_MULTIPLE` with `text/*`, `image/*`, `video/*` and `application/pdf`). The `share_to_rem` boolean resource (`values-v29`) turns the screen off on older phones, which can't hold the live connection. Following Android's guidance for share targets, nothing is sent until the user reviews it and taps **Send**; voice mode's auto-send never applies.

**Entry point.** `ShareActivity` is exported for the share sheet and runs in the sharing app's task. Android's temporary read grant for the shared URIs lasts until that task finishes, so files are read while the review is open and never later. It doesn't set `showWhenLocked`, so it can't appear over the lock screen, and Send also checks `KeyguardManager.isDeviceLocked` and refuses. It reads only `EXTRA_TEXT`, `EXTRA_SUBJECT` and `EXTRA_STREAM`, falling back to `ClipData` URIs; any other extra is ignored, and nothing in a share can start work, choose a thread or skip the review. Android 13 and newer leave the screen out of the recent-apps preview.

**Review.** `ShareSession` (a view model, so rotation keeps the review) asks each provider only for a type, display name and size, each provider call on its own thread with a 5-second limit, because a provider can block without end. `ShareIntake` decides what is offered, and it is unit-tested without Android. It accepts only `content:` URIs. It refuses any URI served by Raticode itself, by authority prefix or by the provider's package, so another app can't make Raticode upload its own cached files. It re-checks the provider's type against the supported list, takes at most 8 files, and limits text to 4,000 characters with a note when shortened. Control characters and text-direction overrides are removed so a disguised link shows plainly. Files over 10 MB, or more than 40 MB together, block Send until they're removed. Each refusal is listed in plain words. The shared text is editable, and the sheet warns that Rem reads all of it as the user's request and may pass it to the desktop's model, so instructions the user didn't write should be removed. A shared request is a phone request, so Rem may answer it with phone action cards; each card still needs its own tap.

**Sending.** Send reuses the composer's paths: `LiveClient.importRemFile` reads each file through `DocumentImport` (bounded, cancellable, 10 MiB, wiped after use) and queues it as a `file.offer` on the Rem chat file channel. Names are made safe and gain an extension for their type, because the desktop picks the attachment type from the name. No file is ever written under a provider's name. When the uploads are `available`, and after any Rem reply in progress, `sendRemMessage` queues one `desktop.action` `rem.message` with the attachment IDs. The sheet shows **Queued** once the request is in the encrypted outbox, and **Sent** only when the desktop's authenticated `rem.home` contains the message's ID. A refusal returns to the review with the desktop's reason. A send needs a paired desktop with **Use Raticode from this phone**; files also need a desktop that reports the Rem file channel. Otherwise the sheet says what to change. While the sheet is open, or a send is still running behind it, `LiveClient.shareStart` keeps the connection and reads `rem.home` once a second without marking any thread read, as voice mode does. `shareStop` disconnects unless the app, voice mode or background sync needs the connection. Watching for the desktop's answer stops after 2 minutes. Stop or Cancel before queuing sends nothing; files already uploaded expire unused on the desktop's phone channel. No protocol or desktop change is needed.

**Not verified.** The sheet has been checked by unit tests, Kotlin and lint compilation, and an instrumentation test (`ShareUiTest`) that was compiled but not run, because running it needs an APK build. Real share sheets (Chrome, Photos, Files, Samsung Gallery), Direct Share and multi-window drag-and-drop are untested. Direct Share targets and drag-and-drop aren't implemented, and neither is sharing to a desktop thread other than Rem's chat.


## The browser

Since November 6, 2026 the phone has **More › Browser** (also a bottom-bar choice): Raticode's browser rebuilt for the phone on Android's system WebView, since the desktop's Electron tabs, profiles and Rem's browser tools can't run on Android. `browser/BrowserRules.kt` holds the decisions plain JUnit tests (address bar input, which navigations load, are explained, ask first or are refused, history, bookmarks, suggestions, download names and warnings, saved state). `browser/BrowserRuntime.kt` is one per process and owns the tabs and their WebViews, so tabs survive moving between pages; at most three keep a live page and the rest sleep with their back/forward list in memory. `browser/BrowserStore.kt` saves tabs, history, bookmarks and choices encrypted under their own Keystore key in no-backup storage. `ui/BrowserPage.kt` draws the page, and `ui/BrowserControls.kt` draws one compact toolbar at the top, which `browser/BrowserControlsMotion.kt` folds to a strip while reading. Composables call the runtime and `LiveClient`; neither builds transport records.

Pages load over the phone's own internet connection, never the desktop link, and only `https` pages load: the app's `usesCleartextTraffic="false"` also covers WebView, so `http` gets an explanation and the phone's own browser instead. Each WebView has no file or content access and no JavaScript interface; mixed content, third-party cookies, location and unprompted pop-ups are refused, and a page gets the camera or microphone only after a yes each time; Safe Browsing is on and WebView metrics are off. App links ask first and lose named components and URI grants; certificate errors are never bypassed; a crashed page process is let go instead of ending the app. Downloads ask first and use Android's download manager.

Two desktop ops connect it to the computer: `browser.tabs` lists the desktop window's web tabs (yours and Rem's, never previews or local files), and `browser.open` opens a page in a new background tab of the user's desktop profile, never Rem's. The window publishes and collects them through the local API on its device-sync loop; the desktop keeps both in memory only. **Ask Rem about this page** puts the title, address and any selection in Rem's message box through `RemHandoff`, and nothing sends until the user does. Web links in chats open in the browser unless the user turns that off. See [the protocol section](mobile-desktop-v2.md#the-browser-on-the-phone-november-6-2026).

**Firefox (November 7, 2026).** Browser settings offer Raticode or Firefox. With Firefox, `ui/FirefoxPage.kt` hands addresses, the computer's tabs and chat links to Firefox for Android (a Custom Tab over Raticode, or the Firefox app) and opens Firefox's own settings, Mozilla account sign-in, add-ons and privacy screens through the deep links Firefox exports. `browser/FirefoxApps.kt` sends only those screens and web addresses, and only to a Firefox or Firefox Beta that Android confirms Mozilla signed. Raticode reads nothing from Firefox's profile. The computer's engine shows on its tab list, and More › Desktop settings can switch it. See [Firefox as the phone's browser](mobile-desktop-v2.md#firefox-as-the-phones-browser-november-7-2026).

**Microsoft Edge (November 7, 2026).** Browser settings also offer Microsoft Edge. `ui/EdgePage.kt` hands addresses, the computer's tabs and chat links to Edge for Android (the Edge app by default, in its own task so its tabs and sound survive switching, or a Custom Tab over Raticode). Edge documents no deep links into its settings, Microsoft account sign-in or extensions, so those rows open Edge and say where to tap; no undocumented intents are sent. `browser/EdgeApps.kt` sends only web addresses, and only to Edge, Edge Beta, Dev or Canary that Android confirms is signed with a certificate Microsoft's Digital Asset Links file lists for it. The computer's tab list can say it runs Edge, and Desktop settings offer Edge when the desktop lists it. Not yet run against a real Edge. See [Microsoft Edge as the phone's browser](mobile-desktop-v2.md#microsoft-edge-as-the-phones-browser-november-7-2026).

**Google Chrome (November 7, 2026).** Browser settings also offer Chrome. `browser/BrowserApps.kt` describes a browser app once (its saved engine value, packages, its maker's signing certificates, a sign-in page and what it can't do) and `ui/BrowserAppPage.kt` is the page for any of them; saving the choice, the Browser page, Browser settings and chat links all go through `BrowserApps.ALL`, so another such app is one new file. `browser/ChromeApps.kt` is Chrome: pages go to Chrome or Chrome Beta only when Android confirms Google signed it, in the Chrome app by default or as a Custom Tab over Raticode. Chrome exports no links to its settings or sign-in and has no extensions, so the page offers only pages, Google's sign-in page, Android's app settings for Chrome and its Google Play page. The computer's tab list can say it runs Chrome, and Desktop settings offer Chrome when the desktop lists it. See [Google Chrome as the phone's browser](mobile-desktop-v2.md#google-chrome-as-the-phones-browser-november-7-2026).

**Gecko browser (November 8, 2026).** `browser/GeckoBrowser.kt` runs GeckoView inside Raticode as a second browser, with its own tabs, profiles (session contexts), favorites, settings, and Firefox extensions from addons.mozilla.org. It is https-only and refuses the same addresses as the Chromium browser, and asks the same way for the camera or microphone. On the desktop, where Gecko has no embedding API, Raticode instead places real Firefox's window inside the tab over X11, on Linux only. See `docs/mobile-desktop-v2.md`, Gecko inside Raticode.

**Private tabs (November 8, 2026).** Tabs marked private exist only in memory: `BrowserRules.encode` and `GeckoRules.encode` leave them out of saved state, and they add no history or closed-tab entries. WebView tabs run in a throwaway `androidx.webkit` profile that is deleted after the last private tab closes, and again at the next start if Android ended the app first. Gecko tabs use `usePrivateMode`. Gecko's own rule removes that data when the last private session closes, so private sessions are never closed to save memory.

**Browsing inside Raticode (November 8, 2026).** Only Raticode's browsers (WebView, and GeckoView above) run inside Raticode's window; Android gives other apps' screens their own window (Custom Tabs, the app itself), and cross-app activity embedding needs an opt-in Firefox, Chrome and Edge don't make. Their pages call the Custom Tab choice **Quick look** and offer **Browse inside Raticode**. The integrated browser's page controls sit under the address bar, and its pages keep running while Raticode is in front on any page. When `MainActivity` stops they pause, except a page playing sound, which keeps playing under a `mediaPlayback` foreground service (`BrowserPlaybackService`) with a media session and media notification: the lock screen and shade controls, and Stop. See `docs/mobile-desktop-v2.md`, Lock-screen media controls. See `docs/mobile-desktop-v2.md`, Browsing inside Raticode.

**The media bar (November 8, 2026).** `browser/BrowserMedia.kt` gathers what `BrowserRuntime` and `GeckoBrowser` report and carries out the bar's buttons; `ui/BrowserMediaBar.kt` draws it as the first child of `LiveScreen`'s column, so it sits above every page. Decisions live in plain-Kotlin `BrowserMediaRules`. Since November 10, 2026 the bar draws `BrowserMedia.bar`, which skips the tab the Browser page shows (`BrowserMedia.inView`, set by `ShowingMediaOf` while the page is composed), while the lock-screen controls keep following `BrowserMedia.current`. The desktop bar skips its on-screen editor tabs the same way. Titles, artists and artwork addresses are page-supplied, so they are cleaned, capped and always shown beside the site. WebView still has no JavaScript interface: the app runs scripts in the page and reads their answer, and the page can't call the app. See `docs/mobile-desktop-v2.md`, The media bar.

**One tab list (November 10, 2026).** The built-in browsers are named Raticode (chromium) (`BrowserRuntime`, WebView) and Raticode (gecko) (`GeckoBrowser`); stored values stay `raticode` and `gecko`. `ui/BrowserTabsSheet.kt` lists both runtimes' tabs in one sheet, ordered by plain-Kotlin `BrowserTabs`. The runtimes stay separate (tabs, private sessions, history, downloads, sign-ins, rules); picking a tab of the other one sets `BrowserRules.Saved.showing`, which routes the Browser page without changing the default (`engine`). Firefox, Chrome and Edge can only take a page. See `docs/mobile-desktop-v2.md`, One tab list for both built-in browsers.
