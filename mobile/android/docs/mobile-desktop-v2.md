# Device protocol v2 candidate

> Since November 2026 this app lives in the Raticode repository and `src/gofer/devices/protocol/v2` is the only copy of these schemas. Dated notes below that mention both repositories, or files being byte-identical, describe the time when the two apps were separate.

September 19, 2026. Mobile owned `protocol/v2` at this point. Desktop and Mobile developers agreed the TLS profile, invitation and session fields, framing constants, role boundaries and retention rules on the shared swarm board. This candidate preserves `protocol/v1`; it does not reinterpret v1 Noise bytes as TLS.

Implemented here are a bounded Android/JVM TLS engine, opaque carrier reordering, authenticated-stream JSON framing, controller capability rejection, schemas, and public interoperability probes. Enrollment, protected trust, LAN/ntfy adapters, durable journals and live UI are now implemented separately from the retained public feasibility probes. Schema acceptance alone never authorizes an action.

## Protocol choice and evidence boundaries

Use standard TLS 1.3 through Android's platform SSLEngine, paired with Python pyOpenSSL/OpenSSL memory BIO. The proposed Noise XXpsk3 profile was not blindly implemented. Signal's old Noise Java artifact uses legacy NoisePSK behavior. Other evaluated Noise candidates lacked the required review or Android evidence. The user explicitly authorized evaluating standard TLS instead, and both developers agreed after runnable probes.

Platform engines own the handshake, signatures, key schedule, record encryption and cipher counters. No application cryptography or patched Noise internals exist here. Android live transport requires API 29 or newer. The minSdk 26 app displays an Android 10 requirement on older devices. The simulator is now test-only. A successful API 36 emulator test is not evidence for every API 29+ vendor device.

TLS is a reviewed standard, and platform providers receive platform security updates. That does not establish independent review of this application protocol, enrollment ceremony, storage, relay framing or authorization. Independent cryptographic review remains an unmet release gate. Debug INTERNET permission is explicitly authorized for disposable local interoperability tests. The app now has INTERNET permission and live-only navigation; historical simulator code is restricted to tests. The user's networking authorization permits later implementation without claiming the independent review passed.

Sources inspected for this decision:

- [Android SSLEngine protocols and APIs](https://developer.android.com/reference/javax/net/ssl/SSLEngine), TLS 1.3 starts at API 29.
- [Android 10 TLS behavior](https://developer.android.com/about/versions/10/behavior-changes-all#tls-1.3), including no supported 0-RTT.
- [TLS 1.3, RFC 8446](https://datatracker.ietf.org/doc/html/rfc8446).
- [Conscrypt capabilities](https://github.com/google/conscrypt/blob/master/CAPABILITIES.md).
- [Python TLS memory BIO documentation](https://docs.python.org/3/library/ssl.html#memory-bio-support).
- [Signal's legacy Noise implementation](https://github.com/signalapp/noise-java/blob/master/src/main/java/com/southernstorm/noise/protocol/HandshakeState.java).
- [Tink releases](https://github.com/tink-crypto/tink-java/releases) and [streaming format](https://developers.google.com/tink/streaming-aead/aes_gcm_hkdf_streaming).

## Identities and enrollment

The profile name is `raticode-tls13-v2`; ALPN must negotiate exactly `raticode/2`. Enable only TLS 1.3, no SNI, no 0-RTT, no cached sessions. Construct a new SSLContext for every connection and route migration. Do not export or persist TLS cipher state. Desktop additionally disables tickets and session caching. Android may issue unused tickets when tested as a responder; a fresh context prevents accepting resumption on another connection.

Each device has one self-signed EC P-256 certificate. Check validity dates, self-signature, one-certificate chain, exact P-256 parameters and the SHA-256 of DER SubjectPublicKeyInfo. Pin matching is mandatory even if the system trusts another certificate. TLS CertificateVerify proves possession of the corresponding private key. Display labels, DNS, IP addresses, QR previews and discovery are never authentication. Application code must also check active trust and revocation before dispatch, including queued work.

Android identity keys must be generated and used through Android Keystore in the pairing milestone. Never silently replace missing keys while protected trust exists. Desktop uses an OS credential facility, with fail-closed behavior when unavailable. This feasibility milestone uses only public test identities in test source sets, never production signing material.

An invitation uses `raticode://pair?v=2&data=<unpadded-base64url-utf8-json>`, at most 4096 characters. Its exact decoded bytes follow `invitation.schema.json`. Fields include responder identity and pin, role desktop, HTTPS relay origin, separate random 256-bit bootstrap topics, an independent random 256-bit invitation secret, optional LAN endpoint and expiry. Topics are routing values, never encryption keys. Validate origin and endpoint before contact; prohibit credentials, URL actions, paths, query and fragments. Reject controls in names. Cap lifetime at 300 seconds, and fail with a clock error if expiry cannot be checked. Bootstrap topics must differ. Desktop serializes consumption and bounds failed attempts.

The initiator always pins the QR responder before sending the secret. For enrollment only, desktop's TLS verification callback may accept an unknown structurally valid self-signed P-256 client certificate to prove possession. This grants no trust. The first encrypted `session.bind` must match both roles/IDs, profile, mode, random session ID, SHA-256 of the exact decoded invitation bytes, and the one-time secret. Compare secrets in constant time. Never reserialize invitation JSON before hashing. The responder returns the same binding; both sides verify it before any other records.

Desktop then requires explicit local trust confirmation. Pending enrollment cannot dispatch events. Persist the confirmed identity, granted capabilities and new long-term random routing topics before `session.ready`. The initiator durably saves protected trust before `session.ready_ack`. Desktop activates the enrollment durably after that acknowledgment. Recovery may only finish the same pending enrollment using the same authenticated pin; it may not consume another invitation or acquire new capability. Lost keys require a fresh invitation and desktop revocation of the old device.

Reconnect requires mutual pinned TLS, active registry trust and a resume binding with null invitation hash/secret. A ready acknowledgment is enrollment durability evidence, not a chat/work receipt. Revocation invalidates active sessions, routing credentials, pending enrollment and queued dispatch; check registry revision again at the dispatch transaction. Full expiry/race/recovery/revocation state-machine tests belong to pairing, not to these TLS feasibility tests.

## Framing and routes

The same format carries opaque end-to-end TLS bytes over direct LAN or ntfy. Outer HTTPS to ntfy is separate from inner device TLS. A relay sees only random routing/session values, direction, byte indexes, timing and sizes. It must never receive plaintext bodies, file metadata, paths, keys, invitation secrets or preview headers. TLS 1.3 encrypts identity certificates after ServerHello; initial TLS handshake metadata remains observable.

| Limit | Value |
| --- | --- |
| Encoded outer JSON frame | 3072 UTF-8 bytes |
| Decoded opaque TLS fragment | 1 through 2048 bytes |
| Buffered out-of-order fragments | 32 |
| Out-of-order byte budget | 65536 bytes |
| Missing-fragment deadline | 30 seconds, monotonic clock |
| JSON application/session record | 1 through 65536 UTF-8 bytes |
| JSON nesting | 16 |
| JSON collection elements | 1024 |

Outer fields are exactly `version`, `session_id`, `mode`, `direction`, `index`, `body`. Index increases per direction over the entire handshake and encrypted stream. It is not a TLS cipher counter or a durable event sequence. Validate strict JSON, canonical base64url and exact route binding. Reject conflicting buffered duplicates. Discard old carrier duplicates without dispatch; TLS validates ordered ciphertext. Authenticate the outer session/mode binding again inside the first encrypted record. Modified outer fields may cause bounded connection failure, never trust or plaintext acceptance.

A gap timer runs even without new traffic. On timeout, malformed input, TLS failure or migration, discard the carrier and TLS session. Start a fresh authenticated session and replay durable application IDs. Never splice bytes across sessions or routes. `OpaqueTlsReorder` emits fragments individually so callers can pump bounded TLS input. LAN reads must likewise split into at most 2048-byte feeds. Serialize engine calls; the future adapter owns a handshake deadline and cancellation. An authenticated TLS engine alone is not an enrolled or authorized peer.

Inside TLS, every JSON record has a four-byte unsigned big-endian length. Validate the bound before allocation. Records can cross TLS or carrier boundaries; decode UTF-8 only after complete reassembly. Duplicate JSON fields, invalid UTF-8, trailing input, unknown fields/types and truncated streams fail closed. The public fixture `frame.json` demonstrates encoding only; it is not ciphertext or a handshake transcript.

Prefer LAN only after authenticating the pinned endpoint. Same-network detection/discovery may suggest an address, but cannot establish trust. If direct authentication or liveness fails, use a fresh pinned session over the configured relay. Use identical durable event/request IDs across routes. Do not copy TLS counters. A relay publish success or LAN socket write is not a durable peer receipt.

## Durable application rules

The v2 envelope retains `id`, `thread_id`, `request_id`, `sequence`, `type`, `payload` with version 2. Session authentication supplies sender identity. Catalog, sync and fleet events use null thread IDs; bounded errors may also use null. Thread creation obtains its authoritative ID from desktop. Every context update carries `expected_revision`; provider/model changes preserve the existing thread, persona, project/resources and history. Names are labels, never paths or grants.

Event IDs identify immutable serialized bytes. Preserve those bytes on retry and hash them before storage; never hash language-dependent JSON reserialization. Event deduplication is independent from operation/request deduplication. Multiple correlated replies or cancellation events may share a request ID but must have separate event IDs and sequences. Persist inbox event, cursor, authorization context and accepted work atomically before emitting acceptance. Commit outgoing bytes before scheduling any transport.

Retain event history for seven days, capped at 10000 events per peer. History expiry requires an authoritative snapshot and cursor transaction before dependent work resumes. Retain accepted request/job tombstones for the lifetime of pairing. Pending accepted work is capped at 100 operations per peer and 20 per thread. Initial implementation budgets cap a peer's pending outbox at 128 events/8 MiB, history at 64 MiB and tombstones at 100000; reject new work when full rather than evicting deduplication evidence. These operational caps must be surfaced in the adapters and tested there. Retry transient transport failures with jittered exponential backoff from two seconds to five minutes and respect Retry-After. Permanent validation, revoked trust and authorization failures are not retryable.

`outcome_unknown` exists for both chat and fleet jobs when non-idempotent execution may have started before a crash. Retrieve the durable result or require desktop recovery; never automatically dispatch a second job. Cancellation intent and confirmed cancellation are separate states. A new event ID must not bypass a stable job ID/input-hash conflict check.

Mobile role is always `controller`. It never advertises or receives `worker.execute`. `MobileCapabilities` rejects worker grants and incoming job submit/cancel/get requests. Fleet job execution requires both endpoints to be explicitly trusted desktops and a target-local policy revision/project/resource/tool approval check. Enrollment capabilities grant communication only. Desktop local confirmation also enables workspace sync by default for a new phone, effective after its authenticated acknowledgment; execution still uses desktop-owned thread context and approval policy. Remote approvals remain absent by default and must never widen existing desktop policies.

Fleet status comes from authenticated heartbeat/snapshot evidence, with `observed_at`, `last_seen` and `fresh_until`. Use 20-second authenticated heartbeats on LAN only. Bound freshness to 60 seconds. Offline means an observed transport disconnect, never proof a machine is powered off. Display stale/unknown once freshness expires; never turn discovery or an old snapshot into reachable status. Empty running-work data on a stale peer means unknown work, not proof of idleness. Avoid periodic relay heartbeats under public quotas.

## Files, relay and threat model

File candidate: Tink RAW `AES128_GCM_HKDF_1MB`, Java/Android 1.23.0 and Python 1.16.1. Use library streaming APIs and native format without custom encryption. AAD is exact UTF-8 `raticode-file-v2\n<canonical-file-UUID>\n<decimal-plaintext-size>\n<lowercase-plaintext-SHA256>` without a final newline. Bind name, MIME, file ID, keyset and transport manifest inside an authenticated encrypted offer. File manifest/chunk schemas are reserved for the jointly reviewed files milestone; v2 `file.offer` alone does not grant file capability yet.

Reassemble encrypted stream bytes in order, authenticate to EOF, enforce actual byte counts and whole-file SHA-256 before making a file available. Reject truncation even on a segment boundary. Keep 10 MiB plaintext/file, 50 MiB local attachment quota, 24-hour incomplete-transfer expiry (the phone's own upload offers end ten minutes earlier, because the desktop refuses an `expires_at` more than a day past its clock), and explicit scoped export. Validate quotas before and during streaming. Never export unauthenticated prefixes or auto-open executables. Keys and metadata remain inside TLS/protected local storage.

ntfy is configurable and untrusted; there is no Raticode SaaS backend. Desktop owns dated official quota evidence. Public-service constraints reported by Desktop dev include 4096-byte messages, 250 publishes/day and 2 MB attachments. Treat deployment limits as configuration/capability limits, not an SLA. A 10 MiB encrypted stream cannot be one public attachment. The files milestone must choose bounded opaque encrypted segments with whole-stream reassembly or direct LAN transfer; no paid plan or plaintext fallback. Coalesce token replies and expose rate-limit/backoff state. Physical-device background reliability and public-network migration remain untested.

Threats covered by the design include malicious relay reordering/replay/truncation, LAN impostors, discovered-but-untrusted peers, stolen expired QR material, concurrent invitation use, revoked queued work, duplicate/conflicting IDs, stale status and unauthorized file/job requests. Relay denial of service and traffic analysis remain possible. A compromised unlocked endpoint can see its plaintext and act with that endpoint's authority. Keystore storage does not promise hardware backing or protect a compromised running process. Log only sanitized error codes; no raw TLS/app records, secrets, filenames, paths or notification previews.

See [protocol probe instructions](protocol-probes.md) for actual executed evidence and reproduction. None of these tests replaces independent review or a phone-plus-two-desktops acceptance run.


## Current file carrier amendment

The implementation uses standard pinned TLS for bounded file chunks instead of the proposed separate Tink blob channel. No separate cipher format is invented. `file.offer` authenticates immutable UUID, safe name, MIME, plaintext size, SHA-256 and expiry. `file.request` begins a download. Each `file.chunk` carries canonical base64url for at most 16 KiB, a contiguous byte offset and an EOF flag that must exactly match the offered size. `file.status` reports receiving/available/cancelled/failed and committed received bytes. Since Android 0.16.0 the phone keeps up to four upload chunks unacknowledged, always in order, and the desktop acknowledges each one. `file.cancel` stops a transfer. These fields stay inside end-to-end TLS over either carrier.

Receivers encrypt staging locally before committing cursor/offset, reject changed duplicate chunks, enforce 10 MiB/file and 50 MiB plaintext quota, and authenticate complete size/hash before marking available or exporting. Offers expire after at most 24 hours. No external blob SaaS is required. Public relay quotas can make large transfers impractical; prefer LAN. Tink interoperability fixtures remain historical probes, not the active transfer format.

## Wi-Fi-only transport, October 26, 2026

The user removed external network connections from scope. Both peers now use only the direct TCP carrier on the local network. The ntfy carrier, relay service, rate-limit handling and relay-to-LAN migration were deleted from Android and desktop. Statements above about ntfy, relay quotas and relay fallback are historical.

Wire bytes are unchanged, so existing pairings remain valid. The invitation still carries the schema-required `relay`, `pair_initiator_topic` and `pair_responder_topic` fields, and `session.ready` still returns long-term topics. No peer contacts them. Desktop writes the reserved, unresolvable origin `https://relay.invalid`. Desktop refuses to create a phone invitation without a private `lan_endpoint`, and Android rejects invitations whose `lan_endpoint` is null. A later protocol revision can drop these fields once both apps change together.

Android registers a `ConnectivityManager` callback for `TRANSPORT_WIFI` networks without `NET_CAPABILITY_INTERNET` and with the default non-VPN requirement. It binds each socket to one of those networks before connecting. Without Wi-Fi, no socket opens and the phone shows fixed guidance. Losing Wi-Fi closes the session; regaining it retries immediately. Sync runs every five seconds while connected. Pinned TLS, binding, trust and durable receipts are unchanged.

Android 17 blocks local network access by default for apps targeting SDK 37 or higher. Those apps need the runtime `ACCESS_LOCAL_NETWORK` permission. This app targets SDK 36 and holds `INTERNET`, which still receives the implicit grant. Request `ACCESS_LOCAL_NETWORK` before raising the target SDK. See [Android local network permission](https://developer.android.com/privacy/local-network-permission).

## Background parity extension, October 27, 2026

Both apps must be updated together. All additions are optional fields or new event types inside the same pinned TLS session; older peers reject unknown types before dispatch.

**Long-running background sync.** Polling requests (`sync.request`, `catalog.request`, `thread.history.request`, `thread.search.request`, `fleet.request`, `swarm.request`, `approval.request`) change no desktop state. Desktop keeps their replay records in a separate window of the most recent 2,048 per phone instead of the lifetime inbox, which a phone syncing every few seconds would otherwise fill after a few days. Mutating events keep lifetime deduplication. The phone likewise checks duplicate snapshot events (`sync`, `thread.history`, `catalog`, `thread.search`, `fleet`, `swarm`, `approval`) against its latest 512 instead of storing every ID. Ordering still requires increasing sequences.

**Thread resources.** `thread.history.snapshot` (rich requests) and `thread.snapshot` add optional `resources`: up to 32 `{id, name, kind, enabled}` entries, where `kind` is `builtin`, `skill` or `mcp`. IDs are UUIDv5 values derived on desktop; names are labels only. Sync entries carry the enabled IDs in `resource_ids`. `thread.context.update` adds optional `set_resources`; only when it is `true` does desktop treat `resource_ids` as the new enabled set. Older phones always resend their last list without the flag, so a stale list never turns tools off. The phone can only switch existing desktop resources on or off. It cannot add skill paths, MCP commands or URLs.

**Approvals.** `approval.request` (null thread) returns `approval.snapshot` with `remote_allowed` and up to 50 pending items: `approval_id`, `action_digest`, `source` (`workflow` or `swarm`), `title`, `summary`, `requested_at` and `instruction_required`. `approval.resolve` now allows a null thread and an optional `instruction` up to 2,000 characters. The digest is SHA-256 over the desktop's canonical description of the pending request; a changed request needs a fresh review. Workflow decisions use the desktop's existing workflow approval path with `decided_by` set to `phone`. Swarm requests map approve to proceed and deny to redirect, which requires an instruction.

**Swarm console.** `swarm.request` with `swarm_id` (UUID or null) returns `swarm.snapshot`, which now allows a null thread, `remote_allowed`, statuses `paused` and `idle`, and per-swarm `project_name` and `progress`. The requested swarm also includes up to 16 `agents` and the latest 20 board `messages`. `swarm.control` (`pause`, `resume`, `stop`) and `swarm.message` (1–4,000 characters) use the desktop swarm service. Swarms come from the open projects the desktop shared with that phone.

**Desktop opt-in.** Approvals and swarm controls require **Allow approvals and swarm controls from this phone** in desktop Paired devices. It is off by default, requires thread sync, and is reported as `sync.snapshot.connection.remote_control`. Without it, snapshots are empty and actions return `unauthorized`. This does not change enrollment capabilities, so turning it on or off needs no new pairing.

**Live progress and history cache.** While the open thread is running, the phone requests its history about once a second instead of every five seconds. Phone history is a cache of desktop history. When the local limit of 2,000 messages or 8 MiB is reached, the phone drops cached pages of the least recently loaded other threads instead of stopping. Queued and unresolved messages are never dropped, and reopening a thread reloads it.

## Desktop control extension, October 27, 2026

Android 0.7.0 and the matching desktop add the rest of the desktop app as an alternate phone UI. Both apps must be updated together. The phone sends these events only after a sync snapshot reports `connection.desktop_control`, so an older desktop never receives an unknown type.

**Events.** `desktop.read` and `desktop.action` carry `{op, params}` with a null thread and a UUID request ID. `op` comes from fixed lists in the schema; `params` is an object of at most 24 fields that the desktop validates per operation. `desktop.read` is a polling request and uses the recent read window; `desktop.action` keeps lifetime deduplication, and the desktop also passes the request ID to services that deduplicate (Rem commands, organization idempotency keys). `desktop.result` answers both with `{op, ok, part, parts, body}` and, on failure, `code` (`unauthorized`, `unavailable`, `invalid`, `conflict`, `not_found`) and a user-facing `detail`. `body` is JSON text split into at most 48 parts of 24,000 characters; the phone parses it only after every part arrived. A projection that would not fit keeps the newest items and reports how many earlier ones remain on desktop. Every successful body carries a `digest` of the view. A read may send it back as `params.known`; when the view is the same, the desktop answers `{"unchanged": true, "digest": …}` instead of resending it, so a polling screen costs little while nothing changes.

**Operations.** Reads: `overview`, `media.image` (see below), `rem.home`, `rem.task`, `rem.thread`, `organizations.list`, `organizations.read`, `settings.get`, `usage.overview`. Actions: Rem messages, task-thread instructions, task create/run/pause/resume/delete and run cancel/dismiss; organization pause/start, task create, comment, approve, review, reopen, cancel and asking an employee; starting a swarm run; and `settings.update`. Each calls the same desktop service the window uses, with its own validation, revisions and approval policies.

**No paths or new authority.** The phone names projects by its catalog IDs and records by desktop IDs; the desktop maps catalog IDs to its own folders. Results are projections without paths, grants, credentials or provider configuration. Files, the code editor, terminals, the browser, pairing, credentials, skill and MCP definitions, organization configuration and imports, and settings that widen agent permissions are not operations.

**Settings.** Desktop app settings live in the desktop window. The window publishes an allowlisted subset (appearance, general, Rem defaults, report format, editor and terminal display) through the authenticated local API. `settings.update` validates each key and value, including provider and model against the desktop catalog, and queues the change. The window applies it with its normal settings code and acknowledges it on its next sync. Agent tools, browser permissions, swarm access, execution mode, folders and keybindings stay desktop-only.

**Opt-in.** **Use Raticode from this phone** in desktop Paired devices is off by default and requires thread sync. It includes approvals and swarm controls. Without it, every operation returns `unauthorized`. It does not change enrollment capabilities, so turning it on or off needs no new pairing. Unpairing removes it.

## Tailscale route extension, October 30, 2026

The user asked for optional access away from home through their own Tailscale network. This adds a second carrier route, not a new protocol: the same TCP framing, pinned TLS 1.3 profile, ALPN, session binding, enrollment and trust revisions run over the Tailscale address. Pairing, desktop confirmation and grants are unchanged, and the route grants no authority.

`sync.request.payload.include_tailnet_endpoint` is an optional boolean. When it and `include_connection` are true, `sync.snapshot.payload.connection` adds `tailnet_endpoint`: `null`, or `{host, port}` for the address the desktop listens on in the user's tailnet. `null` means the desktop's Tailscale option is off. A desktop with the option on but not yet listening leaves the field out, and the phone keeps the address it has. Requests without the flag receive the earlier shape, so older phones keep working with an updated desktop. The phone sends the flag only while its **Connect through Tailscale** switch is on. An older desktop rejects the field and closes the session without answering, so the switch needs the matching desktop. Android removes queued flagged requests when the switch is turned off and before any reconnect with it off, then queues a clean request, so an older desktop syncs normally over Wi-Fi again.

Android accepts a Tailscale `host` only as an IP literal in `100.64.0.0/10` or `fd7a:115c:a1e0::/48`, and `lan_endpoint` keeps its private-address meaning. For compatibility with a desktop started with `RATICODE_DEVICE_HOST` set to its Tailscale IPv6 address, Android also accepts a Tailscale-range `lan_endpoint` in invitations and snapshots and routes it through Tailscale. Neither field may be a hostname, public, wildcard or multicast address. A reported Tailscale address never replaces the Wi-Fi address or an address the user entered. Android binds Tailscale sockets only to a VPN network whose routes carry the exact address and has no unbound or cellular fallback.

Fixtures `sync.request.tailnet.json` and `sync.snapshot.tailnet.json` match the desktop branch `tailscale-private-phone-access` byte for byte; `SHA256SUMS` was updated in both. Mobile negative cases reject a non-boolean flag, extra endpoint fields, port 0 and extra connection authority.

## Rem chat files and message images, October 30, 2026

Android 0.8.1 adds three things on top of the desktop control extension. All three need **Use Raticode from this phone**. The phone uses each one only after the desktop advertises it, so an older desktop keeps working and never receives an unknown operation.

**Rem chat file channel.** A `rem.home` result may include `files_thread`, a canonical UUID the desktop derives for that phone. It is not a shared thread and never appears in the thread list. The desktop accepts `file.offer`, `file.chunk`, `file.request`, `file.status` and `file.cancel` on it only from that phone and only while desktop control is on. Transfers use the normal limits: 10 MiB per file, end-to-end TLS, verified SHA-256.

**Attachments in Rem's chat.** The phone uploads each file on `files_thread`, then sends `rem.message` with `params.attachment_ids`, up to 8 UUIDs of files that finished uploading on that channel. The desktop copies each verified file into Rem's chat attachments and passes them to Rem like files attached in the desktop window. In the `rem.home` result, user messages may carry `attachments: [{file_id, name, size}]` for display. A queued Rem message keeps its files on the phone until the desktop receipt arrives.

**Files from Rem.** When the phone asks Rem's chat for a file, Rem names the file and the desktop offers it to that phone on `files_thread`. The desktop uses its normal scoped snapshot (no symlinks, only regular files of at most 10 MiB) and refuses anything else. Since November 1, 2026 the file may be anywhere the account running Raticode can read, not only in an open desktop project or the Second Brain folder, when Rem was given its exact path; credential folders, the coding agents' sign-ins (such as `~/.claude` and `~/.codex`), files named like tokens, credentials or keys, and Raticode's own data need the user's message to name the exact path, inside open folders too. Since November 2, 2026 a tapped file link in Rem's chat, in the reply's text or its Details, reaches the same files as Rem's reply files; links in work threads and shared threads still reach only the open folders. The desktop refuses a tapped link to one of those protected files with `unauthorized` and a sentence telling the user to ask Rem for it by its full path. No protocol change. Rem's reply in `rem.home` carries `files: [{file_id, name, size}]`. The phone downloads a file only when tapped. Tapping the file's name downloads it if needed and then opens it in another app (since November 2, 2026); the Download, Save and Open buttons remain. The name opens the file only while its row is on screen, so a file never opens later on its own. Pictures and videos are the exception (see below). Opening is local to the phone and adds no protocol fields. Offers expire after an hour; the phone then asks the user to request the file again.

**Message images.** `overview` and `rem.home` may include `media: true`. The phone then fetches web images in Markdown replies (`![alt](https://…)`) with the read `media.image` and `params.url` (http or https, at most 2,048 characters). The desktop fetches the image from a public address only, using the same pinned-address fetcher as its link previews, with no cookies or referrer, and answers `{url, mime, data}`. `mime` is JPEG, PNG, GIF or WebP and `data` is standard Base64 of at most 768 KiB. The phone decodes it at no more than 1,600 pixels on the longer side and keeps the 40 most recent images in memory only. The phone never contacts the image's site itself. Without `media`, a failed fetch or a larger image, the phone shows a card that opens the address in the browser only when tapped.

The schema adds `media.image` to the `desktop.read` and `desktop.result` operation lists in both repositories.

**Attachments from either device (November 4, 2026, Android 0.18.0).** `overview` and `rem.home` may include `attachment_files: true`. The phone then asks for a file attached to one of the user's messages in Rem's chat with the desktop action `rem.attachment` and `params: {message_id, file_id}`, where `file_id` is the attachment's `file_id` in `rem.home` (the phone's own upload ID for files it sent, the desktop's attachment ID for files attached in the window). No path crosses. The desktop looks the attachment up on that user message, refuses anything else with `not_found`, reads the stored copy from Rem's chat attachment folder through the scoped snapshot (no symlinks, regular files only), refuses files over 10 MiB with `unavailable`, and sends `file.offer` on `files_thread` under the name the file was attached with (the stored name if that isn't a name the phone accepts). The result is `{file_id, name, size}` for the new offer; the phone requests and verifies it like any download. It needs **Use Raticode from this phone**, like every desktop action. The schema adds `rem.attachment` to the `desktop.action` and `desktop.result` operation lists in both repositories. The phone sends it only after seeing the flag on the current connection and drops queued fetches before connecting, because an older desktop doesn't know the operation. This replaces the rule below that the phone never asks for an attachment's bytes.

**Attachment thumbnails (November 3, 2026, Android 0.15.0).** No protocol change. Rem chat and thread attachments show a thumbnail or file-type tile. The phone previews only bytes it already holds: its own uploads (matched by the `file_id`/attachment `id` it sent, which the desktop keeps) and finished downloads, read back through the same verified store. It never asks the desktop for an attachment's bytes, so files attached in the desktop window stay there and their tiles say so.

**Faster uploads and messages that wait for their files (November 3, 2026, Android 0.16.0).** No protocol change and no desktop change. The phone sends up to four `file.chunk` events before the first `file.status` comes back, in offset order on the one TLS stream, so the desktop's in-order check (`offset == received`) holds; after a reconnect the outbox resends them in order and the desktop answers already-committed chunks from its retransmission path. When several uploads are going, the one with the fewest bytes left goes first. The phone marks an upload cancelled locally in the same save that queues `file.cancel`; statuses that arrive later for it, including the desktop's `cancelled` status with `received_size: 0`, change nothing. A refused `file.offer` or `file.chunk` marks the upload failed on the phone. A Rem message sent while its files upload waits in the phone's encrypted journal and is queued as the usual `rem.message` with `attachment_ids` only once every file is `available`, so the desktop never sees a message whose files haven't arrived.

**Pictures and videos from Rem (November 1, 2026).** No protocol change. The desktop offers every file as `application/octet-stream`, so the phone recognizes pictures (`jpg`, `jpeg`, `png`, `gif`, `webp`, `bmp`, `heic`, `heif`) and videos (`mp4`, `m4v`, `webm`, `3gp`, `mkv`, `mov`) by name. For those files in a Rem reply, the phone sends the usual `file.request` once per file without a tap, so the preview is ready before the one-hour offer lapses; the transfer, size limit and SHA-256 check are unchanged. The inline preview is the picture at no more than 720 pixels, or a video's first frame and length, made in memory. Tapping opens a full-screen picture or an in-app player that plays from memory and zeroes the bytes on close. A tile says when the file is downloading, waiting for the desktop, gone or not previewable; an unplayable video offers another app, and Save and Open stay available. The desktop window shows the same files inline through its own media preview.

## Tapping links, October 31, 2026

Links in Rem's chat, shared threads and Rem work threads now render as links, including `[label](<path with spaces>)` destinations and plain `https://` addresses or absolute file paths written in text. Code spans stay text. Only `http`/`https` addresses (with a host and no user name) and file links act on a tap; `javascript:`, `intent:`, `mailto:`, `content:` and other schemes stay text.

**Web links** open in the phone's default browser. The view intent carries a `CATEGORY_APP_BROWSER` selector so an app that claims the site does not take it; without a default browser any app that views web pages is used, and with none the phone says so. The phone sends nothing to the desktop for a web link.

**File links** use the desktop action `files.link`, which runs no model. The phone sends it only after `overview` or `rem.home` reports `file_links: true`, so an older desktop never receives the unknown operation; the phone tells the user to update the desktop instead. Like every desktop action it needs **Use Raticode from this phone**. Params are `source` (`rem`, `rem_thread` or `thread`), `message_id` (the Rem chat message ID, the work-thread message ID, or the shared-thread history `source_id`; at most 200 characters), `thread_id` (omitted for `rem`) and `href`, the link exactly as CommonMark returns its destination, at most 2,048 characters. The phone never decodes, resolves or builds a path.

It emits `file.offer` and answers `{file_id, name, size, thread_id}`, where `thread_id` is `files_thread` for Rem's chat and work threads and the shared thread itself for `thread`. Refusals come back as `not_found`, `unauthorized`, `invalid` or `unavailable` with a sentence the phone shows.

The tap is the download request: while the link sheet is open, the phone sends `file.request` as soon as both the result and the offer are stored, in either order, and shows progress. Since November 1 the verified file then opens directly in the phone's viewer for its type, with no Save/Open question; Markdown and other text without a viewer opens as `text/plain`, and a file no app opens gets "Save instead". Opening is local to the phone and adds no protocol fields. Closing the sheet first leaves the offer for a later tap. Tapping the same link again reuses a file that is still offered, downloading or downloaded, and opens it again. The desktop documents its side in its `docs/mobile-desktop-parity.md`.

The schema adds `files.link` to the `desktop.action` and `desktop.result` operation lists and the fixture `desktop.action.files-link.json`; both are byte-identical with the desktop copy, and `SHA256SUMS` matches. Mobile negative cases reject the op as a read, on a thread, or under another name.

**Paths written as text, November 5, 2026.** A `rem.home` message may carry `file_mentions`: full paths of existing desktop files in its body and Details, exactly as written, at most 32. The phone ignores them on the user's own messages, keeps only `/` or `~/` paths up to 1,024 characters, and links each where a path can start, longest first. Paths with spaces link only through this list, since text alone can't show where they end. Inline code links when it is exactly a mention, a full path the phone can recognise, or an `http`, `https` or `file:` address; other code stays text. A tapped mention is sent as `href` unchanged, and the desktop reads it as written and applies every `files.link` check. Without the field (older desktops) the phone links only what it recognises on its own.

## Workflows on the phone, October 31, 2026

The user asked to see workflows on the phone: the list, each workflow's graph, its status and run history, with **Run**, **Stop** and **Resume**. Editing stays on the desktop. Mobile proposed this interface and the desktop adopted it with one addition, `expected_revision`. The desktop's `docs/mobile-desktop-parity.md` is the full field reference; this section records what the phone relies on.

New op names go in the existing `desktop.read`, `desktop.action` and `desktop.result` lists. There are no new event types. The same opt-in (**Use Raticode from this phone**) and refusal codes apply. `overview` reports `workflows: true`, and the phone sends workflow ops only after it sees that in the current session. An older desktop never receives an unknown op; the phone says to update the desktop and offers **Check again**.

- **`workflows.list`** `{}` returns `{workflows, earlier}`: up to 100 workflows from the desktop projects shared with this phone. Each has `workflow_id`, `name`, `description`, `project_name`, `status`, `updated_at` and `latest_run`.
- **`workflows.read`** `{workflow_id, run_id?}` returns the same fields plus:
  - `revision`, the saved source's fingerprint;
  - `nodes` (up to 200) and `edges` (up to 400, labeled `""`, `when`, `otherwise` or `needs`);
  - `runs` (the newest 20) and `earlier_runs`;
  - `run`, the detail of the chosen or newest run, with `error` and a status, times and one-line `detail` for each node;
  - `preview: {blocking, destructive, warnings}`;
  - `controls: {run, stop, resume}`, each `{allowed, reason}`.
- **`workflows.run`** `{workflow_id, expected_revision}` starts a run with saved inputs, using the same background start as the desktop's Run button. A workflow changed since the phone read it is refused with `conflict`. A required input without a default is refused with `invalid`. The request ID deduplicates retries.
- **`workflows.stop`** and **`workflows.resume`** take `{workflow_id, run_id}` and call the desktop's own stop and resume. Rattish runs can't be resumed. `controls.resume` is false with the desktop's sentence, and a sent resume gets `unavailable`.
- Actions answer `{workflow_id, run_id, status, message}` rather than a view. The phone shows `message` above the workflow and re-reads it at once.

Statuses are `idle`, `queued`, `running`, `waiting`, `stopping`, `succeeded`, `failed`, `stopped`, `interrupted` and `invalid`. Nodes can also be `pending` or `skipped`. The phone treats `queued`, `running`, `waiting` and `stopping` as active and shows any other value as finished text. It parses bodies leniently, because the body is opaque JSON text inside the schema.

**Phone behavior.** Every status is an icon and a word, never color alone. Run, Stop and Resume each ask for confirmation. The Run confirmation lists the preview's destructive actions and warnings. A disabled control states the desktop's reason. While offline the screen keeps the last view, says it may be stale and turns the controls off. The open workflow polls every two seconds while a run is active and every five seconds otherwise, using the `known` digest. Results stay in memory. On every reconnect, queued workflow reads are dropped from the outbox before it is resent: they are polling reads, and a downgraded desktop would close the session on the unknown op before reporting what it supports. Queued actions are kept. One limit remains: an action queued while offline still reaches a desktop that was downgraded in the meantime. A desktop with answered refusals (November 2) replies `unsupported` and the phone drops the action; an older one closes the session until the action is cleared.

The schema adds the five ops and the fixtures `desktop.read.workflows-read.json`, `desktop.action.workflows-run.json` and `desktop.action.workflows-stop.json`. They are byte-identical with desktop commit `d886e39` on `dev`, and `SHA256SUMS` matches.

## Task order and one-time task retention, November 1, 2026

The user asked for the phone's Rem task list to show the most recently run task first, for one-time tasks to leave the list once they finish while the chat keeps links to the task and its work thread, and for one-time tasks to be removed completely 30 days after their run finished. The desktop owns retention and cleanup; the phone deletes nothing. Mobile proposed the phone's side here and the desktop published the fields in its `docs/mobile-desktop-parity.md` ("Finished one-time tasks"). They are fields inside the opaque `desktop.result` body, so there are no new ops, events or schema changes, and the phone parses them leniently.

**Finished one-time task.** `schedule.kind` is `once`, nothing is scheduled (`next_occurrence_at` is empty), there is no active run, and the newest run has a `finished_at` and `succeeded`, was `cancelled`, or is a `blocked`, `failed` or `outcome_unknown` run the user dismissed (`acknowledged`). A run that still needs the user keeps the task listed. Running it again from the chat lists it until that run finishes. The desktop's `listed` on `rem.task` decides when present; the phone applies the same rule itself to an older desktop, which sends every task.

**Order.** Tasks with an active run come first, because they are running now. The rest follow by the desktop's `ran_at`, newest first: the latest of the active run's start and the newest run's start and finish, or the task's creation time if it never ran. Without `ran_at` (an older desktop) the phone uses the last run's `finished_at`, or its `created_at` when that is blank, and keeps tasks that never ran at the end in the desktop's order.

**Chat links.** A Rem message's `work` card opens the task with `rem.task {task_id}` and the work thread with `rem.thread {thread_id}`. It doesn't need the task in `rem.home` `tasks`, which leaves finished one-time tasks out. The card shows the task's live status while the desktop still sends the task, and only its title and links otherwise. When `work.task_available` is `false` the card says "Removed from your desktop" and doesn't open; when `work.thread_available` is `false` it drops **Open work thread**. An older desktop omits both, and an open of a removed task or thread shows the desktop's `not_found` sentence. The task screen of a finished one-time task explains why it left the list and, with `cleanup_at`, when the desktop removes it.

**Removal.** 30 days after the newest run finished, the desktop deletes the task, its runs and their work threads. Rem's conversation messages and their `work` objects stay. The phone keeps no copy of either; it shows what the desktop sends.

## Rich results in Rem's chat, November 1, 2026

The user asked for Rem's chat to show rich results and work the same on the phone and the desktop. Every field below is optional and only adds to a message: `body` stays the whole answer, with its report links. A phone that ignores the fields, or a desktop that doesn't send them, shows what it showed before.

**Messages** in `rem.home` can carry:

- `details`: Markdown under the short reply, at most 6,000 characters. It can hold tables, task lists, code and ```` ```rem-chart ```` blocks.
- `suggestions`: up to three replies the user might send. Tapping one sends it at once as an ordinary `rem.message` with no attachments, under the same connection and replying checks as Send; the draft in the message box is kept.
- `meta`: `{provider, model, seconds}` for how the reply was made.
- `result`: a finished task's card, `{title, type, state, checks: {passed, failed, total}, artifacts, sources, thread_id}`. Each artifact is `{name, title, kind, size, href}`; the desktop sends an artifact only when its path appears in the message body, so `href` is exactly what `files.link` accepts for that message. Each source is `{url, title, kind}`, where `kind` is `cited`, `read` or `found`.

**Runs** (`active_run`, `last_run`, `runs`) add `phase_label`, `waiting_reason` and `checks`. The phone shows the step label as the card's status, like the desktop.

**While Rem replies**, `rem.home` has `turn_label` (for example "Reading earlier messages") and `draft_reply`, the reply as it is written. Both are empty otherwise. TalkBack hears the finished message, not the draft.

**Previews.** `media.preview {url}` returns `{url, kind, title, description, site_name, image}`, where `image` is a small data URL or empty. The desktop fetches it with the link-preview fetcher, which reaches only public addresses and sends no cookies. `overview` and `rem.home` report `rich_results: true`; the phone sends `media.preview` only after seeing it. The schema adds `media.preview` to the `desktop.read` and `desktop.result` operation lists, with the fixture `desktop.read.media-preview.json`. Install the desktop build first.

**Which checks failed.** On a task's screen the phone lists the checks of the run being fixed, or else of the last run: **Failed** and **Unresolved** by name with the reviewer's reason (long reasons fold behind Show more), then Not checked, with Passed folded below. It reads them from `criteria` on `rem.task`'s `active_run` and `last_run` (`{id, description, result, evidence}`). A desktop that doesn't send `criteria` gets the count line only. See the desktop's `docs/mobile-desktop-parity.md`.

**Action chips.** Messages carry `kind: "task_update"` for task updates and runs carry `review_retryable`. Under the newest finished-task update the phone shows Open report (the card's first report, through `files.link`), Retry review and Run again, by the same rules as the desktop. They come from the task record only, never from Rem's text. Run again sends `rem.task.run`; Retry review sends `rem.run.retry_review {run_id}`, only to a desktop reporting `review_retry: true`. The desktop runs its own `retry_review`, which refuses a run without an interrupted review or whose task changed.

**Tasks that wait for other tasks (November 10, 2026).** A one-time Rem task can name prerequisite tasks in `after`; it has no run until they all succeed. While it waits, `rem.home` and `rem.task` carry `dependency {state, reason, prerequisites[]}` on the task: `state` is `waiting`, `held` or `met`, `reason` is the sentence to show, and each prerequisite has `task_id`, `title`, `state`, `reason`, `run_id`, `run_state` and `retryable`. The phone shows `waiting` under Coming up and `held` under Needs you, as `RemTaskStatus` does on the desktop. **Retry “…”** sends `rem.task.run` for a `retryable` prerequisite, and **Start now** sends `rem.task.run` for the waiting task, which releases its condition. Both are existing operations, so no capability flag is needed. A hold is announced once by a `task_update` whose `work` has an empty `run_id` and `state: "held"`; it alerts as **A task needs you**, and the phone keys it by task until the task's first run card arrives (`RemRich.liveWork`). A user message Rem received because a queued request's prerequisites succeeded carries `queued_after`, a list of their titles. An older desktop sends none of these fields, and the phone shows its tasks as before. A new desktop with an older phone shows a waiting task as a one-time task that hasn't run, whose Run now starts it early.

**Reply deltas.** With a desktop reporting `draft_deltas: true`, the phone reads `rem.draft {since}` about every 0.7 s while Rem replies and gets `{replying, turn_label, start, text, length, reset, attempt}`: only the text after `since`, or all of it with `reset` when the draft started over. `attempt` numbers Rem's model calls within one reply; a repair or retry starts a new attempt from nothing. The phone sends back `attempt` with its next read (`rem.draft {since, attempt}`), so a read it resends after a lost answer still gets the whole new text instead of the new text glued onto the old. These are reads, not pushed events: every desktop-to-phone event is stored durably in the desktop's per-phone outbox (at most 10,000 events) and recorded in the phone's encrypted journal, so pushing each fragment would fill both with throwaway text. **Memory.** A desktop reporting `memories: true` (in `overview` and `rem.home`) adds a **Memory** button to the Rem chat header. It opens `rem.memories`, which returns `{mode, memories: [{id, text, created_at, edited_at, added_by_user}]}`; `mode` is `on`, `paused` or `off`. The screen sends `rem.memory.add {text}`, `rem.memory.edit {memory_id, text}`, `rem.memory.forget {memory_id}` and `rem.memory.mode {mode}`; each answers with the same list. A Rem message that saved, changed or forgot memories carries `memory: {saved, updated, forgotten, refused, undone}`, where each entry is `{id, text, removed}` and `removed` means the user later forgot it. The phone shows those lines under the reply with **Undo**, which sends `rem.memory.undo {message_id}`. The desktop applies every change, refuses text that looks like a password, key or token, and treats a repeated forget or undo as done. The schema adds these operations to the `desktop.read`, `desktop.action` and `desktop.result` lists, with the fixtures `desktop.read.rem-memories.json` and `desktop.action.rem-memory-forget.json`.

## Answered refusals, November 2, 2026

The phone keeps each request in its queue until an event with that request ID arrives, and resends the whole queue after every sign-in. A desktop that refused a request by closing the session therefore cut the phone off on every reconnect, until Raticode Mobile was reinstalled. A download whose desktop offer expired after an hour while the phone slept did this, and so could a conflict, missing thread access, a full quota or an unknown request from a newer phone.

The desktop now answers a refused request with an ordinary `error` event (`code`, `retryable: false`, `detail`) carrying its request ID. It adds no event, field or capability, so phones already in use recover once the desktop is updated: the phone applies the error, removes the request from its queue and shows the detail. Where it can, the desktop records the refused event ID first, so a resend gets the same answer and never runs. Event ID and sequence conflicts and unsupported requests can't be recorded; each resend is answered again. Lost trust still ends the session, and so does a full desktop outbox, which the phone's next acknowledging sync frees. The desktop logs only the fixed refusal code.

The phone gives every request a new random ID and the next number in its journal's `sequence`, and the desktop refuses a new ID with a number it already recorded (`sequence_conflict`, "The desktop already has a different request with this number. Send it again."). Android 0.17.4 fixes a phone bug that caused that refusal. Applying a received event works on a copy of the journal and saves the copy at the end. When the event was a `media.preview` answer and more source previews were waiting, the phone queued and sent the next preview from the live journal part-way through, and the copy then overwrote it. That put the number back by one and dropped the sent preview from the queue, so the phone's next request (usually a poll, sometimes a Rem message) reused the number and was refused. A Rem result with more than three source cards set it off.

`LiveClient` now applies each event inside `CommitGate.during`. Any request queued while an event is being applied waits until the copy is saved, then gets its number from the saved journal, in order, even if applying failed. A refused `desktop.read` or `desktop.action` now ends the same way as a failed `desktop.result`: its preview or image slot is freed, a refused Rem message comes back with Try again and Edit, and only actions show the "Desktop request" dialog. A refused background read shows its reason on that screen until the next read succeeds. Other refused requests still show the dialog. `LiveRequestNumbersTest` reproduces the refusal on the old code against the real desktop device code.

## Phone action cards, November 2, 2026

Rem can suggest a phone action under its reply to a request the phone sent: a timer, an alarm, a calendar draft, a place or directions on the map, a number in the dialer, or a text or email draft. No event, operation or schema change. `rem.home` reports `phone_actions: true`, and a Rem message may carry `phone_actions`, at most three objects inside the opaque `desktop.result` body. The phone sends nothing new, so an older desktop is unaffected and an older phone ignores the field.

**Who gets them.** The desktop marks a message that arrived as `rem.message` from a phone (`source: "phone"`, set only by the device path, never by the local API). Only for such a request does Rem's prompt describe phone actions, and Rem's reply stores the checked actions with `reply_to` set to the request ID. `rem.home` includes them only for the phone whose `device_rem_requests` row matches that ID, the same rule as files from Rem, and checks them again on the way out. Replies to desktop requests, task updates and other phones never carry them.

**Allowed types and fields.** Unknown types or fields, wrong JSON types, control or invisible formatting characters, and line breaks outside `body` and `notes` are refused; the phone counts refused items and says so without showing them.

| `type` | Fields | Phone opens |
|---|---|---|
| `timer` | `seconds` 1–86,400, `label`? ≤60 | `ACTION_SET_TIMER`, `EXTRA_SKIP_UI` false |
| `alarm` | `hour` 0–23, `minute` 0–59, `label`? ≤60, `days`? unique `mon`…`sun` | `ACTION_SET_ALARM`, `EXTRA_SKIP_UI` false |
| `calendar_event` | `title` ≤200, `start` (ISO date-time, offset optional, or a date for all day), `end`?, `all_day`?, `location`? ≤200, `notes`? ≤1,000 | `ACTION_INSERT` on `content://com.android.calendar/events`; no attendees |
| `map` | `query` ≤200, `directions`? | `geo:0,0?q=…`, or a Google Maps directions URL |
| `dial` | `number`: digits, optional leading `+`, spaces, `().-`; 3–15 digits; or `recipient` (see below), never both | `ACTION_DIAL` (never `ACTION_CALL`) |
| `sms_draft` | `to`? (one number, same rule) or `recipient`?, never both; `body`? ≤1,000; at least one of the three | `ACTION_SENDTO` `smsto:` with `sms_body` |
| `email_draft` | `to`? (one plain address), `subject`? ≤200, `body`? ≤2,000; one of them | `ACTION_SENDTO` `mailto:` |

A calendar event ends after it starts and lasts at most 14 days; without `end` it lasts an hour. A time without an offset is read in the phone's time zone and shown on the card. Numbers can't contain `*`, `#`, `,`, `;` or letters, so a card can't fill the dialer with a service code or add pauses. Queries and numbers are percent-encoded, so they can't add URI parts. The desktop (`src/gofer/ui/rem_phone_actions.py`) and the phone (`live/PhoneActions.kt`) apply the same rules.

**Opening.** Each card shows everything the other app will receive and a button naming it (**Start timer**, **Set alarm**, **Open dialer** and so on). Nothing opens without that tap. If the lock screen is showing, the phone asks Android to dismiss it (`requestDismissKeyguard`) and opens the app only on success. In voice mode the cards appear only with a visible reply; the overlay hands the tap to `VoiceActivity`, which unlocks first. Drafts stop at the other app's screen: the user saves the event, presses Call or Send there. Clock apps act on the tap itself (Google Clock starts the timer and saves the alarm as it opens), so those cards say so. Voice mode's automatic send never applies to cards. The phone doesn't report taps to the desktop.

**Audit fixes, November 4, 2026 (Android 0.17.3).** No protocol change. The phone disables a tapped card's button for two seconds; opens a card from voice mode in the other app's own task and then closes voice mode; shows in the voice panel the cards from every Rem message answering the request, up to the next user message (a reply that also started a task carries its cards on a separate "Ready on your phone." message); sends calendar drafts with the `vnd.android.cursor.dir/event` type; falls back from `geo:` to `https://www.google.com/maps/search/?api=1&query=…`; writes alarm times in the phone's format; and marks events already over. The desktop adds a sentence to Rem's reply when it drops cards the model returned (`missing_cards_note`), since the reply is written before the cards are checked.

**Calling and texting people by name, November 5, 2026 (Android 0.20.0).** `dial` and `sms_draft` accept `recipient`: the user's own words for a person ("my brother", "Baby Bro", "Mom"), at most 60 characters, no line breaks or hidden characters, and fewer than three digits so a number can't travel as a name. The desktop prompt tells Rem to use it when the user names a person instead of giving a number. The number is found on the phone and never reaches the desktop or the model:

- **Saved people.** The phone keeps a list of contacts the user picked with Android's contact picker (`ACTION_PICK` with `Phone.CONTENT_TYPE`, which needs no contacts permission and returns one entry the user chose). Each entry holds the contact's name, the one number chosen, its label, the contact's lookup key and the words the user calls them. It is encrypted with its own Android Keystore key in no-backup storage (`PeopleStore`), is never synced, logged or sent, and survives resetting pairing.
- **Matching.** Words are lowercased, a leading "my" or "the", possessive "'s" and punctuation dropped, and only exact matches with a saved name or the contact's own name count, so a misheard name finds nobody rather than someone else (`PhonePeople`).
- **The card.** One match shows "Text Baby Bro · Mobile" with the number's last four digits and opens that number. Several matches (two brothers, or one person's mobile and work numbers) list up to five, and the user taps one. No match shows **Choose contact** with **Remember as "…"** ticked; a pick that is kept answers to those words from then on, and an unticked one is used for that card only, in memory. **Someone else** picks again for this card without changing what is saved. Backing out of the picker says "No contact chosen."; a number with `*`, `#`, pauses, extensions or letters is refused by the same rule as Rem's numbers. Opening still needs a tap and an unlocked phone, and the dialer or messaging app still waits for the user to press Call or Send. The phone reports nothing about the pick to the desktop.
- **Voice mode.** The overlay hands **Choose contact** to `VoiceActivity` (`STEP_PICK_CONTACT`), which unlocks, holds the turn while the picker is open, and shows the card again with the person chosen. On a locked phone showing replies, a card that names a person reads "Text a saved contact" and shows no buttons until the phone is unlocked.
- **Managing.** More › **People Rem can reach** lists the saved people, adds someone from contacts, adds or removes names, changes the number (picker again, names kept) and removes one person or everyone.
- **Compatibility.** No event, operation or schema change. An older phone refuses a card with `recipient` as an unknown field and says Rem suggested a card it doesn't allow; update the phone with the desktop.

## Rem chat notifications, November 2, 2026

Rem's chat alerts use a new read, `rem.notices`, on the existing encrypted link; nothing is pushed. With **Rem chat notifications** turned on, Android notifications allowed and the desktop's `overview` reporting `rem_notices: true` (it needs **Use Raticode from this phone**), the phone sends `desktop.read` `rem.notices {after}` about every 10 seconds while it is connected: with the app open, while voice mode is open, or with background sync on. `after` is the desktop's message position (`seq` in Rem's message table, which never changes once a message is stored). The answer is `{cursor, notices, skipped, more}`:

- `notices` holds at most 8 of Rem's messages after `after`, oldest first, each `{id, kind, body, created_at, title, needs_user}`, with `kind` `reply` or `task_update`; `skipped` counts older ones left out, and `more` means messages remain after `cursor`, so the phone reads again at once.
- The desktop picks which messages count. A Rem message counts when the latest question before it came from this phone (its ID is in `device_rem_requests` for that phone). A task update counts when the task's `delegation_context.source_message_id` is one of this phone's requests. Answers to questions typed on the desktop, and updates for tasks started there, never alert the phone.
- Without `after`, or with an `after` past the end of a reset conversation, the answer is only the current `cursor`. A non-integer, boolean, negative or too-large `after` is refused as `invalid`.

The phone keeps `cursor` in its encrypted journal, saved in the same write as the received event, so messages that arrived while it was offline alert once it reconnects (up to 8, plus an "earlier messages" count). Turning alerts on drops the saved position, so the first read only sets it and older messages never alert. Reads queued in an earlier session are dropped before reconnecting, as for workflows, because an older desktop would refuse the unknown op; the phone asks again only after the new desktop's `overview` says it may. Nothing about the alerts is stored on the desktop.

**What an alert shows.** The phone decides. By default an alert says only "New message", "Task update" or "A task needs you": no reply text and no task name. **Show Rem's words**, a separate switch that starts off, shows Rem's reply as one plain line of up to 600 characters. Either way the lock screen gets a public version that says only "New message from Rem". Alerts use the `rem-messages` channel (high importance), Android's conversation style with Rem as the sender, and a long-lived `rem-chat` shortcut, so Android files them under Conversations. Nothing is alerted while Rem's chat or voice mode is on screen, and opening Rem's chat clears the alert.

**Replying.** The alert's Reply action uses `setAuthenticationRequired(true)`, so on Android 12 and newer a locked phone asks for unlock before the reply leaves the shade; the receiver (`RemReplyReceiver`, not exported) also refuses while `KeyguardManager.isDeviceLocked`. Generated smart replies are off. A reply is an ordinary `desktop.action` `rem.message` with its own request ID, queued in the encrypted outbox like one typed in Rem's chat, so it survives a lost connection and is sent on the next one. The receiver holds the broadcast open (`goAsync`, at most 8 seconds) until the reply is saved in the outbox, so Android can't end the process first. With the app closed and background sync off, the phone connects for two minutes after a reply, so the reply and a quick answer can get through, then disconnects again; leaving the app, voice mode or the share sheet during those two minutes doesn't cut that connection short. A desktop refusal (for example, phone control turned off) shows in the alert as "Not sent: …" and in Rem's chat with **Try again** and **Edit**. The alert never repeats the reply's text unless **Show Rem's words** is on.

The schema adds `rem.notices` to the `desktop.read` and `desktop.result` lists, with fixture `desktop.read.rem-notices.json`; the schema, fixture and `SHA256SUMS` are byte-identical with the desktop copy.

**Tests.** `RemAlertRules` holds the decisions in plain Kotlin, and `RemAlertRulesTest` covers them without an emulator: what a reply does (alerts off, Android older than 10, locked, empty, too long, sent), which settings problem shows first (no permission, app blocked, Rem category blocked, desktop control off, desktop too old), that both switches start off, that turning alerts or Rem's words off removes the alert, that turning alerts on starts from the current message once, and that alert lines carry no reply text or task name without the opt-in while the lock-screen text is fixed. Applying these with Android's APIs (`VISIBILITY_PRIVATE` with the public version, `setAuthenticationRequired`, the unlock prompt, the permission dialog, the conversation section) needs an emulator or phone and hasn't been run. The desktop leaves legacy duplicate "Started …" notices out of `rem.notices`, as Rem's chat does.

## Alerts for anything that needs you, November 9, 2026

Rem chat notifications can also cover work this phone didn't start. **Rem chat notifications** stays the master switch and still covers replies and updates for this phone's own requests. Under it, three new switches each start off: **A task needs you**, **A task finishes** and **Proposals are waiting**. **Quiet hours** sits beside them. There is still no push service, so these alerts need the app open or background sync on.

**Phone to desktop.** The phone adds fields to `rem.notices` only when the desktop's `overview` reports `rem_notices_filter: true` and at least one switch is on. Otherwise it sends the existing request, byte for byte. Support is asked again on every connection, reads queued in an earlier session are dropped before reconnecting (`dropQueuedNoticeReads`), and a queued read carrying the filter is dropped in the same journal save if a desktop stops advertising it (`dropQueuedNoticeFilters`).

`params` gains two optional fields:

- `include`: a non-empty array of any of `"needs_you"`, `"finished"`, `"proposals"`, naming the switches that are on.
- `mark`: the opaque string from the desktop's previous answer. Absent on the first filtered read.

**Desktop to phone.** With `include`, the desktop answers as today and adds:

- `mark`: an opaque string of at most 256 characters holding the desktop's position in sources other than Rem's message table, such as the self-work report and organization events. Without a `mark` in the request it only sets the position, so turning a switch on never reports old proposals or organization items.
- On each notice that counts because of the filter, `reason`: `needs_you`, `finished` or `proposals`. A message that counts because this phone asked for it keeps the existing rule and has no `reason`, so it alerts with only the master switch on.
- `kind` may also be `organization` (any task that isn't in Rem's chat, which includes self-work tickets as well as organization tasks) or `proposals` (one batch).

**What the desktop decides.** Everything about what counts stays on the desktop:

- `needs_you`: tasks from any source that are waiting on the user, including desktop-started Rem tasks, self-work and organization tasks. Rem's own task updates already carry `work.needs_user`; self-work tickets report through the self-work report instead of Rem's chat.
- `finished`: tasks from any source reaching a finished state.
- `proposals`: at most one notice per self-work round that left proposals waiting, with an `id` that stays the same for that round. Rounds are the desktop's to define.

Filtered notices use the same `{id, kind, body, created_at, title, needs_user}` shape and the same limit of 8 plus `skipped`. Validate `include` against the three names and answer `invalid` otherwise.

**What the phone does with the answer.** The phone saves `cursor`, `mark` and the remembered self-work round IDs in the same journal write as the received event. It drops a notice whose `reason` is a switch that is now off, which covers a read already on its way when the switch changed. It also remembers the last 16 round IDs, so one round alerts once even if a later answer names it again. While Rem's chat or voice mode is on screen it holds back only `reply` and `task_update`, because `proposals` and `organization` items aren't in that chat. An answer with no `mark` clears the saved one, so a switch turned on later starts from the desktop's current place. Turning the master switch on clears the cursor, the mark and the round IDs. Turning on one of the three alert switches keeps the cursor, so replies to this phone's own requests from an offline gap aren't lost. That switch stays quiet instead until a complete read has come back carrying it, so what it finds from before never alerts.

**What an alert says.** Without **Show Rem's words**, alerts say only "A task needs you", "A task finished" or "Proposals are waiting", never a task name or the desktop's text. With it on, the alert shows the notice's `body` as one plain line, falling back to those words when the body is blank. The lock screen's public version is unchanged: "New message from Rem".

**Quiet hours.** These are local wall-clock hours kept on the phone, defaulting to 22:00 to 07:00 when turned on, and they may span midnight. A start equal to the end has no effect, and the settings say so. During quiet hours alerts are still posted, using `setSilent` plus an explicit `rem-quiet` notification group, because Android mutes a silent alert only when it belongs to a group. They make no sound and show no pop-up but wait in the notification shade. Nothing is held back or lost, and the desktop is never told. Quiet hours cover every Rem chat alert, including replies to this phone's own requests.

**Compatibility.** `params` is an open object in `event.schema.json`, so neither the schema nor its `SHA256SUMS` changes. `mark` and `reason` are read leniently: an unknown `reason` counts as none, and a `mark` over 256 characters counts as absent because an opaque value can't be shortened.

**Status.** The phone half is implemented, and the matching desktop change to `rem.notices` is on desktop `dev` at `0d921e9`: `overview` reports `rem_notices_filter` and the read takes `include` and `mark`. A desktop from before that commit doesn't advertise `rem_notices_filter`, so on it the new switches do nothing and the settings say to update Raticode on the computer. The rules the desktop settled on for each source are in its `docs/mobile-desktop-parity.md`, and `docs/desktop-handoff.md` lists where they differ from the brief.

**Tests.** `RemAlertRulesTest` and `RemNoticesTest` cover the switches, quiet hours, the request an older desktop gets, parsing, per-round batching, what stays generic and what is held back while Rem's chat is open. `LiveRemAlertsTest` runs the real client, settings and notification code on an emulator against the scripted stand-in in `live-device-fixture.py`. The desktop's own tests cover its filter without a phone. The phone hasn't been tested against the desktop's real filter on an emulator or a real phone; `docs/desktop-handoff.md` section 10 has the steps.

## Wake the computer, November 9, 2026

**Opt-in.** A new per-phone setting in desktop Paired devices, off by default and shown only while **Use Raticode from this phone** is on. The phone's button stays hidden until it is on.

**Wire.** `overview` adds `wake_mac`, a string such as `aa:bb:cc:dd:ee:ff`, only while the setting is on. The desktop leaves the key out entirely while it is off and never sends `null`. The phone treats a missing key, `null` or a malformed value alike, as off. Older phones ignore unknown `overview` fields and older desktops never send it, so `params` and `event.schema.json` don't change and there is no capability flag. The phone never sends a request field for this, so it can't block sync with an older desktop.

**Desktop choice of address.** Report the hardware address of the physical interface that holds the address in `lan_endpoint`. The exact format, the cases that leave the key out, the selection steps and the expected tests are in [`desktop-handoff.md`](desktop-handoff.md#wake-the-computer).

**Phone behavior.** See "Wake the computer" in `docs/architecture.md`. A value that is not six lowercase or uppercase colon-separated hex pairs, or that is all zeroes or has the multicast bit set, counts as absent and removes any saved address.

**Status.** Both halves are implemented: the desktop half landed in desktop commit `6342c4f` (**Let this phone wake this computer**, Linux only). It has not been tried with a real phone waking a sleeping computer. See `docs/desktop-handoff.md`.

**Tests.** `WakeOnLanTest` covers the packet bytes, one real UDP datagram on loopback, address validation, saving and clearing, the subnet check, Tailscale refusal, the broadcast calculation and the button's wording.

## Screen context for voice mode, November 2, 2026

With **Let Rem read your screen** turned on (Voice assistant settings, off by default, with a consent dialog), opening Rem over another app with the power button or assist gesture lets Rem answer questions about that app's screen.

- **Capture.** `RemVoiceInteractionService` requests Android's assist data only while the setting is on (`setDisabledShowContext` keeps `SHOW_WITH_ASSIST` disabled otherwise) and never requests screenshots. `RemVoiceSession.onHandleAssist` reads the focused app's `AssistStructure`: visible text, or a content description where a view has no text, plus the web domain. It skips views the app blocks from assistants (`isAssistBlocked`), password and PIN fields, anything captured while the keyguard is showing, and an app whose window is secure (Android passes no structure). `ScreenText.clean` drops hidden characters and repeated lines and keeps at most 6,000 characters.
- **Scope.** The text stays in `VoiceController` memory. Since November 4 nothing is shown about it and nothing is shared until the user taps the share-screen button in the panel's bottom row, which is off every time Rem opens and lit while on ("Sharing the screen from Chrome" under the words). A screen that can't be read gives its one-line reason only when the button is tapped. It goes only with the next message, if it is under five minutes old, and is forgotten when that message is queued or the turn ends. A reopening without assist data (tile, shortcut, sharing off) clears it. Sending still needs an unlock.
- **Wire.** `rem.home` reports `screen_context: true` on a desktop that accepts it. Only then does `rem.message` carry `params.screen = {app, text}`; desktop action params are an open object, so the event schema is unchanged. The request waits in the encrypted outbox only until the desktop answers, and the desktop records only the event's digest.
- **Desktop.** `clean_screen` (`gofer.ui.rem_screen`) checks it (8,000 characters at most, hidden characters removed). `RemHome` keeps it in memory for that one reply and stores only `screen_app` on the message, so later turns and Rem's history never contain the text. The prompt marks it untrusted page content. Since November 4, work the user's own words ask for goes ahead: if the reply that saw the screen proposes any work, Rem decides again from the same prompt without the screen and keeps that decision, so only the user's words and the records can start, change, remember or send anything. A reply that proposes nothing keeps only its answer. Before, every action was dropped and a request like "fix the 4 AM task" was refused. The AI provider Rem uses reads the text; its own records may keep it, as the consent dialog says.
- **Limits.** Text only: pictures, video and canvas-drawn apps give Rem little or nothing. Android's **Use text from screen** for the digital assistant must be on. Android 17 adds `SHOW_WITH_ASSIST_STRUCTURE_SCREEN_CONTENT`, so how much screen content the structure carries may change there.

## Replies to a message, November 3, 2026

Any message in Rem's chat, Rem's or the user's, can be replied to from its ⋯ menu.

- **Wire.** `rem.home` reports `replies: true` on a desktop that accepts them; only then does the phone offer Reply, because an older desktop would drop the link without saying so. `rem.message` then carries `params.refers_to`, the ID of the message replied to (at most 128 characters). The message being replied to is kept with the draft across rotation.

## Voice tidying, November 3, 2026

**Tidy voice messages** is a desktop setting (Settings > Rem, off by default). With it on, dictated words go to a fast model on the desktop before the user sees them, and the phone shows them only when they come back, in an editable box. There is no undo; the user edits the words directly.

- **Wire.** `overview` and `rem.home` report `voice_tidy: true` while the setting is on. Only then does the phone send `desktop.action` `rem.tidy {text}` (at most 4,000 characters), because an older desktop would refuse the unknown op and close the session. The desktop answers twice under the same request ID: first `{pending: true}` at once, which takes the event out of the phone's encrypted outbox, then `{text, tidied, reason, model, ms}` when the model is done. The model runs on its own thread, off the device lock and the connection's loop. A setting turned off between reads answers once with `{text, tidied: false, reason}`. Blank or overlong text is refused as `invalid`. The schema adds `rem.tidy` to the `desktop.action` and `desktop.result` lists, with the fixture `desktop.action.rem-tidy.json`; the schema, fixture and `SHA256SUMS` are byte-identical with the desktop copy.
- **Failures keep the words.** The phone waits at most 25 seconds (the desktop gives the model 15). When tidying is off, the phone isn't connected, the desktop refuses, the model is unavailable or too slow, or the desktop's checks reject the answer (empty, notes added, a number changed, length changed too much), the phone shows the words as heard with "Not tidied: …" and the reason. Words that weren't tidied are never sent unseen: after Send they open in the box for the user to check. A late answer finds nobody waiting and is dropped.
- **What is hidden.** In voice mode, new words stay off the screen while listening (`VoiceState.Listening.hidden`); words already in the box from before **Keep talking** still show, and only the new words are tidied, so earlier edits stay. While the user keeps talking, the phone tidies everything said so far once at least 15 new words have built up and at least 5 seconds have passed since the last round (version 0.19.2; no upper limit, so a fast talker's round carries more words and a slow talker isn't cut up). A pause of two seconds or more, or pausing the microphone, tidies whatever is left even below both thresholds. Rounds happen while it keeps listening, and shows the answer in place of the hidden words (`Listening.preview`); words said after that stay hidden until the next pause re-tidies the whole message. One request is out at a time, and words said while it is out wait for its answer. A failed round changes nothing on screen, and still counts toward the next one, so a failing desktop isn't asked at every word. They never go through the paired desktop or its Wi-Fi/Tailscale link, and Raticode doesn't read them except a selection the user sends with Ask Rem. Pages may navigate to web addresses up to Chromium's own limit of 2 MiB; the 2,048-character limit applies only to addresses sent to or from the computer, bookmarks, history and the saved tab list. (Until November 7, 2026 pages were held to 2,048 characters too. That is the likeliest cause of a refusal seen on a phone after Google's sign-in, but the refused address wasn't measured. The user's screenshot shows the address bar already on `accounts.youtube.com/accounts/…`, so that hand-off page had started and a later navigation was refused, with "can't open this kind of address". A tab on a longer address is saved without its query, which on sign-in pages holds one-time tokens, so after a restart it reopens without them; such pages aren't added to history or bookmarks and can't be sent to the computer. Links to other apps (`mailto:`, `tel:`, `intent:`, store links and the like) open only after a tap on the page and the user's confirmation; `intent:` links lose any named component, selector and URI grants first, and an `https` `browser_fallback_url` is used when no app takes one. Certificate errors are never bypassed: the page shows why and **Back to safety**. Location, MIDI and protected-media requests are refused with a note. The app holds camera and microphone permission for its own features, so a page gets them only when the user says yes to a prompt naming the site, each time (changed November 8, 2026; they were refused outright before). Page dialogs (alert, confirm, prompt, leave page) come only from the tab on screen, one at a time, and name the site. HTTP sign-in prompts are answered in a dialog and never saved. File inputs open Android's picker, which grants only the chosen files. Downloads ask first, name the size and site, warn twice about apps, installers and scripts, and go through Android's download manager to Downloads (Android 10 and newer) with the page's cookies; files a page builds itself (`blob:`/`data:` links on https pages, such as a chat Open WebUI exports) are read in the page instead, up to 25 MB, and saved to Downloads after the same question (`PageFiles.kt`). The app still has no JavaScript bridge: a script that runs before each page keeps the page's last 20 blobs for a minute, so a file whose address the page revokes right after the click can still be read, and the app collects the encoded file by asking the page for it in pieces. A blob made by a frame from another site can't be read this way, and the note says the file couldn't be read. Gecko tabs save these files through Gecko itself: Gecko asks before following every link, downloads included, so a Gecko tab follows a page's link to a `blob:` its own origin made, or to a `data:` address, and otherwise keeps refusing those addresses (`PageFiles.geckoMayLoad`). At most three tabs keep a live page; others sleep with their back/forward list in memory and reload when shown, and pages keep running while Raticode is in front, on any of its pages, so a tab's music goes on while the user is in Rem or Threads. A tab whose page crashed stays closed until Reload or a tap on it.

- **Rules.** `GeckoRuntimeSettings.HTTPS_ONLY` (Gecko has its own network stack, so the app's cleartext ban doesn't cover it). Main-frame navigation goes through `BrowserRules.classify`, the same rule as the other browser. Certificate errors, HTTPS-only failures and Safe Browsing blocks show Raticode's own error page with no way past (`onLoadError`). The camera and microphone need a yes each time; location and notifications are refused. `about:config` and remote debugging are off. Pop-ups without a tap are blocked, and other apps can't be opened from pages.
- **Extensions.** `WebExtensionController` installs from `https://addons.mozilla.org/…​.xpi` only (`GeckoRules.installable`), and Gecko refuses unsigned files. Raticode shows the requested permissions and sites first (`onInstallPromptRequest`). The catalogue search asks Mozilla's API and sends only the search words. Browser-action popups open in a sheet; extension tabs and options pages open as tabs.
- **Sound** uses Gecko's media sessions and shares `BrowserPlaybackService`.
- **Build.** GeckoView needs `compileSdk` 37 (the app still targets 36), AGP 9.1 and Gradle 9.3.1. `androidx.lifecycle` is held at the app's 2.10.0 because the instrumentation tests use a method 2.11 dropped; GeckoView's tests pass with it. The APK carries `arm64-v8a` and `x86_64` only, so 32-bit-only phones can no longer install it, and the debug APK is 194 MB (it was 15 MB). GeckoView also adds `WAKE_LOCK` and `MODIFY_AUDIO_SETTINGS`, listed in `scripts/release-policy.json`. GeckoView's version must follow Firefox releases, as it carries the engine's security fixes.

**Extension results** (real extensions from addons.mozilla.org, on the emulator's GeckoView 159): Dark Reader 4.9.135 installs and works (light pixels on a page went from 96% to 6%, and a fresh load with it off drew normally); uBlock Origin 1.75.4 installs and its popup opens, though blocking itself wasn't measured; Bitwarden and SponsorBlock install, and SponsorBlock went through the search, Add and permission dialog; Multi-Account Containers and Tree Style Tab, written for desktop Firefox, install, but whether they do anything on Android wasn't checked. Sidebars aren't offered on Android, and Android supports fewer extension APIs than desktop Firefox.

**Existing Firefox settings and sign-in.** Android keeps the Firefox app's profile private to that app, so nothing can be read from it. A Mozilla account sign-in in another app needs a client registered with Mozilla and its sync code, so it isn't offered; signing in on websites works normally. A bookmarks HTML export from Firefox can be imported, and extensions can be added again.

**Importing from Firefox** (`browser/GeckoImport.kt`, `GeckoImporter.kt`, `ui/GeckoImportSheet.kt`; the browser's menu or settings, **Import from Firefox**). When Mozilla-signed Firefox or Firefox Beta is on the phone (found through the manifest's `<queries>` entries), the sheet offers it first. Android gives Raticode no way into Firefox's data, Firefox exports no provider or intent for its add-on list, and on Firefox 159.0.1 a VIEW link to `about:support` from outside Firefox showed "Cannot Complete Request", while shared text, search intents and `fenix://open` didn't reach the page either (one emulator; other channels and versions weren't tried). So **Get my extensions from Firefox** copies `about:support`, replacing what was on the clipboard (the sheet says so before the tap), opens Firefox, and the user pastes it into the address bar and taps **Copy raw data to clipboard**, the button in Firefox 159's own `aboutSupport.xhtml`. Raticode reads the clipboard only during that handover, for at most ten minutes, only once the sheet's own window has focus again, with **Check now** as the fallback; it takes the text only if it is Firefox's troubleshooting JSON, then clears it. Anything else copied during the handover stays put and is not shown, and only plain text is read, so a copied file is never opened. If Android ends Raticode while Firefox is in front, the browser screen's saved state brings the sheet and the handover back; it holds only the time the handover began. Closing the sheet ends the handover, so the clipboard isn't read after that. If Firefox's list is already on the clipboard when the button is tapped, that list is used rather than replaced. Extensions off in Firefox start unticked. Firefox for Android's bookmarks can't come over this way, and most of its settings live outside what `about:support` reports. Files, pasted text and public collections stay under **From a computer or a collection**. The user reviews what was found and taps **Import**. Nothing changes before that, files are read once into memory and never kept, and only extension IDs go to Mozilla's site.

| Source | Brings |
|---|---|
| `extensions.json` or `addons.json` from a Firefox profile | The extensions the user added (built-in parts and themes are left out) |
| `prefs.js` or `user.js` | Tracking protection, website colors, search engine, Save browsing history |
| `about:support` **Copy raw data**, pasted | Extensions and the same settings |
| Bookmarks HTML export, or Firefox's JSON bookmarks backup | Favorites in the current profile, added to those there; folders aren't kept |
| A link to a public collection on addons.mozilla.org | Its extensions |

Each extension is looked up by ID and installed from Mozilla's site, so what it runs is the current signed version rather than a copy from the file, and each still shows the permission dialog. An extension Mozilla's site doesn't list (self-hosted, unlisted or built by hand) can't be added. Only the settings named in `GeckoImport` are read; every other line of `prefs.js`, including sync and account details, is skipped. Password, cookie, key and history files are refused by name before they're opened. Turning off history through an import keeps the history already saved.

Not brought over: passwords, cookies and sign-ins; the Mozilla account and Firefox Sync (Mozilla's documentation treats Sync as a special case and shows no self-service route for other apps); each extension's own settings, which Firefox keeps in its private storage, so use the extension's Export or Backup if it has one and restore it here; settings this browser has no control for, which the review lists; and, from the Firefox app on the same phone, anything it doesn't list in its own troubleshooting data, because Android keeps the rest private to that app. That covers its bookmarks and most of its settings. The handover hasn't been run end to end on a device, so what Firefox for Android actually lists is unconfirmed.

**Private tabs and other browser gaps** (November 8, 2026). Both browsers now have private tabs (`docs/architecture.md`). WebView tabs need `WebViewFeature.MULTI_PROFILE`, so an out-of-date WebView gets a notice instead of an unisolated tab. Gecko gained reopen closed tab, a text size control, Save as PDF, and answers for date, month, week, time and color fields, which did nothing before; they're typed in and checked (`GeckoRules.formValue`), because GeckoView supplies no picker. The WebView browser gained Print or save as PDF. Links, images and pop-ups opened from a private tab stay private, and **Open link on your computer** isn't offered there. Pages can use the camera or microphone after a yes to a prompt each time (never remembered, https only, only for the page on screen); the app already held those Android permissions for QR pairing and voice. Location stays refused: the app has no location permission, and adding one needs a reviewed change to `scripts/release-policy.json`. Private tabs still appear in the media bar and playback notification while playing, downloads and bookmarks stay, and neither browser stops screenshots or the keyboard's own learning. Neither browser has its own password manager. WebView has no password-saving API, only Android's Autofill service. GeckoView does offer one (`Autocomplete.StorageDelegate`, `onLoginSave`, `onLoginSelect`), but it needs Raticode to store every site password, which wasn't added while no save or fill can be run on a device. Not built: reader view, translation, ad blocking in the WebView browser.

**On the desktop it exists on Linux, in a different form.** Mozilla removed Gecko's embedding API in 2011 and GeckoView is Android-only, so desktop Raticode runs real Firefox in a profile of its own and places Firefox's window inside the Raticode tab over X11 (the desktop's `docs/browser.md`, "Gecko"). It isn't streamed, and its tabs, settings, bookmarks, extensions and Mozilla account are Firefox's own. Wayland doesn't let one program place another's window inside its own, so on Wayland desktops Raticode restarts through XWayland while Gecko is chosen. macOS has no supported way to do this and Windows isn't built. Rem's tabs and the phone's view of the computer stay on Raticode's Chromium browser, and the desktop's streamed Firefox mode is a separate choice.

### Browsing inside Raticode, November 8, 2026

The user chose Firefox with **Over Raticode**, expecting the page inside Raticode with Raticode's bottom bar, and got a Firefox Custom Tab: Firefox's ✕ at the top and no Raticode bar. They asked for several tabs and Raticode's bar whichever browser is chosen (Raticode's, Firefox, Chrome or Edge), with tabs and music kept when switching away, and for the integrated browser's Back, Forward and Reload row to move from the bottom, where it sat on top of Raticode's bar, to the top.

**What Android allows.** Only Raticode's own browser can run inside Raticode's window. The others can't, for these reasons:
- **Custom Tabs** (what "Over Raticode" was) are an activity of the browser app stacked on Raticode's task; it covers the whole window and Raticode can't draw over it. Chrome's partial Custom Tabs are a bottom sheet at least half the screen tall, so they would cover the bottom bar, and Firefox doesn't offer them.
- **Activity embedding** (Jetpack WindowManager) shows another app's activity in a host only when that activity opts in (`android:allowUntrustedActivityEmbedding`, or the host's certificate in `knownActivityEmbeddingCerts`). Firefox, Chrome and Edge don't, and on a phone-width window embedding stacks activities full screen anyway. Android's `ActivityView`/`TaskView` are for system apps only.
- **An embedded engine** is a different browser, not the user's app: Android System WebView (Chromium, already Raticode's browser) has no Chrome or Edge account, sync or settings; Mozilla's GeckoView would put Firefox's engine in Raticode but not the user's Firefox profile, Mozilla account sign-in or add-ons, would add tens of megabytes to the app, and would need Raticode's browser rules (https only, refused schemes, permissions, downloads, certificate errors) rebuilt for a second engine. It wasn't added; it needs a decision on that size and review.

**What changed.**
- **Controls at the top.** Back, Forward, Tabs, Reload or Stop, and the menu are one row under the address bar (`BrowserPage`, tag `browserContent` for the page area below them). Nothing sits between the page and Raticode's bar. Since November 8, 2026 the address shares that row; see Compact browser controls below.
- **Music keeps playing elsewhere in Raticode.** Leaving the Browser page no longer pauses every page; it only leaves fullscreen video. Pages pause when Raticode leaves the screen (`MainActivity.onStop` calls `BrowserRuntime.visible(false)`). Before, moving to Rem or Threads paused every page and stopped all page timers (`WebView.pauseTimers`): on the emulator a plain looping `<audio>` tone played on, but the page's scripts stopped (0 timer ticks in 3 seconds), and streaming players use them to fetch the next audio and change tracks. Android may still stop Raticode in the background; the browser has no media notification or playback service.
- **Clearer choices on the Firefox, Edge and Chrome pages.** "Over Raticode" is now **Quick look**, with the note that it hides Raticode's bar and its ✕ stops sound; the header's "Use Raticode" is now **Raticode's browser**, and the version line says the app "opens Raticode's web pages" instead of "your browser in Raticode". A **Browsing inside Raticode** card (`InsideRaticode`, tag `insideRaticode`) says the above in two sentences and offers **Browse inside Raticode**, which sets the engine to Raticode. Saved choices, profiles and sign-ins are unchanged.

**Tests.** `BrowserTopBarTest` (emulator, no paired computer; the navigation and sound parts need the emulator's internet) puts the browser above a stand-in bottom bar and checks that the five controls are one row under the address bar and above the page, each at least 48dp, with the page reaching the bar; that a second tab opens from the tab button and the first can be selected again; that Back, Forward and Reload work; and that a looping tone started by a real tap keeps playing (`currentTime` advances more than 2 seconds and the element isn't paused) and the page's timers keep running (at least 15 ticks of a 100 ms interval in 3 seconds) while another page replaces the browser, then the browser comes back with both tabs. With the old pause on leaving the page, the timer check fails with 0 ticks.

**Sound after Raticode leaves the screen (November 8, 2026).** Until now every page paused when Raticode left the screen, so music in Raticode's browser stopped when the user went to another app or the screen turned off. Now:
- **Which pages play.** While Raticode is in front, or while a page plays, `BrowserRuntime` asks each live page whether a playing `audio` or `video` element with its volume up exists (`BrowserMediaScript.STATE`, run with `evaluateJavascript` every 2 seconds in front and every 4 while Raticode is away; no JavaScript interface is added). A player a script keeps outside the document counts once it has started after the page's hook is in; Web Audio and frames aren't seen, so such a page pauses with the rest.
- **The notification.** When a page starts playing while Raticode is in front, `browser/BrowserPlaybackService.kt` starts: a foreground service of type `mediaPlayback` (new permission `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, not exported, listed in `scripts/release-policy.json`) with a silent ongoing notification, **Playing in Raticode's browser** and the site, and **Stop**. The lock screen shows only the title. It starts while Raticode is in front because Android 12 and newer don't let an app in the background start one.
- **Leaving the screen.** `BrowserRuntime.appInFront(false)`: with nothing playing, every page pauses as before. With a page playing, the others pause and that one keeps running; JavaScript timers stay on, since Android pauses them for every page at once. When it stops playing, or **Stop** is tapped (every page's media is paused), the service ends and every page pauses.
- **More tabs.** A tab playing sound is never the one put to sleep when a fourth tab goes live.
- **Not done.** There is no media session, so the notification has no play, pause or track controls and headphone buttons don't reach the page; Android may still stop a long-running playback when memory is short.

`BrowserBackgroundSoundTest` (emulator, needs the internet) plays a tone after a real tap, checks that the service is in the foreground, presses Home, and checks that the tone and the page's timers keep going for 3 seconds; then it pauses the tone and checks that the service ends and the page's timers stop. With the old pause on leaving the screen it fails ("The page's timers ran").

### The media bar, November 8, 2026

A bar above every Raticode page shows what a tab in one of the two built-in browsers is playing. Android gives Raticode no view of playback in the Firefox, Chrome or Edge apps, so they never appear.

- **When it shows.** While a tab plays audibly. Muted video doesn't count. If several play, the one that started last is shown. After a pause it stays 30 seconds with Play available (`PAUSE_GRACE_MS`, the same wait as the desktop's bar); media that ended and can't resume stays 5 seconds (`STOP_GRACE_MS`), so it doesn't blink between tracks. Closing the tab, a crash, a new document or the notification's **Stop** removes it at once. Gecko reports a same-page address change and a new page alike, so `GeckoDocuments` counts only the first address change after a load starts; a load that ends without one, such as a download, leaves the bar alone. It's hidden during full-screen video and when the keyboard is up on a short or landscape screen. Nothing is saved, so a restored tab never claims to be playing.
- **Gecko** uses GeckoView's `MediaSession` delegate for play state, title, artist, artwork and which buttons exist. Gecko only reports audible media, including in frames.
- **Chromium (WebView)** has no such API, and WebView has historically disabled `navigator.mediaSession` for lack of any media UI of its own. `BrowserMediaScript.HOOK` runs in each new document and, only when the API is missing, adds a stand-in with the same shape, so sites that describe their tracks and register buttons do so as in a phone browser. It also records registered buttons and players started outside the document. The app asks for state with `evaluateJavascript` every 2 seconds in front, and again shortly after a button. Next and Previous use the page's registered buttons; Play and Pause use the page's button when it registered one, and the element otherwise.
- **Limits in WebView.** Media in frames isn't seen (an embedded player on another site's page shows no bar), the bar can lag a start by up to 2 seconds, and a page that registers its buttons before the hook lands shows them as unavailable. `mediaPlaybackRequiresUserGesture` stays on, so a page that starts a brand-new player on Next, rather than reusing one the user has already started, may be refused; the bar then shows what actually happened.
- **What a page can put there.** Title and artist are cleaned of control and text-reordering characters and capped at 200 characters. The site name comes from the browser, not the page, and always shows. Thumbnails: Gecko supplies its own; for WebView the app fetches the page's artwork or video poster once, over https only, with no cookies, up to 2 MiB and 8,192 pixels a side, decoded to about 192 pixels and kept in memory. IP addresses in any written form, `localhost` and local names, with or without a trailing dot, are refused. Redirects are followed by hand, at most three, and each address is checked before anything is sent to it. The check goes by the address as written: a public name that resolves to a private address isn't caught. The desktop bar is more permissive (http and embedded pictures, and a page's own private host) because its pictures load inside its web page; here the app itself makes the request. Without a usable picture the bar shows a music icon.

**Tests.** `BrowserMediaRulesTest` (JUnit) covers the rules above. `BrowserMediaBarTest` (emulator, needs the internet) plays a tone in a real WebView and walks the bar through metadata, Next, pause, another Raticode page, return to the tab and closing it.

### Lock-screen media controls, November 9, 2026

Android 0.31.0 puts the media bar's track on Android's own media controls: the lock screen, the notification shade, and anything that reads media sessions (headsets, cars, watches). Phone only; no event, operation or field is added and the desktop doesn't change.

- **How.** `BrowserPlaybackService`, the `mediaPlayback` foreground service that already kept a playing page alive, now owns a framework `android.media.session.MediaSession` and posts a `Notification.MediaStyle` notification tied to it. No library, permission or manifest entry is added. It renders exactly `BrowserMedia.current`: `BrowserMedia` calls `BrowserPlaybackService.sync` whenever the shown track or its picture changes, and the two engines no longer start or stop the service themselves. So the controls appear and go with the bar, including the 30-second hold after a pause (5 seconds when the page can't resume), and a closed tab, crash, new document or Stop removes them at once. The service stays in the foreground through the hold, so Play from the lock screen doesn't need a new foreground start from the background.
- **Buttons.** Android 13 and newer draw the controls from the session's `PlaybackState` actions; older versions use the notification's buttons. Both list only `BrowserMediaRules.buttons(track)`: Previous and Next when the page offers them, Play or Pause when it can toggle. Presses arrive through `MediaSession.Callback` or the notification's service intents and go through `BrowserMediaRules.allowed` before `BrowserMedia.perform`, so a stale button or a headset key can't do what the bar wouldn't. A press for a tab whose page has gone removes it. Stop is a custom action and a notification button and calls each engine's `stopSound`.
- **Privacy.** `BrowserMediaRules.shown` decides the text. A private tab (`Report.private`, from each engine's `isPrivate`) shows "Private tab" with no title, site or picture, everywhere the session is read. While the phone is locked, the title and picture are replaced by "Playing in Raticode's browser" when **Show what's playing on the lock screen** (both browsers' settings, `browser_media` shared preference, on by default) is off or App lock is on. The service watches `SCREEN_OFF` (hides at once, since the keyguard can lock a few seconds later), `SCREEN_ON` (asks `KeyguardManager`) and `USER_PRESENT`. Some lock screens draw media controls from the session rather than the notification, so redacting the session is what counts; the notification's public version is generic as well whenever hiding could apply.
- **Locks.** While the Child lock is on, every press shows the blocked toast and does nothing; playback continues. Tapping the controls opens `NotificationOpenActivity`, so App lock and Child lock still cover Raticode.
- **Android rules.** The service keeps its `mediaPlayback` type and `FOREGROUND_SERVICE_MEDIA_PLAYBACK` permission (Android 14). Starting it from the background throws on Android 12 and newer; `sync` and `startForeground` catch that and the page plays on without controls. Media-session notifications are exempt from Android 13's notification permission, so the controls show even when it was denied. Every `startForegroundService` ends in `startForeground`, with a placeholder when the music stopped in between.
- **Limits.** The hold uses the main thread's clock, which doesn't advance while the CPU sleeps, so on a sleeping phone the paused controls can outlast 30 seconds. There's no position or seek bar: neither engine reports position to the bar. Firefox, Chrome and Edge apps have their own controls.

**Tests.** `BrowserMediaControlsRulesTest` (JUnit) covers the text, privacy, lock-screen and button rules. `BrowserMediaControlsTest` (emulator, needs the internet) reads Android's own `dumpsys media_session` and `dumpsys notification` and presses keys with `cmd media_session dispatch`: a real WebView tone through play, pause, page metadata and Next, a private Gecko-keyed track, a press for a gone tab, the title on a swipe lock screen and hidden there when turned off (back after unlocking), and closing the tab, with screenshots of the shade and lock screen in `/data/local/tmp/raticode-media-controls-*.png`; and a real Gecko tab playing an MP3, skipped when Gecko can't play it. `BrowserBackgroundSoundTest` checks the service now outlives a pause by the hold.

### One tab list for both built-in browsers, November 10, 2026

The user asked for the browser's tabs from every engine in one tab bar, and for the built-in browsers to be named **Raticode (chromium)** (WebView) and **Raticode (gecko)** (GeckoView) on the desktop and the phone. Phone half; no event or operation is added.

- **The computer's tabs.** Each `browser.tabs` entry may carry `engine` (`raticode`, `gecko`, `firefox`, `chrome` or `edge`), the browser running that tab on the computer; the top-level `engine` stays the computer's default for tabs Rem and the phone open there. `DesktopBrowser.parse` reads the per-tab value (unknown values read as `raticode`) and falls back to the top-level one when an older desktop omits it. Each row names its browser; with per-tab values the list is titled "On your computer", since it can mix browsers.
- **Saved state.** `showing` is written only when it differs from `engine`, and only `raticode` or `gecko` read back.

## Ask Rem about a file or a change, November 9, 2026

Android 0.30.0 adds Ask Rem to the file viewer's text selection, to each diff file and hunk in Source control, and to commit details. No event, operation or field is added and the desktop doesn't change.

- **What it does.** `live/AskRem.kt` builds the words: `About this file:` or `About this change:` with the relative path, or `About this commit:` with the full commit ID, then `Project:`, `Change:` (staged, not staged, or the commit) and `Lines:`, and the selected text or hunk in a fenced block of at most 2,000 characters. Site information moved to the WebView browser's menu, Extensions to the top of the Gecko menu, and the address shows only the site's name, keeping the end of a long name because that part says whose site it is.
- **Folding.** `browser/BrowserControlsMotion.kt` (plain JUnit) decides. Scrolling the page down 24 dp folds the row into a 28 dp strip with the site's name and lock; scrolling up 32 dp or reaching the top brings it back, and so does tapping the strip or tapping Browser on the bottom bar. It also folds after 5 seconds without use, stretched by Android's "time to take action" setting. Starting a page load, switching tabs, opening a menu or dialog, editing the address, find in page, error pages and blank tabs bring the row back or hold it open. It never folds while TalkBack or another touch-exploration service is on, because those users can't reach it by scrolling.
- **Scrolling signals and limits.** WebView's `OnScrollChangeListener` and GeckoView's `ScrollDelegate` report the page's root scroller only, so a site that scrolls inside its own panel (some web apps, and full-screen feeds) folds only by idling and returns by the strip or the Browser tab. The row crossfades instead of sliding so the page is resized once per change, not on every frame; for 350 ms after a change (1.5 seconds after the user taps the strip or the Browser tab, so a page still coasting from a swipe cannot fold them again) scroll movements are ignored, because resizing a page can nudge its position.

**Tests.** `BrowserControlsMotionTest` (JUnit); `BottomBarLayoutTest`, `BrowserTopBarTest` and `GeckoBrowserTest` on the emulator. `KeepBrowserControls` is a test rule that stops idle folding for tests that use the toolbar long after a page loaded.

## Global board and Rem's self-work, November 2026

The phone gets the desktop's global board (tickets from every organization and Rem's own) and Rem's self-work controls. The desktop half is desktop branch `rem-kanban-self-work`, which owns tickets, the 15-minute idle rule, self-work scheduling, thread limits, deduplication and every check; the phone shows what the desktop says and asks it to change. All of it needs **Use Raticode from this phone**; without it every op is `unauthorized`.

**Capability.** `overview` adds `kanban`. The phone sends the ops below only after this session's overview says so, and drops queued `kanban.board` and `selfwork.read` reads when it reconnects, so an older desktop never receives an op it would refuse by closing the session. Actions tapped before the overview arrives wait on the phone and go once it says the desktop takes them, or fail with a note asking to update Raticode on the computer.

**`kanban.board`** (read). Params `{known?}`. Answer `{tickets, organizations, earlier, counts, digest}`: every open ticket first and then the newest closed ones, within the size limit, with `earlier` counting what stayed on the desktop.
- `tickets[]`: `ticket_id`, `scope` (`rem` or `organization`), `organization_id` and `organization_name` (empty for Rem's), `key`, `title`, `description` (at most 4,000 characters), `status` (`backlog`, `todo`, `in_progress`, `in_review`, `done`, `blocked`, `cancelled`), `priority` (`low`, `medium`, `high` or `urgent`, the phone's name for the board's `critical`), `assignee_id` (`rem` on every Rem ticket), `assignee`, `proposed`, `proposal_reason`, `duplicate_of`, `created_by`, `created_at`, `updated_at`, `revision`, `running`, `block_reason`, `summary`, `type`, `project` (a name, never a folder), `run_id`, `thread_id`.
- `organizations[]`: `organization_id`, `name`, `state`, `employees[]` (`employee_id`, `name`, `title`). They fill the assignee menus. No paths, grants or configuration.

**`kanban.ticket`** (action). Returns the refreshed board. The desktop runs each change as the user, through the same code the desktop board and Rem use; organization tickets still go through their organization's approval, review and revision rules.
- `{action: "create", scope, organization_id?, title, description?, priority?, status? (backlog or todo), assignee_id?, type?, project_id?}`. `project_id` is the phone's catalog ID, mapped to a folder on the desktop; a path is ignored.
- `{action: "assign", ticket_id, scope, organization_id?, expected_revision, assignee_id, to_organization_id?}`. An organization's ticket goes to one of its workers, or empty for unassigned, and never to Rem. A Rem ticket stays with Rem, or `to_organization_id` hands it to an organization: the desktop creates it there first and then closes Rem's copy.
- `{action: "move", ticket_id, scope, organization_id?, expected_revision, column}`. Organization tickets follow their board's rules. Rem's tickets have no Review column, and moving one to In progress starts it now, through the same claim self-work uses. A stale revision is `conflict`.
- `{action: "approve" | "decline", ticket_id, scope, expected_revision, reason?}` for a `proposed` ticket. Approval leaves it in Backlog as an ordinary ticket. Declining closes it and keeps the record, so the idea isn't proposed again.

**`selfwork.read`** (read). Params `{known?}`. Answer:
- `settings`: `enabled`, `max_threads`, `auto_pull_backlog`, `idle_minutes`, `revision`.
- `limits`: `max_threads_min`, `max_threads_max`.
- `state`: `mode` (`off`, `waiting`, `working`, `paused`), `active_threads`, `thread_limit`, `todo_remaining`, `proposals_waiting`, `last_prompt_at`, `starts_at`, `detail`.
- `report`: `since`, `updated_at`, `unseen`, `summary`, `tickets_added[]` (`ticket_id`, `title`, `scope`, `organization_name`, `proposed`, `at`), `work_done[]` (`ticket_id`, `title`, `state` of `done`, `blocked` or `researched`, `summary`, `thread_id`, `at`), `duplicates_merged[]` (`ticket_id`, `title`, `kept_title`, `reason`, `at`), `notes[]` (`text`, `at`).

**`selfwork.settings`** (action). `{enabled?, max_threads?, auto_pull_backlog?, expected_revision}`. Returns `selfwork.read`'s answer. A stale revision or a value outside `limits` is refused with a sentence the phone shows.

**`selfwork.report.seen`** (action). `{updated_at}`. The user has seen the report up to that point, on any device. Returns `selfwork.read`'s answer.

**On the phone** (**More › Global board**, or pinned to the bottom bar as **Board**): three sections.
- **Board** is every ticket by column, one column at a time (swipe or tap a column), with a whose-tickets filter (Everything, Rem or one organization) and an assigned-to filter. A long-press opens **Move**, which lists every column and says why one is closed. **New** adds a ticket for Rem or any organization, with a worker for an organization's ticket and a kind and project for Rem's.
- **Proposed** lists what Rem wrote for approval, with its reason, any likely duplicate, and **Approve** and **Decline** buttons. Decline takes an optional reason for Rem.
- **Self-work** shows what Rem is doing and when it starts, with the on-off switch, maximum threads (quick taps become one change), Pull work from Backlog, which explains what happens with it on and off, and the running report: tickets added, duplicates merged, notes and work done. Opening it marks the report seen on every device.

A ticket's page shows why it exists, its assignee menu, Move, its last result and details, and for an organization's ticket a link to that organization. Rem's chat shows **While you were away**, with what self-work added and finished, until it is opened or dismissed; while Rem is working and nothing is new, it says that instead. The phone asks for the report at most every 30 seconds while Rem's chat is open.

**States.** Before the first answer the page says it is loading. Offline with nothing loaded says so; offline with something loaded shows it with a note that it is old, and every button that changes something turns off. A failed read shows the desktop's sentence and Try again, or a strip above older data. An older desktop gets a note asking to update Raticode on the computer, with **Check again**. A refused action shows the desktop's sentence.

**Not on the phone.** Editing a ticket's title or plan, cancelling a ticket, accepting an organization's reviewed work (the ticket links to its organization), and Rem's project choice for proposals.

**Tests.** Phone: `KanbanTest` covers the parsing, the board's filters and move rules, every action's request and the report line, against answers in `app/src/test/resources/desktop/` written by the desktop's own handlers. Desktop: `tests/unit/test_rem_kanban.py`. The phone's real request bytes (`Kanban.createParams` and the others, built from those samples) were replayed through the desktop's handlers in a scratch pytest; every one was accepted and changed the expected state. The schema adds the five ops and fixtures `desktop.read.kanban-board.json`, `desktop.read.selfwork-read.json`, `desktop.action.kanban-ticket.json`, `desktop.action.selfwork-settings.json` and `desktop.action.selfwork-report-seen.json`, byte-identical with the desktop.

## Task progress notification, November 9, 2026

Android 0.29.0 shows one ongoing notification for tasks started from this phone, while background sync is on. It uses no new op, event type or field, so it works with the current desktop and no schema or `SHA256SUMS` change is needed.

The phone reads the existing `rem.home`, which needs **Use Raticode from this phone**. It sends the read in the background every 15 seconds only while it has a claimed run or a request under 10 minutes old, with the `known` digest so an unchanged answer stays small. The desktop still owns all execution and every state shown; the phone only reports what `rem.home` says.

A run counts as this phone's when:

- it follows this phone's own `rem.message` in Rem's chat, before the next user message from anywhere. The desktop stores a message with the phone's request ID as its `id`, and a run linked through `work.run_id` on a following Rem message must have started after that request, on a one-time task with no `schedule.at`;

Self-work never counts: the desktop's `self_work` runs post no message in Rem's chat, and the phone claims nothing without a request of its own. Tickets started through the board aren't followed either.

With **Show Rem's words** on and Rem's alerts on, the title becomes the task's title. The lock-screen version never names a task. Turning the words off replaces the title at once.

## Organization work schedule, November 10, 2026

Organizations get a work schedule: named focus blocks (name, focus, keywords) that repeat daily, weekly on chosen weekdays, monthly (a day of the month, where 29 to 31 fall on the last day of shorter months, or the 1st to 4th or last weekday) or quarterly (the same, in the 1st, 2nd or 3rd month of each quarter), each with a 24-hour start and end. An end at or before the start runs into the next day; the same start and end is a whole day. Where blocks overlap, the longer cadence wins (quarterly, monthly, weekly, daily), then the shorter block; the desktop refuses two overlapping blocks with the same cadence and length. The schedule uses the organization's one time zone, shared with working hours. Workers favor tickets that match the block on now, and a block change never stops running work. Nothing is applied by itself: an organization without blocks gets a suggested schedule to start from. The desktop logic is `gofer/ui/organization_schedule.py`.

**Capabilities.** `overview` adds `organization_schedule`. The phone sends `organizations.schedule` only after this session's overview says so; tapped earlier, it waits with the other organization actions and fails with the update note if the desktop doesn't take it.

**`organizations.read` addition.** `schedule`: `{timezone, configured, blocks, template, current, next, changes_at, issues, underway}`. Blocks are `{block_id, label, focus, cadence, start, end, days, month_day, nth_week, weekday, quarter_month, keywords, when}`, `when` being the desktop's description. `current` adds `started_at` and `ends_at` (its `start`, `end` and `when` are blank, so the phone looks the block up in `blocks` by ID); `next` is the block that wins at `changes_at`, null meaning no block then. `issues` are `{kind: gap | outside_hours, text}`; `underway` is `{employee_id, name, task_id, title, check_in, block_label}`. An older desktop's read has no `schedule`.

**`organizations.schedule`** (action). `{organization_id, expected_revision, timezone?, blocks}` replaces the whole block list (at most 40) at the organization's revision; `timezone` goes only when it changes. Blocks are sent without `when` and with only their cadence's fields: `days` for weekly, `month_day` or `nth_week` with `weekday` for monthly and quarterly, `quarter_month` for quarterly. The answer is the organization's read. A stale revision is `conflict`; a schedule the desktop can't accept is `invalid` with its sentence (for example, two blocks that overlap and neither takes precedence).

**On the phone.** The Organization tab's **Work schedule** card shows the block on now with its focus on one line and "until HH:MM" in the organization's time zone, "Next: <block> at HH:MM", the desktop's warnings, and who is working under which block. Without blocks it says workers use their usual priorities and offers **Use suggested schedule** (the editor opens filled from the template; nothing saves until **Save**) or **Build your own**. The schedule page lists the blocks with their times, the time zone, **Add block**, and Save; a block's page edits its name, focus (600 characters), how often, weekdays, the day of the month or the nth weekday, the month of the quarter, start and end (typed or picked, with "Ends the next day" and "All day" notes) and up to 12 comma-separated keywords, and deletes it. `live/WorkSchedule.kt` ports the desktop's block checks, same-rank overlap check and descriptions for quick feedback; the desktop's refusal is authoritative and shown on the page. Offline, the card and list show the last answer and nothing can be changed or saved. An older desktop gets the update note in place of the card.

**Tests.** Phone: `WorkScheduleTest` parses real answers from the desktop's `test_the_phone_reads_and_edits_the_work_schedule` organization (`organizations-read-v2.json` before any schedule, `organizations-read-schedule.json` after saving the suggested one), checks the descriptions against the desktop's, the block and overlap rules, and builds the contract fixture `desktop.action.organizations-schedule.json`'s params.

**Searching Rem's chat, November 10, 2026.** A desktop whose `rem.home` says `search: true` takes two new reads. `rem.search {query, before?}` searches its whole saved chat without a model and answers `{query, total, results, next}`. Each result has `{id, seq, role, kind, created_at, where, snippet, title}`, and `snippet`/`title` are `{text, match}` parts. `rem.history {before, through?}` answers the page of messages before message `before`, shaped as in `rem.home`, as `{messages, earlier, tickets}`, reaching back to `through` when given. The phone keeps pages in memory only (`LiveClient.remEarlier`), adds messages that slide out of the newest window, and drops the pages when the window holds the whole chat or no longer overlaps (a cleared history). Offline or with an older desktop it searches what it holds (`RemSearch.local`) and says so; it never sends either read without the flag. Both are added to the schema's `desktop.read` and `desktop.result` lists with fixtures. The desktop's `docs/mobile-desktop-parity.md` has the matching rules. Tests: `RemSearchTest` and `LiveRemSearchTest` (fixture flag `--search`, invitation argument `searchInvitationFile`).
