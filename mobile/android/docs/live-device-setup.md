# Live desktop setup

> User documentation for this feature is on the website: [Pair and connect](../../../website/docs/mobile/pairing.md). The website is the single source of truth for how Raticode works; this file is developer and design detail.

## Update without resetting pairing

Install `app/build/outputs/apk/debug/app-debug.apk` over the existing same-key debug app. Do not uninstall or forget pairing to update. Version 0.5.3 keeps the synchronized thread list open and preserves encrypted live trust, history, files, drafts and queued messages. The demo is no longer shipped.

Update both mobile and desktop for the optional v2 sync extension and scoped thread creation. Normal `electron:dev` reads source, so an AppImage rebuild is unnecessary. Stop the previous desktop development process and launch from `frontend`:

```sh
nvm use 22.12.0
RATICODE_DEVICE_EXPERIMENTAL_NETWORK=1 npm run electron:dev
```

Desktop automatically selects its default private IPv4 interface. `RATICODE_DEVICE_HOST=<desktop-private-IP>` overrides this, for example when a VPN chooses the wrong interface. Keep the separate UI HTTP server on loopback. Device settings show the selected Wi-Fi address and Rem dispatcher readiness. Without a private address, desktop does not create phone invitations. Packaged apps need rebuilding to include source changes.

Already-paired phones receive the desktop's updated LAN endpoint over encrypted sync; a fresh QR is unnecessary. For a first pairing, create a five-minute invitation in desktop **Paired devices**, scan it on the phone, compare identities and confirm the pending phone on desktop. Invitation review does not execute commands. Android 10 or newer is required.

## Sync desktop threads and chat

1. Update desktop and install the new APK over the existing app. Keep the same signing key and application ID so pairing survives.
2. In desktop **Paired devices**, **Sync desktop threads with this phone** is enabled by default for newly confirmed phone pairings. It shares current and future threads and history, and allows new conversations using your desktop projects. Existing sync choices remain unchanged; enable it if an older pairing has sync off. Raticode can run in the background: closing its window hides it to the tray and sync continues. Quit from the tray menu stops sync. Desktop confirmation and the phone acknowledgment must finish before sync becomes active.
3. The phone stays on the thread list when threads arrive. **Threads** shows the desktop's sections: Pinned, Unread, Read, Running and Archived. Read holds the seven most recently read threads; desktop archives older ones. Running and Archived start collapsed. Unread threads have a bold title and a blue dot; running threads show a spinner. Opening a thread clears Unread on the phone until desktop reports a newer update; it does not mark the thread read on desktop. Each dated row shows its project or Global, an Archive button (Delete when archived) and a menu with Pin/Unpin thread, Restore thread for archived rows, and Delete thread. Deletion requires confirmation and remains pending until the desktop renderer saves any configured archive and removes the thread. An unavailable archive folder leaves the thread pending and reports the problem on desktop. **Search in threads** searches titles and saved desktop message text across groups, including history not downloaded on the phone. Tap a result to load and scroll to its matching message. Search requires a connection. Choose Global/project, provider, model, effort and permissions, then send from the bottom composer to start a desktop-visible thread. The small **New thread** icon starts an empty conversation. Neither asks for a name. Desktop derives the title from the first message, using its first eight words and an ellipsis for longer text. Attach file first creates an empty shared thread and carries the draft into chat before opening Android's picker. Shared thread lists are paged instead of stopping at 100 entries. **Load earlier messages** reads older history on demand.
4. Tap the scope or model above the conversation to open **Thread settings**. Choose an open project or **Global**, provider/model, model-specific effort and provider permissions. Global uses desktop Rem's project-selection tool and continues in the selected project. Context revisions reject stale changes. The native desktop thread ID, project, selected resources and text history survive model changes. Desktop edits take precedence over a conflicting phone selection.
5. **Attach file** in a thread opens Android's scoped picker; in Rem's chat the paperclip first offers photos, the camera, recent files, Downloads and all files. Select up to eight files by repeating the action. In a thread each must finish its verified upload before Send is enabled; in Rem's chat Send works while files upload, and the message goes once they have arrived. Tap an attachment chip to remove it from the draft. **Files** retains incoming download/export and transfer cleanup controls. Limits remain 10 MiB per file and 50 MiB local file storage.
6. **Dictate** requests microphone permission and uses Android's on-device recognition engine. Review the resulting draft before sending. Android 12 or newer and an installed offline language model are required. There is no automatic cloud speech fallback. The keyboard microphone is an alternative supplied by your keyboard.
7. **Send** persists the message first; offline sends say **Queue**. Only a durable authenticated receipt marks acceptance. **Stop Rem** requests desktop cancellation. Rem's thoughts and tool steps refresh on the phone about once a second while the open thread runs, and the final response appears in both conversation views.

Sync polls every five seconds over Wi-Fi while mobile is active. The renderer checks for changes every five seconds. Provider catalogs refresh within 60 seconds, or with Refresh. The same encrypted connection carries catalogs and history. Being on the same Wi-Fi is a route, never authorization.

Shared conversations use the desktop's existing provider permission modes and selected resources. Codex, Claude Code, Cursor, Copilot, OpenCode, Antigravity and Grok use their normal desktop adapters. Antigravity and Grok require CLI-managed permissions where their adapters require it; choose that mode in Thread settings. The phone can change those settings just as the desktop can. There is no separate mobile read-only cap. The desktop still executes requests and enforces the selected provider's approval policy.

The project catalog includes validated open desktop projects even when they have no existing thread. Rem can return a file from another open project without changing the conversation's scope. The file tool uses the phone's mapped thread ID, rather than the desktop renderer's native ID. Existing transfer size limits and checks against symlinks and replaced directories still apply. Routine shared-context refreshes no longer revoke running work. Explicit unpairing, revocation and disabling sharing still cancel it.

Running indicators include desktop-originated jobs and phone requests. When offline, a previously running thread is labelled as its last synced state. Rejected requests now display the authenticated desktop reason; stopped providers and failed providers are distinguished.

The phone uses the same desktop projects and provider policies as its owner. There is no separate Project access section for phones. Turning off thread sync stops workspace sharing; revocation and unpairing still cancel pending work.

## Resources, approvals and swarms

**Thread settings > Resources** lists the thread's desktop tools: Commands, Web, Subagents, Browser, skills and MCP servers. Turn them on or off and choose **Apply**. The change follows the thread to desktop. The phone can only switch existing desktop resources; add skills or servers on desktop.

To answer approvals and control swarms from the phone, turn on **Allow approvals and swarm controls from this phone** under Phone in desktop **Paired devices**. It is off by default and needs thread sync. On the phone, open **Thread list options > Approvals** to approve or reject paused workflows and to let a swarm proceed or redirect it with an instruction. A changed request must be reviewed again. With response notifications enabled, a generic "desktop approval is waiting" alert appears; it never names the request. **Thread list options > Swarms** shows swarms in your shared desktop projects with status, progress, agents and the board. You can pause, resume, stop and message a swarm. All of it runs on the desktop.

## Desktop in the background

Close the Raticode window to keep it running in the tray. Phone threads, Rem turns started from the phone, approvals, swarms and phone deletions keep working; the phone does not need the window open. **Quit Raticode and stop background work** in the tray stops everything. If the hidden window's renderer crashes, Raticode reloads it automatically, up to three times an hour. If the window is destroyed, Raticode restores a hidden one; **Open Raticode** in the tray shows it.

## Wi-Fi only

Unless you turn on [Tailscale](#away-from-home-with-tailscale-optional), the phone connects to the desktop only over Wi-Fi. Each Wi-Fi connection binds its socket to the phone's connected, non-VPN Wi-Fi network, so device traffic never uses mobile data. There is no internet relay. Away from the desktop's network, the phone shows its saved threads and queues messages until Wi-Fi returns, then reconnects immediately.

Invitation review shows the desktop's Wi-Fi address and port. An invitation without one is rejected; update and restart desktop on your Wi-Fi network, then create a new QR. Pending pairing and **Desktop > Wi-Fi connection** both display the saved address and offer **Set desktop address**.

If the address is missing or stale, choose **Set desktop address** and copy the IP address and port from desktop **Paired devices**. Use the device listener's port, not the desktop UI's HTTP port. This saves an encrypted route hint and reconnects to the existing desktop identity. The invitation bytes, identity pin and desktop confirmation requirement are unchanged. A pending enrollment first tries resume, then retries the original unexpired invitation. If that invitation has expired and desktop never received enrollment, generate a fresh QR. An authenticated desktop snapshot replaces the manual address when it reports a current one.

Phones paired with an older relay-only QR keep their pairing. If they have no saved address, enter it once with **Set desktop address**.

Desktop **Connection and troubleshooting** shows both the LAN IP and port. Pairing setup lives under **Pair a device**, and identity, connection details and unpair/revoke controls appear directly under **Phone**. The thread-list composer explains whether it needs a connection or thread sync, and enables creation when the grant arrives. Desktop connection controls are available from the thread toolbar's overflow menu.

Short pauses between parts of a LAN packet no longer discard the connection. Incomplete frames still expire after 30 seconds. This repair does not establish the cause of any particular physical phone timeout.

Being on the same Wi-Fi does not prove direct reachability. Guest Wi-Fi/client isolation, a firewall, a VPN-selected interface or an outdated host override can block it. Check the private address in desktop Paired devices. Use the host override for the intended interface and restart after its address changes. Without Tailscale there is no fallback route.

## Away from home with Tailscale (optional)

Tailscale is a private network made of your own devices. With it, the phone can reach the desktop on mobile data or someone else's Wi-Fi without forwarding router ports or opening anything to the internet. It is off by default. Nothing in this section has been tried on a physical phone or a real Tailscale network yet.

**Sign-in.** Raticode does not sign in to Tailscale, embed it or ask for keys. You install Tailscale's own apps and sign in to your own account with Google, Microsoft, GitHub, Apple or another supported identity provider ([Install Tailscale on Android](https://tailscale.com/docs/install/android); on Linux, `sudo tailscale up` prints a sign-in link, see [Install Tailscale on Linux](https://tailscale.com/docs/install/linux)). No API key, OAuth client or auth key is needed. Auth keys are meant for servers and devices where you cannot sign in yourself ([Auth keys](https://tailscale.com/kb/1085/auth-keys)), and an API token would let Raticode change your Tailscale network, which it should not do. Embedding Tailscale inside Raticode would require one of those keys or a separate sign-in per app; it was not chosen.

**Setup:**

1. Create a Tailscale account, or use an existing personal one. Turn on two-step sign-in with your identity provider. Anyone who controls the account can add devices to your network.
2. Install Tailscale on the desktop and sign in. On Linux run `sudo tailscale up` and open the printed link.
3. Install the Tailscale app on the phone from Google Play and sign in to the same account.
4. Restrict the network. A new Tailscale network lets every device reach every port on every other device. In the admin console's access controls, remove the default allow-all rule and allow only the phone to reach the desktop's device port, for example `{"grants": [{"src": ["<phone Tailscale IP>"], "dst": ["<desktop Tailscale IP>"], "ip": ["tcp:44233"]}]}` with your own addresses and port ([Grants](https://tailscale.com/kb/1324/grants)). Keep other rules you rely on. Pin the port with `RATICODE_DEVICE_PORT` so it cannot change.
5. Leave Funnel, Serve, subnet routes and exit node off on the desktop. Raticode needs none of them.
6. On the desktop, in **Paired devices > Away from home with Tailscale**, turn on **Also listen on this computer's Tailscale address**. The desktop keeps its Wi-Fi listener. This needs a desktop build with Tailscale support (desktop `dev` from October 31, 2026). Without it, set `RATICODE_DEVICE_HOST` to the desktop's Tailscale IPv6 `fd7a:115c:a1e0:…` address instead; the desktop then listens only on Tailscale, and phones need Tailscale even at home.
7. Pair the phone at home on Wi-Fi as usual, or keep the existing pairing. Tailscale does not change pairing, the pinned desktop identity or desktop confirmation.
8. On the phone, open **Desktop** (or **More > Connection**) and turn on **Connect through Tailscale**. The phone asks the desktop for its Tailscale address on the next sync. You can also choose **Set Tailscale address** and enter the desktop's Tailscale IP (from `tailscale ip` or the admin console's Machines page) and the same device port as the Wi-Fi address.
9. In the Tailscale app, do not exclude Raticode under app-based split tunneling ([Android split tunneling](https://tailscale.com/docs/features/client/android-app-split-tunneling)). An excluded app cannot see the Tailscale network, so Raticode would just fail to connect.

**How the phone chooses a route.** On Wi-Fi it first tries the desktop's Wi-Fi address directly, then Tailscale. After Tailscale works on a Wi-Fi network, it tries Tailscale first until the phone joins a different Wi-Fi network. Without Wi-Fi it tries only Tailscale. A Tailscale address is used only through a VPN network whose routes carry that exact address; if Tailscale is off, signed out or excludes Raticode, the phone reports that and opens no socket. It never falls back to plain mobile data. Both routes use the same pinned TLS 1.3 session and desktop authorization, so Tailscale is only a second encryption layer and grants nothing.

**Drops and recovery.** When the Wi-Fi or Tailscale network under an open session goes away (leaving home, Tailscale restarting its VPN), the phone closes that session and reconnects at once over whatever route is left. If the desktop stops answering for 45 seconds after the phone sent something, for example because it slept or the path broke without a close, the phone reconnects instead of showing a dead session as connected. A Tailscale connection gets 10 seconds to open, because an idle tunnel may first need a handshake or a relay. Queued messages stay on the phone and are resent after each reconnect, and the desktop resumes from the phone's last received event. A desktop that newly sees the phone sign in ends that phone's older sessions.

The phone accepts Tailscale addresses only in Tailscale's ranges, `100.64.0.0/10` and `fd7a:115c:a1e0::/48` ([IP address assignment](https://tailscale.com/kb/1033/ip-and-dns-addresses)). Names such as `desktop.tail1234.ts.net` are not accepted. The address you enter is saved encrypted and is never replaced by a desktop sync; **Remove saved address** goes back to the address the desktop reports. A desktop that stops listening on Tailscale reports that, and the phone drops the reported address. Pairing a different desktop clears an entered Tailscale address. Turning the switch off ends a Tailscale session at once.

While the switch is on, the phone's sync requests include `include_tailnet_endpoint`. A desktop without Tailscale support rejects that field and closes the session, so the phone cannot sync with it while the switch is on. Update the desktop first. If the switch was turned on against an older desktop, turning it off restores Wi-Fi sync: the phone removes any queued request for the Tailscale address in the same save, never resends one while the switch is off, and queues a clean sync request.

**Check that it works.** Turn Wi-Fi off on the phone, keep Tailscale on, open Raticode and send Rem a message; the header should read **Encrypted Tailscale**. Turn Tailscale off on the phone and reconnect; Raticode should report that Tailscale is not connected. From the phone, only the device port on the desktop's Tailscale address should answer. The router should have no port forwards to the desktop. Android allows one VPN at a time, so another VPN app replaces Tailscale while it runs. Polling every five seconds keeps the mobile radio busy while the app is open; leave background sync off away from home if battery matters.

## Voice assistant (Android 12 or newer)

1. Pair as usual and turn on **Use Raticode from this phone** in desktop **Paired devices**. Voice mode sends through Rem's chat; no desktop update is needed.
2. Opening Raticode from its icon offers **Use Rem as your assistant?** until Raticode is chosen. **Set up** continues with step 3; **Not now** asks again next time; **Don't ask again** stops the offer, which **Offer setup when Raticode opens** turns back on. The same setup is always at **More › Voice assistant** (and **Desktop > Voice assistant**). It shows whether this phone can recognize your language offline (Android 13 and newer offer **Download offline speech**) and whether an offline voice can read replies.
3. Tap **Set up** or **Choose digital assistant**. Android doesn't let apps choose the assistant or open its picker directly, so Raticode opens the closest settings page: on Pixel and most phones the **Digital assistant app** page (tap **Default digital assistant app**), on Samsung **Apps › Choose default apps** (tap **Digital assistant app**, then **Digital assistant app** again). Pick **Raticode**. Back in Raticode, the offer says whether it was chosen; if the phone has neither settings page, it shows the path to follow by hand. This replaces Google's assistant for the power button and the assist gesture; choose Google again the same way to undo it.
4. Map the power button if your phone needs it. Pixel: **Settings › System › Gestures › Press and hold power button › Digital assistant** (Pixel 6 and later do this by default; Power plus Volume up opens the power menu). Samsung: **Settings › Advanced features › Side button** (or **Side key**); if **Press and hold** offers **Digital assistant**, choose it. **Galaxy S20** (last update One UI 5.1, Android 13): **Press and hold** usually offers only Bixby or the power-off menu, so the side key may not open Rem; hold **Home** with navigation buttons, swipe up from a bottom corner with swipe gestures where offered, or use the tile or the shortcut. Other makers place it under **System**, **Gestures** or **Buttons & gestures**, and some phones don't offer it.
5. Hold the power button or use the assist gesture. The first time, allow the microphone. Speak while the dotted line rises with your voice; pauses don't stop it. When you've finished, tap the send arrow at the bottom right: it takes your last words and sends. To change anything first, tap the keyboard button: listening stops and your words open to edit, and the microphone button there adds more words to what is in the box. Tapping the dotted line pauses and resumes listening. Opened over Raticode's own Rem chat, voice mode closes as soon as the message is queued, leaving the chat with your message and Rem's reply behind it. Rem's reply appears and is read aloud. The microphone button after a reply starts a new message; suggestions under the reply send at once.
6. Without the assistant role, use the **Talk to Rem** Quick Settings tile (**Add Talk to Rem tile** on Android 13+), long-press the Raticode icon, or tap **Talk to Rem** on the background sync notification.

Options in the same section: **Talk back to me** (on; it can be switched off or on whether or not a voice is installed, and the speaker button in voice mode does the same), **Let Rem read your screen** (off) and **Show replies on the lock screen** (off). With screen reading on, open Rem over an app, tap the screen button at the bottom (it lights up), and ask about it; it is off again each time Rem opens. The paperclip beside it attaches files after an unlock. If Rem can't see it, turn on **Use text from screen** in Android's digital assistant settings. With a PIN, pattern or password set, a request made while the phone is locked waits for **Unlock and send**. **Type instead** is available at every step, for example when no offline speech language is installed. Voice mode connects over Wi-Fi, or Tailscale when it is turned on, exactly like the app; it can't reach the desktop any other way.

## Linux firewall checks

If no phone appears after scanning a fresh QR, check whether the desktop firewall drops its TCP connection. A bound listener and a successful connection from the desktop itself do not prove that incoming phone connections are allowed. Mobile distinguishes an unopened LAN socket from a TLS authentication timeout after the socket opens.

For UFW, inspect `sudo ufw status verbose` and the kernel log while retrying. Substitute the device port from **Paired devices** in this example:

```sh
journalctl -k --since '10 minutes ago' --no-pager -g 'UFW.*DPT=44233'
```

`[UFW BLOCK]` with the phone's source address, desktop destination address and device port proves that the firewall dropped the connection before pairing. Allow that source to reach only the device listener. For example, for phone `192.168.1.65`, desktop `192.168.1.203`, interface `enp0s31f6` and device port `44233`:

```sh
sudo ufw allow in on enp0s31f6 proto tcp from 192.168.1.65 to 192.168.1.203 port 44233 comment 'Raticode phone LAN'
```

Use your actual addresses, interface and port. This does not open the desktop UI API or grant device trust. If DHCP changes the phone address, update the rule or reserve its address in the router. Remove the rule when no longer needed using the same command with `ufw delete allow` instead of `ufw allow`.

After fixing reachability, tap **Connect** in Desktop for an existing pairing. If the phone was unpaired on desktop, scan a fresh invitation and confirm it on desktop. New phone pairings enable workspace sharing by default. A firewall change does not require reinstalling the phone app or resetting its data.

## Background sync, files and recovery

The app reconnects when opened. Leaving it disconnects unless **Enable background sync** starts the visible foreground service. Android can stop or time-limit that service. Enable generic response notifications separately; previews never contain message text. Denying notifications does not stop foreground chat.

**Task progress** appears by itself while background sync is on and a task you started from this phone is running: one ongoing notification with Plan, Work, Check and Report and the time so far. It needs **Use Raticode from this phone** and permission to show notifications. Tap **Hide** (or swipe it away where Android allows) and it stays away for that task; Android's **Task progress** notification category turns it off altogether.

To check battery use on a real phone, turn on background sync, start a task of several minutes from the phone, leave the screen off, and compare the battery used by Raticode in Android's battery settings with a similar period of background sync and no running task.

**Rem chat notifications** (Desktop › Background & notifications, off by default) alert you to Rem's replies and task updates for requests sent from this phone, with a **Reply** button. They need **Use Raticode from this phone** and a desktop that supports them; the settings say when the desktop needs an update. They arrive only while the phone is connected: with Raticode open, voice mode open, or background sync on. Messages that arrived while the phone was away alert when it reconnects. Alerts say only "New message" or "Task update" unless you also turn on **Show Rem's words**; the lock screen never shows the words. Replying asks you to unlock first. If Android blocks notifications, or you turn off the Rem category in Android settings, Rem's messages still appear in Rem's chat, and the settings link to the right Android page.

With that on, **A task needs you**, **A task finishes** and **Proposals are waiting** add alerts about work this phone didn't start, and **Quiet hours** silences alerts during the hours you pick without holding them back. All four are off by default. The three alert switches need a desktop new enough to support them; until then the settings ask you to update Raticode on your computer.

**Files** opens controls for the selected conversation. Send uses Android's scoped picker, uploads verified bytes and allows attaching the resulting file to a message. Incoming offers require Download, then Export to a chosen destination or Open in another app. Files are limited to 10 MiB and encrypted local storage to 50 MiB. Exported copies are outside the app's encryption.

Clear completed local history preserves drafts and pending requests. Forget pairing deletes live trust and queued local work and requires confirmation; it is not a normal update step. Unpair the phone separately on desktop, or use Revoke to block its old identity. Fixed diagnostics describe authentication, confirmation, route, relay rate limits and storage failures without exposing secrets or raw exceptions.

## Repeatable verification and remaining acceptance

`./gradlew assembleDebug testDebugUnitTest lintDebug` builds and runs local checks. Run interaction tests only on a disposable emulator. The tests reset its application data. `scripts/live-device-fixture.py` uses temporary keys/registry and the real desktop dispatch bridge with a canned provider. Start it with the desktop environment; it uses this repository's `src` unless `PYTHONPATH` names another, push its temporary invitation to the emulator, then run a specific fixture test. A fresh fixture/invitation is required for each independent pairing test.

```sh
./gradlew connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=dev.raticode.mobile.LiveDeviceTest \
  -Pandroid.testInstrumentationRunnerArguments.deviceInvitationFile=/data/local/tmp/raticode-test-invitation.txt
```

`scripts/run-desktop-fixture-test.sh` does all of this for one test, against this checkout's desktop code. It needs the repository's `.venv` and a running headless emulator. CI runs it when **Mobile Android CI** is started by hand with its desktop fixture option.

`LiveLanRecoveryTest` uses a fresh fixture to verify that a pending enrollment with a stale QR address recovers through a manually entered address without changing the QR bytes. Its other test exercises pending-pair controls on a narrow screen, invalid address rejection and fixed unreachable-address guidance.

`LiveMessagingTest` uses a fresh fixture with actual pinned TLS over the emulator's Wi-Fi network. It exercises message delivery, a simulated Wi-Fi outage and recovery, scoped new conversations and reconnect without duplicate replies. `LiveRouteTest` checks that a refused first connection recovers with the original QR bytes; pass `pendingUnclaimed=true` for the pending-identity variant.

`LiveRefusedRequestTest` uses a fresh fixture. Pass `refusedInvitationFile`. It pairs, puts a request for a file the desktop no longer has at the front of the phone's queue, as when a download outlives the desktop's one-hour offer while the phone sleeps, and reconnects. It checks that the desktop answers the request instead of hanging up, that the phone drops it and shows why, that a later message still gets its reply and that a reconnect brings no duplicate. Against a desktop without answered refusals it fails: the phone signs in, is cut off and shows "The Wi-Fi connection to desktop was interrupted" on every retry.

Physical phone Wi-Fi/mobile-data transitions, actual provider execution from a phone, Wi-Fi endurance, two-host acceptance, signed upgrades and independent security review remain release gates. Local canned responses do not clear those checks. See [release readiness](release-readiness.md).

`LiveCreationTest` uses `--workspace --delay-grant --slow-lan` on a fresh fixture. It delays the first server packet header and body beyond the socket polling interval, keeps a typed draft while waiting for project access in the thread-list composer, creates a conversation, receives a canned reply and reconnects without duplicate history. Pass `creationInvitationFile` and optionally `creationOrientation=landscape` to instrumentation.

`LiveRemoteTest` uses a fresh `scripts/live-device-fixture.py --workspace --remote` peer. Pass `remoteInvitationFile`. ### Verify Rem, organizations and desktop settings

`LiveDesktopControlTest` uses a fresh `scripts/live-device-fixture.py --workspace --remote --desktop` peer. Pass `desktopInvitationFile`. It turns on desktop control for the phone, messages an in-memory Rem, taps a suggested reply under its answer and checks it reaches the desktop once while a typed draft stays in the box, runs and creates tasks, opens a work thread, approves a task and pauses and starts a real desktop organization in a temporary folder, changes the desktop theme through a stand-in settings window, and reads usage. The fixture writes what the desktop received to `/tmp/raticode-test-desktop.json`. No provider, workflow, agent or swarm runs.

`LiveBrowserTest#browserWithComputerTabs` uses a fresh `scripts/live-device-fixture.py --workspace --remote --desktop --browser` peer and `browserInvitationFile`. `--browser` makes the fixture's stand-in desktop window publish two web tabs (one of them Rem's) and a local preview through the desktop's real `browser_exchange`, and write the pages phones sent to it to `raticode-test-browser.json` under `RATICODE_FIXTURE_OUT`. The test opens the browser from More, checks the start page lists the computer's web tabs and not the preview, that `http` and `javascript:` addresses are explained or refused, opens a computer tab on the phone, sends it back with **Open on your computer** (the host checks `raticode-test-browser.json` lists `https://example.com/`), and checks **Ask Rem about this page** fills Rem's message box without sending. Loading the page itself is checked only when the emulator has internet access.

`LiveFirefoxBrowserTest#firefoxAsThePhonesBrowser` uses the same `--browser` fixture and `firefoxInvitationFile`, plus Firefox for Android on the emulator: download Mozilla's x86_64 build (for example `archive.mozilla.org/pub/fenix/releases/159.0.1/android/fenix-159.0.1-android-x86_64/`), check `apksigner verify --print-certs` shows Mozilla's Release Engineering certificate (SHA-256 `a78b62a5…9b04`), and `adb install` it. The test skips without it. It chooses Firefox in Browser settings, finishes Firefox's first-run screens (cancelling Android's default-browser question), opens an address as a Firefox Custom Tab, opens Firefox's Sign in and Add-ons screens, turns Firefox off with `pm disable-user` and back on, switches back to Raticode, and switches the computer to Firefox in More › Desktop settings (the fixture's `raticode-test-desktop.json` then shows `browser.engine: firefox`).

`GeckoBrowserTest` needs no paired computer, only the emulator's internet: it runs Mozilla's engine inside Raticode and installs real extensions from addons.mozilla.org, then removes them. ## Unpairing and revoked identities

Desktop now separates **Phone > Unpair** from **Revoke**. Unpair removes trust and access without adding a revoked entry. Under **Revoked devices**, **Remove from revoked list** permits fresh QR pairing without restoring the old pairing or its grants. After deliberately forgetting pairing on the phone, scan a fresh desktop QR, confirm the phone; thread sync is enabled by default. Forgetting deletes local queued messages and live history; desktop conversations remain.

A correct desktop address does not bypass revocation or prove firewall/router reachability. Restart the desktop backend to load these Python changes.


## Screenshots and APK scans

Screenshots and screen recording are allowed, including the QR camera page. Recents can show the app's contents. Pairing, encrypted storage and transport are unchanged. Version 0.5.0 requires the matching desktop backend and frontend; install the same-key APK over the existing app and restart the desktop development app. Re-pairing is unnecessary.

The provided debug APK is debuggable and signed with the Android Debug certificate. Its merged manifest requests Internet, camera, microphone, notifications and foreground data sync, plus AndroidX's app-private receiver permission. From 0.9.0 it also declares, on Android 12 and newer only, an exported voice interaction service and session service protected by the system-only `BIND_VOICE_INTERACTION` permission, an on-device speech recognition service, a Quick Settings tile and an `ACTION_ASSIST` activity alias; none of them adds a permission. It does not request accessibility, overlays, all-files access, package installation, SMS, notification-listener access, device administration or battery-optimization exemption. The source audit found no root commands or downloaded-code loader. The debug APK previously included exported Compose preview and test-host activities. Unused preview tooling has been removed and the test host is now private. These are packaging improvements, not evidence of the cause of the warning. These findings do not determine or clear a Play Protect verdict. Record the exact warning and submit a false-positive review through Google's developer process if appropriate; do not disable Play Protect.
